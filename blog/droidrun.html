The Problem Mobile automation traditionally requires scripting in Java/Kotlin/Swift or using brittle UI frameworks. Droidrun addresses this by letting an LLM drive Android/iOS devices through natural language, eliminating the need for manual UI scripting.

What This Does Droidrun is a Python framework that exposes an LLM-agnostic agent layer over mobile devices. Key components live under droidrun/agent/ - the droidagent.py, executoragent.py, and manageragent.py implement planning, execution, and trajectory writing. Tooling under droidrun/tools/android/ provides ADB-based interaction, while droidrun/credentialmanager/ and droidrun/configmanager/ handle keys and configuration. The pyproject.toml declares dependencies, and Dockerfile enables containerized deployment. CLI entry point is droidrun/cli/main.py, and the system supports multiple LLM providers (OpenAI, Anthropic, Gemini, Ollama) as noted in the README.

How To Use It Setup: Install with pip extras for desired providers: pip install 'droidrun[google,anthropic,openai,deepseek,ollama,dev]'

This pulls in the core framework and optional LLM integrators declared in pyproject.toml. Configuration: Place API keys or device credentials in config/credentialsexample.yaml (or override via environment variables). The framework references this path in droidrun/configmanager/loader.py. Running it: Invoke the CLI via droidrun or import the Python API from droidrun/main.py. For Docker deployments, the Dockerfile at root builds a containerized instance; CI workflows under .github/workflows/ include docker.yml and publish.yml for automated builds.

Real-World Use A language-learning app streak-saver demo (referenced in README) shows Droidrun navigating a mobile app, detecting UI state via screenshots, and executing a “maintain streak” command through natural language. Under the hood, droidrun/agent/executor/prompts/rev1.jinja2 and droidrun/tools/android/adb.py coordinate the touch input, element search, and LLM reasoning. A developer could extend this to automated regression testing, where an LLM agent reads screen state, decides on actions, and writes a trajectory via droidrun/agent/trajectory/writer.py.

Code Health & Issues Medium: No test files detected repository-wide. Agent execution paths, especially around credential handling and ADB interaction, are untested. (droidrun/agent/executor/executoragent.py has no corresponding test module.) Low: Dependencies are declared in pyproject.toml but uv.lock is the only lockfile present. Without a committed lockfile or requirements.txt pinned to specific versions, builds may not be reproducible across environments. CI pipelines install from PyPI each run, which can drift. Evidence: CI is configured (.github/workflows/black.yml, docker.yml), and LICENSE and CHANGELOG.md are present at root, which many open-source projects miss.

The Bottom Line Droidrun offers a well-structured, Python-first framework for LLM-driven mobile automation with solid tooling, multi-provider LLM support, and good documentation. The architecture separates concerns clearly across agent/, tools/, and configmanager/. However, the absence of test coverage and a lockfile for dependency pinning are pragmatic risks for production use. It’s well-suited for teams building custom mobile automations or prototyping LLM-agent workflows on physical/virtual devices, but requires investment in testing and dependency hygiene before shipping to end users.
