pipedash

Manage CI/CD pipelines from multiple providers (self hosted, desktop app and ios app )

Forked from hcavarsan/pipedash

The Problem Teams that adopt multiple CI/CD platforms end up juggling disparate dashboards, manual polling, and fragmented visibility. Switching between GitHub Actions, GitLab CI, Buildkite, Jenkins, Tekton, etc., creates context‑switch overhead and makes it hard to get a unified status view or to trigger builds across providers from a single place.

What This Does pipedash aggregates pipeline data from a configurable set of providers and presents it in a single UI. The core aggregation logic lives in crates/pipedash-core/src/ (e.g., pipelineservice.rs, providerservice.rs). Provider‑specific adapters are implemented as plugins under *crates/pipedash-plugin-/src/ (e.g., pipedash-plugin-github/src/client.rs). The desktop front‑end is a Tauri application located in crates/pipedash-desktop/*, with its entry point at src/main.rs and UI assets defined in tauri.conf.json. Tokens can be stored in the OS keyring, encrypted SQLite, or encrypted PostgreSQL, as implemented in src/infrastructure/secrets/ and src/infrastructure/storage/.

How To Use It

Setup Clone the repository git clone https://github.com/hcavarsan/pipedash.git cd pipedash

Install Rust toolchain (required for Cargo) rustup toolchain install stable rustup default stable

Build all workspace crates cargo build --workspace

Configuration Create a configuration file (default location is config.yaml – see src/infrastructure/config/loader.rs). Required keys include:

providers – list of provider blocks with type (e.g., github, gitlab) and authentication tokens. storage – choose sqlite (path) or postgres (connection URL). refreshintervalsecs – per‑provider polling cadence.

If you prefer encrypted SQLite, set vaultpassword in the environment; the vault password is used by src/infrastructure/config/encryptedconfig.rs to derive the AES‑256‑GCM key.

Running the Desktop App Launch the Tauri desktop client (macOS/Windows/Linux) cargo run -p pipedash-desktop

The binary compiled from crates/pipedash-desktop/src/main.rs starts the UI, loads the config, and begins polling the configured providers.

Running as a Docker Service (example) The repo includes an examples/ directory with Docker Compose snippets (not shown in the file list). Adapt the compose file to point at your config.yaml and run:

docker compose up -d # from the examples folder

Adding a New Provider Implement a plugin that satisfies the pipedash-plugin-api::Plugin trait (src/plugin.rs). Place the crate under crates/ and add it to the workspace Cargo.toml. Register the plugin in crates/pipedash-core/src/plugins/mod.rs.

Real‑World Use A DevOps team runs a self‑hosted PostgreSQL instance for token storage and a SQLite cache for pipeline history. They configure two GitHub organizations and an internal Buildkite instance in config.yaml. After starting the desktop client, a developer can view all CI runs on a single dashboard, click a failing GitHub Action, and re‑trigger it with the same inputs—all without leaving the application.

Code Health & Issues Medium – No test suite – The repository contains zero *test.rs files; CI (.github/workflows/ci.yml) runs cargo check but not cargo test. Untested paths increase regression risk. Low – Limited documentation – Only two markdown docs (README.md, PRIVACY.md) exist; there is no detailed developer guide for plugin creation or config schema beyond inline comments. Low – Secret handling reliance on env var – PIPEDASHVAULT_PASSWORD is required for encrypted storage; absence disables encryption, which may be unexpected for new users. Medium – Potential runtime race – src/infrastructure/sync/mod.rs spawns background refresh tasks per provider without explicit cancellation handling; abrupt shutdown could leave dangling async tasks. Low – License present – LICENSE file is included, satisfying legal compliance. Low – CI coverage – GitHub Actions workflow runs cargo fmt --check and cargo clippy -- -D warnings, showing attention to code style and linting.

The Bottom Line pipedash delivers a functional, extensible Rust‑based aggregation layer for multi‑provider CI/CD visibility, with a polished Tauri desktop front‑end. The architecture is clean and the plugin system is well‑structured, but the lack of automated tests and sparse developer documentation mean additional effort is needed before adopting it in a production‑critical environment. It is a solid fit for teams that need a unified view and are comfortable managing Rust builds and configuring their own storage backends.
