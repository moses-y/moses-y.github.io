The Problem

Technical teams need a workflow engine that can be scripted, extended, and self‑hosted without sacrificing visibility into data flows. Existing low‑code platforms hide the execution environment, making compliance, debugging, and AI integration difficult.

What This Does

n8n delivers a visual automation canvas backed by a full Node.js runtime. Core server code lives under packages/ (≈17 k files) with the AI agent layer in packages/@n8n/agents. The UI is a mix of React and Vue components, while the backend uses Express and a set of TypeScript services. Docker support (docker/images/*) enables reproducible deployments, and a monorepo layout is managed by pnpm (package.json at the root and per‑package package.json files).

Key files:

  • packages/@n8n/agents/src/index.ts – entry point for the AI‑agent SDK.
  • packages/@n8n/ai-node-sdk/src/index.ts – public API for custom AI nodes.
  • docker/images/n8n/Dockerfile – production container that installs the workspace and starts the server.

The repository also ships a suite of benchmark scripts (packages/@n8n/benchmark/scripts/) that validate performance across Docker, cloud, and on‑prem environments.

How It Is Wired

Execution for the benchmark tooling starts at packages/@n8n/benchmark/scripts/run.mjs (main on line 19). The call graph shows:

  • main → ensureEnvVar (6×) → reads required env vars.
  • main → $ (4×) → shell execution wrapper used by Docker helpers.
  • main → writeGithubOutput (4×) → writes CI artifacts via fs.appendFileSync (the only filesystem side‑effect).

$ itself invokes sh (3×) for Docker‑compose commands. The hub .github/scripts/github-helpers.mjs provides 25 functions (e.g., pickHighestReleaseTag, resolveReleaseTagForTrack) and is called from 11 locations, making it the widest‑impact module.

The only outbound network call in the resolved graph is in packages/@n8n/scan-community-package/scanner/scanner.mjs (downloadAndExtractPackage). All other internal edges stay within the monorepo, indicating a relatively self‑contained code base.

No cycles were detected in the resolved call graph; the longest dependency chain is three hops (main → ensureEnvVar → writeGithubOutput). This keeps change impact low for most modifications.

How To Use It

# Clone the fork
git clone https://github.com/moses-y/n8n
cd n8n

# Install dependencies (pnpm is the declared package manager)
pnpm install

# Build the Docker image used for production
docker build -t n8n -f docker/images/n8n/Dockerfile .

# Run the server (default port 5678)
docker run -p 5678:5678 n8n

Configuration is driven by environment variables; ensureEnvVar checks for their presence at startup. Example required vars are listed in .env.local.example. For AI nodes, import the SDK from packages/@n8n/ai-node-sdk/src/index.ts and register custom handlers in your workflow code.

Real‑World Use

A microservice that enriches incoming webhook data with an LLM can be built as a custom node using the AI SDK:

import { createAgent } from '@n8n/agents';
import { OpenAI } from '@n8n/ai-node-sdk';

const agent = createAgent({
  model: new OpenAI({ apiKey: process.env.OPENAI_KEY }),
  prompt: 'Summarize the payload',
});

export const execute = async (input) => ({
  summary: await agent.run(input),
});

Deploy the workflow via the visual editor or the CLI; the node runs inside the same Docker container, preserving data locality.

Code Health & Issues

Static analysis identified eight concrete findings:

  • HIGH – Pin GitHub Actions to commit SHA (.github/workflows/*).
  • MEDIUM – Add least‑privilege permissions for GITHUB_TOKEN (docker-build-smoke.yml).
  • MEDIUM – Pin base image by digest (.devcontainer/Dockerfile).
  • MEDIUM – Add a dependency‑vulnerability scan step (.github/workflows/*).
  • MEDIUM – Move large binary fixtures to Git LFS (packages/@n8n/workflow-sdk/.../public_published_templates.zip).
  • MEDIUM – Set persist-credentials: false on checkout (docker-build-push.yml).
  • MEDIUM – Review/disable preinstall script in package.json.
  • LOW – Add timeout-minutes to long‑running jobs (ci-check-release-from-fork.yml).

Tests (5626 files) and CI (GitHub Actions) are present, but the repo also contains committed PEM certificates (packages/@n8n/syslog-client/test/fixtures/*.pem) that should be reviewed for secret leakage.

The Bottom Line

n8n offers a highly extensible, self‑hostable workflow engine with solid TypeScript architecture and built‑in AI support. The code base is modular, with clear entry points and limited side‑effects, making it approachable for custom development. Addressing the listed security hardening items—especially action pinning and token permissions—will bring the repo to a production‑ready posture for organizations that need full control over automation pipelines.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2.1.0
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Declare least-privilege permissions for GITHUB_TOKENmedium
.github/workflows/docker-build-smoke.yml
1 workflow(s) declare no permissions, 1 of them reference secrets
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Pin the container base image by digestmedium
.devcontainer/Dockerfile
node:${NODE_VERSION}-alpine
An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.
Fix: Use image:tag@sha256:<digest> and enable Dependabot's docker ecosystem.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Move large binaries to Git LFS or out of the repositorymedium2 occurrences
packages/@n8n/workflow-sdk/test-fixtures/real-workflows/public_published_templates.zip
2 blobs over 5MB: public_published_templates.zip 10.9MB, mockApiData.json 6.0MB
One repository here carries twenty blobs over 5MB including a 10.9MB spreadsheet, so every clone and every CI checkout pays for data nobody diffs.
Fix: Track those extensions with LFS, or move datasets to object storage and fetch them in a setup step.
Set persist-credentials: false on checkoutmedium
.github/workflows/docker-build-push.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Review the install lifecycle script and disable scripts in CImedium
package.json
preinstall
Install scripts are the execution vector for every npm compromise from event-stream onward, and a postinstall that fetches a binary makes the build depend on a URL nobody reviews.
Fix: Move the work into an explicit build step, or set ignore-scripts in CI and run it by name.
Set timeout-minutes on the workflow jobslow2 occurrences
.github/workflows/ci-check-release-from-fork.yml
2 workflow(s) declare no job timeout
A wedged step runs to the six-hour platform default, which on a two-hourly schedule means three runs overlap behind it.
Fix: Add timeout-minutes with a realistic bound to each job.
