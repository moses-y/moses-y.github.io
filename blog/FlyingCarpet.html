The Problem: Moving files between heterogeneous devices without a shared network or cloud infrastructure is unexpectedly difficult. AirDrop works only within Apple’s ecosystem, and traditional hotspots either require infrastructure mode or disable internet connectivity. FlyingCarpet addresses this with a cross-platform ad-hoc WiFi transfer protocol, optionally using Bluetooth for negotiation, targeting Android, iOS, Linux, macOS, and Windows simultaneously.

What This Does: The repository implements a peer-to-peer file transfer stack across five platforms. Core logic lives in core/src/ — sending.rs, receiving.rs, lib.rs, with platform-specific modules under core/src/linux/ and core/src/windows/. The Android client is written in Kotlin; Android/FlyingCarpet/app/src/main/java/dev/spiegl/flyingcarpet/ contains Send.kt, Receive.kt, Bluetooth.kt, and MainActivity.kt. The desktop GUI is built with Tauri; entry points include Flying Carpet/src-tauri/src/main.rs and tauri.conf.json. Version 9 added Bluetooth-mediated transfer negotiation, as noted in README.md and Android/FlyingCarpet/app/src/main/java/dev/spiegl/flyingcarpet/Bluetooth.kt.

How To Use It: Setup requires Rust and the Tauri CLI. From the README: install Rust, then cargo install tauri-cli. Build with cargo tauri dev for development or cargo tauri build for release artifacts. Android users can download from Google Play or F-Droid; iOS from the App Store. Linux, macOS, and Windows installers are available on the releases page. Configuration is minimal — the Android manifest (AndroidManifest.xml) requires API level 29+, and macOS-to-Linux Bluetooth transfers need prior manual pairing, as documented in the README. No environment variables or secret keys are required for basic operation.

Real-World Use: A user on a Linux workstation needs to transfer a 1.2 GB design archive to an Android tablet in a location without WiFi. Both devices run Flying Carpet; the Linux host creates an ad-hoc hotspot, the Android device joins, and the file transfers directly over WiFi without internet. The transfer negotiates the connection via Bluetooth if enabled, per the protocol in core/src/linux/central.rs and core/src/windows/central.rs.

Code Health & Issues: No CI/CD pipeline — .github/ contains only FUNDING.yml; no automated build or test gate exists. Test coverage is limited to two Android test files (ExampleUnitTest.kt, ExampleInstrumentedTest.kt); no unit tests for the Rust core or cross-platform logic are present. Platform restrictions are well-documented (Android API 29+, macOS Bluetooth pairing requirements, hotspot-induced internet loss), but not validated in an automated pipeline. Dependency files (Cargo.toml, build.gradle) are present but no automated vulnerability scanning or update workflow is configured.

The Bottom Line: FlyingCarpet delivers a functional, multi-platform ad-hoc file transfer solution with a clean Rust/Tauri codebase and solid platform-specific implementations. It’s well-suited for personal or informal team use where network infrastructure is absent.
