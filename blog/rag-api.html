The Problem

Enterprises that need to expose document‑wide question‑answering across many customers run into two issues: (1) keeping each tenant’s data isolated while sharing the same retrieval infrastructure, and (2) handling the wide variety of file formats (PDF, Word, images, tables, formulas) without building a custom parser stack for every use‑case.

What This Does

rag-api delivers a multi‑tenant Retrieval‑Augmented Generation service that couples LightRAG (graph‑based retrieval) with RAG‑Anything (multimodal parsing). The code base is organized around three domains:

  • src/ – core engine (config, multi‑tenant manager, parsers, rate‑limiter, metrics).
  • src/multi_tenant.py creates per‑tenant LLM and embedding functions and is the hub for tenant isolation.
  • src/smart_parser_selector.py picks the best parser (DeepSeek‑OCR, MinerU, Docling) using the complexity scorer in src/document_complexity.py.
  • src/rag.py runs the LightRAG retrieval pipeline.
  • api/ – FastAPI request handlers (documents.py, insert.py, query.py, etc.) that translate HTTP calls into engine actions.
  • scripts/ – operational helpers; scripts/migrate_tenant.py is the only CLI entry that performs tenant migration.

The top‑level main.py starts the FastAPI server, wiring the router defined in api/__init__.py to the engine modules.

How It Is Wired

  1. Startup – python main.py (or the Docker entrypoint) creates the FastAPI app.
  2. Request flow – an incoming HTTP call hits a handler in api/. For a document upload the path is: api/insert.insert_document → src/multi_tenant.get_tenant_lightrag (called from 9 places) → src/rag.process_document_task → parser selection (src/smart_parser_selector.select_parser) → concrete parser (src/deepseek_ocr_client, src/mineru_client, or src/docling_client) → vector store write (Qdrant via src/rate_limiter.acquire and src/tenant_config) → task persistence (api/task_store).

The most fan‑in functions are src/logger (22 imports) and api/insert (high instability). Changing src/logger has the widest blast radius.

  1. External effects – File system – parsers open PDFs/Docs (open without context manager in src/deepseek_ocr_client.py and src/document_complexity.py). Network – OCR calls (requests.get in deepseek_ocr_client), MinerU remote API (src/mineru_client), and tenant config fetches. * Database – task CRUD (api/task_store) writes to Redis/DragonflyDB; tenant config reads/writes JSON files (src/tenant_config.py).
  1. Rate limiting – every outbound call passes through src/rate_limiter.acquire, which is invoked from 8 locations, making it a critical throttling point.
  1. Metrics – src/metrics.py records response times and error rates; these are called from the monitoring endpoints in api/monitor.py.

The internal call graph shows 290 resolved intra‑repo edges; the most reused utilities (get_tenant_config_manager, DocumentFeatures, ParseOptions) appear in 5–7 places each, indicating they are natural extension points.

How To Use It

# Clone the repo
git clone https://github.com/moses-y/rag-api
cd rag-api

# Build the container (uses uv for dependency resolution)
docker build -f Dockerfile -t rag-api:latest .

# Run the stack (FastAPI + Qdrant vector store)
docker compose up -d   # uses docker-compose.yml

# The API is now reachable at http://localhost:8000
# Swagger UI: http://localhost:8000/docs

Configuration – tenant isolation and parser keys are read from files under src/tenant_config.py and environment variables referenced there (e.g., DEEPSEEK_API_KEY). No secret files are committed; provide them at container start.

CLI migrations – to migrate an existing tenant configuration:

python scripts/migrate_tenant.py --old-id old_tenant --new-id new_tenant

The script uses src/multi_tenant to copy vector data and task records.

Real‑World Use

A SaaS provider can spin up a single rag-api service behind a tenant‑aware gateway. When a client uploads a contract PDF, the service routes the request to api/insert, the smart selector chooses DeepSeek‑OCR for complex layout, stores embeddings in Qdrant, and later answers queries via api/query using LightRAG’s hybrid graph retrieval. All tenant data remains isolated by the per‑tenant manager in src/multi_tenant.py.

The Bottom Line

rag-api provides a functional, container‑ready multi‑tenant RAG service with solid architecture (FastAPI + LightRAG + auto‑parser selection). It is usable out of the box but needs hardening: add a license, tighten CI security, improve test coverage, and refactor the most complex modules before extending it in production. Suitable for teams comfortable with Python, Docker, and FastAPI who can invest in the outlined cleanup.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
astral-sh/setup-uv@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Add a LICENSE; redistribution rights are undefinedhigh
no licence file at the repository root
With no licence the default is all rights reserved, so this code cannot legally be reused, which matters most for the owner's own work carried into client engagements.
Fix: Add MIT or Apache-2.0 at the repository root.
Declare least-privilege permissions for GITHUB_TOKENmedium
.github/workflows/ci-basic.yml
1 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.

An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.

This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.

Add a non-root USER to the imagemedium
Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
