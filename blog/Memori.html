Memori

Memori is agent-native memory infrastructure. A LLM-agnostic layer that turns agent execution and conversation into structured, persistent state for production systems.

Forked from MemoriLabs/Memori

The Problem LLM‑driven agents typically lose context once a request ends, forcing developers to re‑inject prior facts manually. This adds boilerplate, increases latency, and makes multi‑turn or multi‑user scenarios fragile.

What This Does Memori provides a language‑agnostic runtime that records every agent action (LLM calls, tool use, state changes) into a persistent store and surfaces that history as structured context for subsequent calls.

The core runtime lives in core/src/ (Rust) and implements augmentation, embeddings, retrieval, and storage pipelines (src/augmentation/, src/embeddings/, src/retrieval/, src/storage/). Language bindings are in core/bindings/python/ (src/lib.rs) and core/bindings/node/ (src/lib.rs, src/engine.rs). They expose a single entry point (Memori class) that can be chained with an LLM client (OpenAI, Anthropic, etc.). Documentation and example integrations are under docs/ and examples/, e.g., the Python quick‑start in examples/agno/main.py.

How To Use It

Setup Python SDK pip install memori # from PyPI, see badge in README or TypeScript SDK npm install @memorilabs/memori

If you need to build the native Rust core locally (e.g., for custom extensions): cd core make # uses Cargo.toml; builds lib and bindings

The repo also ships a Docker image: docker build -t memori .

Configuration Create a .env (or export) with the keys required by the SDKs:

MEMORIAPIKEY=yourmemorikey OPENAIAPIKEY=youropenaikey # or ANTHROPICAPIKEY, etc.

The example scripts read these variables directly (see examples/agno/.env.example).

Running For a minimal Python demo:

cd examples/agno python -m pip install -r requirements.txt # if needed python main.py

The script registers an OpenAI client, attributes the session (mem.attribution(...)), sends two chat completions, and demonstrates automatic recall.

For a TypeScript run, the equivalent is in examples/agno/main.ts (not listed but implied by the Node binding) and can be started with npm run start after installing the package.

Real‑World Use A support chatbot can call Memori().llm.register(openaiclient) at startup. Each user interaction is automatically stored with an entityid (e.g., user UUID) and a processid (e.g., ticket number). When the same user asks a follow‑up, the SDK injects the prior conversation into the prompt, eliminating the need for custom session handling.

mem = Memori().llm.register(OpenAI()) mem.attribution(entityid=userid, processid="support") subsequent calls automatically include prior messages

Code Health & Issues Low – Missing platform‑specific CI – The repo contains GitHub Actions for Rust (core-ci.yml) and TypeScript (ts-ci.yml) but no explicit Python CI workflow; Python bindings rely on the same Rust CI, which may miss Python‑specific test failures. Medium – Limited test coverage – Only four test files exist (all in core/tests/). No tests for the Python or Node bindings, so integration bugs could surface at runtime. Low – License present – LICENSE is Apache‑2.0, compliant with most commercial use. Medium – Dependency hygiene – core/bindings/node/package-lock.json pins npm packages, but there is no automated vulnerability scanning configured (e.g., Dependabot). Low – Documentation depth – 102 markdown files provide extensive guides, but the main README lacks a quick command to start the Rust core as a service; users must infer make or Docker usage. Low – No secret detection – .env.example files are present, but there is no pre‑commit hook to block accidental commits of real keys (the repo includes .pre-commit-config.yaml but no specific secret‑scan hook).

Overall, the codebase compiles cleanly, CI runs on push, and the core library is well‑structured.

The Bottom Line Memori offers a solid, language‑agnostic memory layer for LLM agents, with production‑ready Rust core and mature SDKs for Python and TypeScript. It is best suited for teams that can manage native builds or prefer Docker deployment and are comfortable adding their own integration tests for the language bindings. The primary gaps are limited Python/Node test coverage and the absence of a dedicated CI pipeline for those ecosystems.
