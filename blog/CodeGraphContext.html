The Problem

AI coding assistants lack awareness of a project's full codebase structure. Developers waste context windows pasting file contents, and AI agents hallucinate imports, APIs, and dependencies because they cannot query the actual dependency graph of a repository. Standard file-search tools don't expose relationships like "what calls this function" or "which modules depend on this class."

What This Does

CodeGraphContext (CGC) is an MCP server and CLI tool that indexes local source code into a queryable graph database. The core logic lives in cgcentry.py and the .github/workflows/ directory shows a mature CI pipeline with e2e, build, and test workflows. The extensions/vscode/ folder provides a VS Code extension with MCP client integration (src/mcp/client.ts), context management (src/mcp/contextManager.ts), and webview panels for call graphs and dashboards (src/webview/callGraphPanel.ts).

The project supports multiple backends via the docs/docs/concepts/backends.md documentation and includes Docker deployment (Dockerfile, docker-compose.template.yml), Kubernetes config (k8s/README.md), and a .cgcignore file for exclusion patterns. The docs/ directory contains 54 Markdown files covering architecture, bundles, CLI reference, and integration guides.

Real-World Use

A developer onboarding to a 100k-line Python monorepo runs cgc index . to build the graph, then queries it from Cursor or VS Code: "Show me all callers of processpayment() in the billing module." The AI assistant receives the relevant subgraph instead of raw file contents, producing accurate code generation and refactoring suggestions.

The Bottom Line

CGC solves a genuine problem for teams using AI coding assistants on large codebases. The architecture is sound (MCP server + CLI + IDE extension) and the documentation is thorough. However, the provenance ambiguity (0 stars, forked from 4049 stars) and missing core tests are concerns. Worth evaluating for teams that already use MCP-compatible tools and need graph-based code context.

Pin third-party GitHub Actions to a commit SHAhigh6 occurrences
.github/workflows
softprops/action-gh-release@v2, peaceiris/actions-gh-pages@v4, docker/setup-buildx-action@v3, docker/login-action@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Commit a lockfile beside the manifesthigh
pyproject.toml
manifest with no lockfile in scope
An unlocked range means the artifact you tested and the artifact you ship can contain different transitive code, so a malicious patch release reaches production with no diff.
Fix: Run the package manager once and commit the generated lockfile.
Replace the wildcard CORS origin with an explicit allow listhigh
src/codegraphcontext/api/app.py
allow_origins=["*"] together with credentials enabled
Any page on the internet can call the API with the browser's cookies attached, so a logged-in visitor to an unrelated site performs authenticated requests without knowing, and the wildcard combined with credentials is the exact configuration browsers refuse for that reason.
Fix: List the origins the API actually serves, and never pair a wildcard with credentials.

With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.

The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
