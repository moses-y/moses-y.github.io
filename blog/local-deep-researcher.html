The Problem

Users who want a fully local research assistant must stitch together a language model, web‑search APIs, and custom summarisation logic. Doing that manually leads to version drift, secret leakage, and brittle scripts that are hard to maintain.

What This Does

local-deep-researcher provides a single Python package that coordinates an LLM (via Ollama or LMStudio) with a configurable web‑search backend (DuckDuckGo, SearXNG, Tavily, Perplexity). The core workflow lives in src/ollama_deep_researcher/graph.py and implements:

  • Search‑query generation – generate_search_query_with_structured_output builds a query from the current research state.
  • Web retrieval – web_research calls one of the search helpers (duckduckgo_search, searxng_search, etc.) and deduplicates the results.
  • Summarisation & reflection – summarize_sources and reflect_on_summary feed the LLM (via get_llm → ChatLMStudio) to produce a markdown report and identify knowledge gaps.

Configuration (model URLs, API keys, number of cycles) is read from .env and wrapped by src/ollama_deep_researcher/configuration.py.

How It Is Wired

Execution starts with a call to web_research (the public entry point) in graph.py. The call chain is:

  1. web_research → from_runnable_config (5 callers) to load Configuration.
  2. web_research → get_config_value (utility for env look‑ups).
  3. web_research → one of the search functions (duckduckgo_search, searxng_search, tavily_search, perplexity_search, searxng_search). Each makes an outbound HTTP request (no timeout – see health).
  4. Results → deduplicate_and_format_sources → format_sources (both in utils.py).
  5. Summarisation path: web_research → generate_search_query_with_structured_output → get_llm → ChatLMStudio (instantiates the LLM client).
  6. ChatLMStudio → _generate runs the model inference.

The graph module owns eight functions and two types, acting as the hub (≈22 internal call edges). utils.py supplies nine helper functions; it is the only file that performs network I/O outside the search helpers. No circular imports exist, and each module is isolated: configuration.py, state.py, prompts.py, lmstudio.py, and __init__.py have zero import edges.

The repository touches external resources in two ways:

  • Model inference – via the LLM client in lmstudio.py.
  • Web search – via HTTP calls in the search helpers inside graph.py (and the single outbound call in utils.py).

Because the import graph is flat, changes to a helper function (e.g., strip_thinking_tokens) have limited ripple effects, but the deep nesting in utils.py (13‑level indentation) makes its logic hard to follow and increases cognitive load for modifications.

How To Use It

# Clone the forked repo (use the exact URL as required)
git clone https://github.com/moses-y/local-deep-researcher.git
cd local-deep-researcher

# Install dependencies (uv is recommended because uv.lock is present)
uv sync          # creates a virtualenv and installs from pyproject.toml

# Copy example environment and edit as needed
cp .env.example .env
# Edit .env: set LLM_PROVIDER, model name, API keys for the chosen search service

# Build and run the container (optional)
docker build -t local-deep-researcher .
docker run --rm -e $(cat .env | xargs) local-deep-researcher

The package does not expose a CLI script; programmatic use is via:

from ollama_deep_researcher.graph import web_research

report = web_research(topic="quantum computing", cycles=3)
print(report)

Adjust topic and cycles to control depth. The Configuration class will read values from the environment.

Real‑World Use

A knowledge‑base microservice can import web_research to generate on‑demand research briefs. For example:

def get_brief(topic):
    return web_research(topic=topic, cycles=2)

This call runs entirely locally, avoiding external SaaS costs while still harvesting fresh web content.

Code Health & Issues

  • Critical – Secret ANTHROPIC_API_KEY is hard‑coded in .github/workflows/claude.yml. Move secret‑using steps to a workflow_run job or gate them behind a protected environment.
  • High – GitHub Actions are referenced by mutable tags (anthropics/claude-code-action@beta, docker/setup-qemu-action@v3, etc.). Pin each to a full commit SHA.
  • Medium – Base image python:3.11-slim is not pinned by digest; use python@sha256:<digest>.
  • Medium – No dependency‑vulnerability scan in CI; add dependency-review-action or osv-scanner.
  • Medium – Outbound HTTP calls lack a timeout (see utils.py). Supply timeout= or a configured requests.Session.
  • Medium – Checkout step retains the GITHUB_TOKEN; set persist-credentials: false and pass the token only where needed.
  • Medium – Dockerfile runs as root; add a non‑root user and switch with USER.
  • Low – Workflow jobs have no timeout-minutes; set a reasonable bound to avoid overlapping runs.

Additional observations: the repo contains no test suite, and the Python dependencies are not locked (no requirements.txt or poetry.lock). The presence of uv.lock suggests a lockfile exists but is not used by the CI pipeline.

The Bottom Line

local-deep-researcher stitches together local LLMs and web search into a single, easy‑to‑invoke Python function, which is valuable for privacy‑focused research pipelines. However, the codebase suffers from security‑critical workflow secrets, missing dependency pinning, and a lack of automated tests, making it risky for production without remediation. It is best suited for internal prototypes or teams prepared to harden the CI/CD and add test coverage.

Keep secrets out of workflows a fork can triggercritical

ANTHROPIC_API_KEY
Contributor-controlled input reaches a job holding a publish token or cloud credential, so a pull request becomes credential exfiltration.
Fix: Move secret-using steps into a workflow_run job that never checks out pull request code, or gate on an environment with required reviewers.
Pin third-party GitHub Actions to a commit SHAhigh6 occurrences
.github/workflows
anthropics/claude-code-action@beta, docker/setup-qemu-action@v3, docker/setup-buildx-action@v3, docker/login-action@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.

Dockerfile
python:3.11-slim
An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.

.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Give the outbound request a timeoutmedium
src/ollama_deep_researcher/utils.py
1 outbound call(s) with no timeout
requests has no default timeout, so a peer that accepts the connection and then says nothing holds the worker forever, and with a small worker pool a single slow dependency takes the whole service down without anything appearing to fail.
Fix: Pass timeout= on every call, or use a session with one configured.
Set persist-credentials: false on checkoutmedium
.github/workflows/claude.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Add a non-root USER to the imagemedium
Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
Set timeout-minutes on the workflow jobslow3 occurrences
.github/workflows/claude-code-review.yml
3 workflow(s) declare no job timeout
A wedged step runs to the six-hour platform default, which on a two-hourly schedule means three runs overlap behind it.
Fix: Add timeout-minutes with a realistic bound to each job.
