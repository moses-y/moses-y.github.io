The Problem

Generating documentation for large, multi-language codebases is impractical with traditional comment-extraction tools. These tools produce per-function docs that miss cross-module dependencies, architectural intent, and the overall system design that developers actually need to onboard or modify unfamiliar repositories.

What This Does

CodeWiki is a CLI and web application that analyzes entire repositories holistically to produce structured, architecture-aware documentation. The core pipeline lives in codewiki/src/be/ and consists of a dependencyanalyzer (with per-language AST parsers for Python, Java, C++, TypeScript, and 5 other languages), a clustermodules step that groups related code into logical modules, and a documentationgenerator that calls LLM backends to write prose. The CLI entry point at codewiki/cli/main.py wraps this in a generate command and a config set command for managing LLM provider settings (OpenAI, Anthropic, AWS Bedrock, Azure, or local subscription via Claude Code/Codex).

The framework outputs HTML documentation with visual dependency graphs, available as static pages or served via the Flask web app in codewiki/src/fe/webapp.py. The project documents itself—generated docs live in the docs/ folder and are published to GitHub Pages.

Real-World Use

A team inheriting a 500K-line monorepo with Python backend, TypeScript frontend, and Java services runs codewiki generate . --output docs/. CodeWiki parses all three languages, builds a dependency graph, clusters modules by functionality, and produces a navigable HTML site showing module responsibilities, cross-module calls, and API surfaces—without the team writing any documentation by hand.

The Bottom Line

CodeWiki solves a genuine problem for teams maintaining large, multi-language codebases where manual documentation is impractical. The architecture is well-structured with clear separation between analysis, generation, and presentation layers. However, the complete absence of tests and CI makes it risky to adopt in production workflows—this is a research prototype (ACL 2026 submission) that needs hardening before it belongs in a team's documentation pipeline. Best suited for evaluation on non-critical repositories.
