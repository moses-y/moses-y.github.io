The Problem

Meshtastic nodes only see traffic they generate or that passes through a single‑radio gateway. Operators who want full visibility of all packets, remote configuration, or a web‑based chat interface must either run a proprietary gateway or build a custom solution that stitches together a concentrator, a database, and a UI. That adds hardware, software, and maintenance overhead.

What This Does

meshpoint turns a Raspberry Pi 4 plus an SX1302/SX1303 concentrator into a full‑featured base station. The radio driver runs on the Pi, captures eight parallel LoRa channels, and can transmit with up to 27 dBm. All captured packets are stored in a local SQLite DB and exposed through a browser UI located under frontend/.

Key UI components live in frontend/index.html and frontend/js/app.js, with individual panels (e.g., frontend/js/configuration/radiocard.js, frontend/js/messagingchat.js) handling radio settings, channel management, and real‑time chat. The dashboard is served by an Express back‑end (detected from package.json dependencies), although the server entry point is not listed explicitly in the tree.

Configuration defaults are kept in config/default.yaml; the file documents region selection, relay options, and TX enable flags (see docs/CONFIGURATION.md). Documentation for onboarding, troubleshooting, and hardware compatibility lives in docs/ (e.g., docs/ONBOARDING.md, docs/HARDWARE-MATRIX.md).

How To Use It

Setup – The repo contains a GitHub Actions workflow (.github/workflows/ci.yml) that installs Node dependencies and runs tests, indicating a standard Node toolchain. Assuming a typical Node environment:

Clone and install front‑end dependencies

git clone https://github.com/KMX415/meshpoint.git cd meshpoint npm ci # installs exact versions from package-lock.json

The hardware‑specific Python layer is referenced by the README badge (python-3.11+) but no Python entry point appears in the file list. If the Python service is required, the repository is missing the launch script (e.g., meshpoint/main.py or run.py). Without it, the back‑end cannot start.

Configuration – Copy the example config and edit for your radio and network:

cp config/default.yaml config/local.yaml Edit config/local.yaml: set region, enable relay, adjust TX power, etc.

Relevant keys are documented in docs/CONFIGURATION.md#smart-relay and docs/RADIO-CONFIG-EXPLAINED.md.

Running – The UI is launched by the Express server (likely npm start or node server.js). The exact script is not present, so the safest command based on common conventions is:

npm start # expects a "start" script in package.json

If a Python gateway is required, the missing entry point must be added (e.g., python -m meshpoint). After the server is up, navigate to http://<pi-ip>:3000 (default Express port) to access the dashboard.

Real‑World Use

A community Wi‑Fi hotspot runs a Pi 4 with an SX1302 concentrator, installs Meshpoint, and points the UI at a wall‑mounted tablet. Field technicians use the web UI to add new channels, push firmware updates to nodes, and monitor signal quality in real time, all without SSHing into the device.

// Example: send a broadcast from the UI (frontend/js/messaging_chat.js) socket.emit('tx', { channelId: 0, payload: 'Hello mesh!' });

Code Health & Issues

Severity – Medium – Missing back‑end entry point – No visible server script (e.g., server.js or app.py) in the repository, making it impossible to start the service from the source. Severity – Low – Incomplete Python integration – README advertises Python 3.11+, but no Python modules or requirements.txt appear; the backend may be split across languages without clear build instructions. Severity – Low – Test coverage limited to front‑end – 16 test files exist, but they target UI components; core radio handling and database logic have no visible tests. Severity – Low – Configuration secrets – config/sudoers-meshpoint and config/journald-meshpoint.conf are shipped verbatim; if they contain host‑specific paths or privileged commands, they may need adaptation per deployment. Severity – Low – License present – AGPL‑v3 is included, satisfying open‑source compliance. Severity – Low – CI configured – GitHub Actions workflow runs linting and tests, indicating a basic SDLC process.

Overall, the repository is well‑documented (49 markdown files) and organized, but the missing executable back‑end prevents a straightforward “clone‑run” experience.

The Bottom Line

meshpoint offers a compelling, web‑based interface for a Raspberry Pi LoRa concentrator, delivering full‑mesh visibility and native TX. The front‑end is mature, but the absence of a clear server start script and the ambiguous Python component make deployment non‑trivial. It is suitable for teams comfortable with Node/Python integration and willing to fill the launch‑script gap; solo users may encounter friction until the missing pieces are supplied.

With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.

1 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
Fix: Commit .github/dependabot.yml covering the repo ecosystems plus github-actions.
