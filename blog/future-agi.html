The Problem

Teams building AI agents today must stitch together separate tools for tracing, evaluation, simulation, and guardrails. The result is fragmented observability, no closed feedback loop, and agents that fail in production without a path to self-improvement. This repo consolidates all of that into one self-hostable platform.

What This Does

Future AGI is a full-stack Python/Django + React application (7,860 files) that provides an end-to-end pipeline for LLM/agent evaluation, tracing, simulation, and guardrails. The codebase is split between frontend/ (React/JSX, 4,278 files) and futureagi/ (Python, 3,546 files). It uses Django on the backend, LangChain, vector stores, and Docker for deployment. The platform exposes a React dashboard for managing experiments, running evals, simulating agent conversations, and inspecting gateways/guardrails.

Key structural splits:

  • frontend/ – React UI, hooks, routes, and API integration
  • futureagi/ – Python backend: model serving, agent gateway, guardrails, and core logic

How To Use It

Setup (inferred from present files):

  • Docker: docker-compose.yml, docker-compose.dev.yml, docker-compose.frontend.yml are present. The frontend/Dockerfile uses node:20.17 and nginx:alpine (mutable tags — see Issues).
  • Python: futureagi/model_serving/pyproject.toml and futureagi/agentcc-gateway/go.mod indicate Python packaging and a Go gateway.
  • Package manager: yarn (lockfiles present: frontend/package-lock.json, frontend/yarn.lock).

Configuration: Environment variables are defined in .env.example (root and frontend/). Secrets baseline files exist: futureagi/.secrets.baseline, futureagi/agentcc-gateway/internal/guardrails/secrets/secrets.go, futureagi/api_docs/develop/secrets.bru — verify these are not committed.

Running it: Use docker-compose up -d from the repo root to start all services (frontend, backend, vector store, gateway). For dev mode, see docker-compose.dev.yml. The Django backend typically runs on port 8000; the React frontend on 3000.

Real-World Use

A product team prototyping an agent can:

  1. Define a dataset in the UI (frontend/src/sections/experiment-detail/...).
  2. Run an eval that scores agent traces against the dataset (backend: futureagi/model_serving/...).
  3. Simulate a voice/conversation flow in the Simulate section, which plays back agent spans.
  4. Deploy guardrails via the gateway (futureagi/agentcc-gateway/) to intercept bad outputs before they reach users.
  5. Every trace flows back into a optimization loop (frontend/src/api/model/optimize.js → useGetOptimization), closing the feedback cycle.

Code Health & Issues

The following findings are from deterministic static analysis (not opinion). Report as-is.

  • [HIGH] Pin third-party GitHub Actions to commit SHAs — .github/workflows uses @vN tags (e.g., google-github-actions/auth@v2, aws-actions/configure-aws-credentials@v4). Tags can move; pin to 40-char SHA.
  • [HIGH] Replace wildcard CORS with explicit allow list — futureagi/tfc/settings/settings.py has CORS_ALLOW_ALL_ORIGINS = True with credentials enabled. Browsers block this pattern for authenticated cross-origin requests.
  • [HIGH] CI does not invoke its test suite — 624 test files exist, but none of the 4 GitHub Actions workflows include a test-running step.
  • [MEDIUM] Declare least-privilege GITHUB_TOKEN permissions — 4 workflows declare no permissions section; token inherits repo defaults.
  • [MEDIUM] Enable Dependabot/Renovate — 9 manifests, no update bot configured.
  • [MEDIUM] Pin container base image by digest — frontend/Dockerfile uses node:20.17, nginx:alpine (mutable).
  • [MEDIUM] Gate PRs on dependency vulnerability scan — no dependency-review-action or osv-scanner in CI.
  • [MEDIUM] Move large binaries out of repo — frontend/public/assets/readme/self-host.gif is 14.6MB; Login.png is 6.0MB.
  • [MEDIUM] Set persist-credentials: false on checkout — frontend-deploy-eu.yaml keeps the token across steps.
  • [MEDIUM] Add non-root USER to Docker image — frontend/Dockerfile has no USER directive; process runs as root.
  • 2 lower-severity findings also detected.

Beyond the measured block: committed secrets are confirmed (REPOSITORY HYGIENE section). No LICENSE or CONTRIBUTING.md issues — both are present.

The Bottom Line

This is a functional, full-stack platform that collapses LLM agent evaluation, tracing, simulation, and guardrails into one self-hostable loop. The code is well-structured for a startup-scale codebase, with a small internal call graph that makes routing understandable. However, the CI gap (no test execution), mutable Docker tags, wildcard CORS, and uncommitted secrets are production-risk items that should be addressed before any non-trivial deployment. Teams that need a unified agent feedback loop today and are comfortable running Docker + Django will find immediate value; those requiring hardened supply-chain guarantees should patch the listed issues first.

Pin third-party GitHub Actions to a commit SHAhigh3 occurrences
.github/workflows
google-github-actions/auth@v2, google-github-actions/setup-gcloud@v2, aws-actions/configure-aws-credentials@v4
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Replace the wildcard CORS origin with an explicit allow listhigh
futureagi/tfc/settings/settings.py
CORS_ALLOW_ALL_ORIGINS = True together with credentials enabled
Any page on the internet can call the API with the browser's cookies attached, so a logged-in visitor to an unrelated site performs authenticated requests without knowing, and the wildcard combined with credentials is the exact configuration browsers refuse for that reason.
Fix: List the origins the API actually serves, and never pair a wildcard with credentials.

.github/workflows
624 test files, no test command in the 4 workflows read
A green check that never executed an assertion is worse than no check, because reviewers trust it.

Set persist-credentials: false on checkoutmedium
.github/workflows/frontend-deploy-eu.yaml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.

A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
