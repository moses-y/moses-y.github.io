The Problem

Managing a hierarchy of AI agents in production means constant prompt tweaks, model swaps, and access-control changes. Each one is a code change, commit, and redeploy. Costs are invisible, regressions go undetected until users complain, and there's no per-agent governance. MATE targets that gap: a control layer that keeps agent behavior configurable without touching agent code.

What This Does

MATE is a multi-agent orchestration engine on Google ADK. Agents live in a database (shared/sql/migrations/ across MySQL, PostgreSQL, SQLite) rather than in code. Configuration changes are versioned and rollback-able. The dashboard (shared/utils/dashboard/dashboardserver.py) provides a drag-and-drop builder for agent hierarchies, tool attachment, and model selection.

The engine includes RBAC per agent (shared/utils/rbacagentfactory.py, shared/utils/rbacmiddleware.py), token-usage tracking broken into prompt/response/thought/tool buckets (shared/utils/tokenusageservice.py, shared/callbacks/tokenusagecallback.py), guardrails (hallucination scoring, PII detection, prompt injection — all in shared/utils/guardrails/), and an eval framework (shared/utils/evalrunner.py) with regression thresholds that fire webhooks. MCP protocol support is in shared/utils/mcp/ with handlers for Google Drive and image generation.

How To Use It

Setup: pip install -r requirements.txt after cloning. Docker is supported via docker-compose.yml.

Configuration: Copy .env.example to .env and set at least one provider key (GOOGLEAPIKEY or any LiteLLM-supported provider). Database defaults to SQLite; migrations run automatically on startup.

Running it: Start the auth server (authserver.py), which serves the dashboard at localhost:8000 with default credentials admin / mate.

git clone https://github.com/antiv/mate.git && cd mate python -m venv .venv && source .venv/bin/activate pip install -r requirements.txt cp .env.example .env Set GOOGLEAPIKEY (or any supported provider key) python auth_server.py Dashboard: http://localhost:8000 — login: admin / mate

The README documents these commands; I did not invent them.

Real-World Use

A team runs a customer-support agent hierarchy: a triage agent routes to billing, technical, or sales sub-agents. An admin edits the billing agent's prompt in the Studio, swaps its model from Gemini to GPT-4o, and restricts it to the finance group via RBAC — all without a redeploy. The eval framework runs a test suite against the new version; a 6-point pass-rate drop triggers a webhook alert before the change reaches production. Token tracking shows the billing agent consumed 40% of the monthly budget on prompt tokens alone.

Code Health & Issues

Med — No CI/CD pipeline: .github/ contains only issue templates, no workflow files. No automated build or test gate exists. Low — No dependency lockfile: requirements.txt without pinned hashes means non-reproducible builds. Low — Stray file: agents/tmp.txt suggests leftover scratch content committed to the repo. Positive: 14 test files exist across shared/test/ covering guardrails, RBAC, migrations, and tracing. Migration system is well-structured with per-database SQL. Documentation is extensive (8 docs, 30 markdown files).

The Bottom Line

MATE is a serious attempt at production agent governance — the database-driven config, RBAC, cost tracking, and eval framework address real pain points, and the migration structure shows engineering discipline. It's better suited to teams running multi-agent systems at scale than solo projects. The lack of CI is the main gap; the no-lockfile dependency management is a secondary concern. For teams already on Google ADK, this is worth evaluating.
