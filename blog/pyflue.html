pyflue

Python port of the Flue: The Agent Harness Framework

Forked from SuperagenticAI/pyflue

The Problem

Teams building AI agents in Python face a recurring set of integration problems: wiring LLM calls to sandboxed file systems, managing session state across requests, and validating model output. PyFlue addresses this by providing a harness framework that standardizes these concerns behind a single API. It is a Python port of the Flue framework, designed for teams that need structured agent workflows rather than ad-hoc scripted LLM calls.

What This Does

PyFlue is an agent harness with a modular architecture. The core logic lives in pyflue/core.py, with separate modules for sandboxes (pyflue/sandboxes/), harness backends (pyflue/harnesses/), and routing (pyflue/routing.py). It supports four agent harnesses out of the box: OpenAI Agents, Google ADK, PydanticAI, and DeepAgents, each with a dedicated adapter in pyflue/harnesses/. Sandbox providers include virtual, Daytona, E2B, Modal, and Runloop, all behind a common interface in pyflue/sandboxes/base.py.

The framework provides Markdown-based skills (.agents/skills/*.md), stateful sessions, typed Pydantic outputs with automatic JSON repair, streaming events, and file-based webhook routing. A CLI (pyflue/cli.py) handles project initialization and local dev server, while pyflue/server.py exposes agents as HTTP endpoints. Deployment scaffolding for Docker, Railway, Render, and others is generated via pyflue/deploy.py.

How To Use It

Setup: Install with pip install pyflue or uv add pyflue. Optional extras exist for sandbox providers and the Monty Python code backend. The pyproject.toml defines dependencies and the uv.lock file exists, though the heuristic analysis flags a potential lockfile inconsistency — verify whether uv.lock is current before relying on reproducible builds.

Configuration: Project configuration lives in pyflue.toml. Skills, roles, and agent instructions are defined in .agents/ directories as Markdown files. Sandbox providers may require API keys, but the repo does not clearly document environment variable names in the README — check docs/deployment.md for provider-specific setup.

Running it: Initialize a project, then run the dev server:

pyflue init my-agent cd my-agent pyflue run --prompt "Review this project" or for the webhook server pyflue dev --port 2024

The Python API is async-first: await init(...) creates an agent, await agent.session(...) opens a session, and session.skill(...) or session.prompt(...) executes work. A concrete example is in examples/agents/codingagent.py.

Real-World Use

A support automation system could use PyFlue to triage incoming issues. The file-based agent pattern in examples/agents/issuetriage.py shows the workflow: a webhook triggers a session, the agent reads the issue payload, applies a triage skill, and returns a typed result. The sandbox policy controls whether the agent can write files or execute shell commands, and sessions allow the agent to resume state if the user follows up. For teams needing safe host-side Python execution, the optional monty backend (pyflue/code/monty.py) provides a sandboxed interpreter.

The Bottom Line

PyFlue is a well-structured agent harness with genuine breadth: multiple backends, sandbox providers, and deployment targets. The architecture is clean, the documentation is substantial, and the examples are practical. It is under active development, so treat it as a framework for teams who can tolerate API churn and are willing to pin versions. Teams needing a stable, battle-tested agent framework should wait for a 1.0 release; teams building prototypes or internal tools will find it immediately useful.
