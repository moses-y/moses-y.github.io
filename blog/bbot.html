The Problem

Security teams need an automated way to enumerate assets (sub‑domains, cloud buckets, code repos, etc.) across many public sources without manually stitching together dozens of scripts. Repeating this work for each engagement wastes time and often misses low‑hanging findings.

What This Does

bbot is a Python‑based reconnaissance framework that drives a large collection of modules (≈150 under bbot/modules/). Each module implements a single data source or technique (e.g., bbot/modules/dnsbrute.py, bbot/modules/githubusersearch.py, bbot/modules/bucketgoogle.py). The core orchestration lives in bbot/core/, with the event system in bbot/core/event/ and the configuration model in bbot/core/config/models.py. The CLI entry point bbot/cli.py parses command‑line arguments, loads a preset YAML (e.g., subdomain‑enum.yml shown in the README), and streams results through output plugins such as bbot/modules/output/json.py or bbot/modules/output/neo4j.py.

How To Use It

Setup

Install the stable release from PyPI pipx install bbot

Or build the official Docker image (Dockerfile present)

docker build -t bbot -f Dockerfile .

The repository also ships a Dockerfile.full that includes optional heavy dependencies (e.g., Neo4j driver).

Configuration

Global defaults are in bbot/defaults.yml. API keys for modules are added under the modules section of a preset file (see the subdomain‑enum.yml example in the README). Runtime options (DNS thread counts, resolver list, etc.) are configurable in the same preset or via CLI flags (-c key=value).

Running

Basic sub‑domain enumeration bbot -t example.com -p subdomain-enum

Use a custom preset

bbot -t example.com -c preset=custom.yml

Stream results to Neo4j

bbot -t example.com -p subdomain-enum -o neo4j

The command invokes bbot/cli.py, which loads the target (-t), preset (-p), and output modules (-o). Results are emitted as events (bbot/core/event/) and consumed by the selected output plugin.

Real‑World Use

A penetration testing pipeline can call bbot from a CI job to produce a JSON asset list:

.github/workflows/recon.yml name: Run BBOT run: | bbot -t $TARGET -p subdomain-enum -o json > assets.json name: Upload artifacts uses: actions/upload-artifact@v3 with: name: assets path: assets.json

The JSON can feed downstream tools (e.g., vulnerability scanners) or be imported into a Neo4j graph for visual correlation.

Code Health & Issues

High – Hard‑coded secrets – bbot/modules/badsecrets.py contains example API keys that should be removed or masked. Medium – Limited test coverage – Only 4 test files are present; many modules lack direct unit tests, increasing regression risk. Medium – Dependency exposure – Dockerfile.full pulls heavyweight libraries (e.g., Neo4j driver) that may not be needed for all users, inflating image size. Low – Documentation gaps – While the README covers basic usage, module‑specific configuration (e.g., required fields for bucket_google) is not fully documented. Low – CI only runs static analysis – Workflows include codeql and benchmark.yml but no automated functional test suite execution on PRs.

Overall, the repository includes a CI pipeline (.github/workflows/.yml) and a pre‑commit config, indicating some process discipline.

The Bottom Line

bbot delivers a comprehensive, extensible recon engine with a clear CLI and Docker support, making it suitable for teams that need automated asset discovery across many public sources. The codebase is reasonably organized, but the presence of hard‑coded secrets and sparse test coverage suggest a need for additional hardening before deploying in high‑risk environments. Teams comfortable adding their own tests and sanitizing configuration will find it a valuable addition to a recon workflow.

Pin third-party GitHub Actions to a commit SHAhigh7 occurrences
.github/workflows
astral-sh/setup-uv@v7, codecov/codecov-action@v7, docker/setup-buildx-action@v4, docker/login-action@v4
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Remove continue-on-error from steps that gate correctnesshigh
.github/workflows/tests.yml
line 58 on a correctness step
A failing test suite reports a green check, which is precisely the path this audit exists to close.
Fix: Delete continue-on-error, or move a genuinely advisory step into a separate non-required job.
Declare least-privilege permissions for GITHUB_TOKENmedium2 occurrences
.github/workflows/distro_tests.yml
2 workflow(s) declare no permissions, 1 of them reference secrets
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Pin the container base image by digestmedium
Dockerfile
python:3.11-slim
An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.
Fix: Use image:tag@sha256:<digest> and enable Dependabot's docker ecosystem.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
