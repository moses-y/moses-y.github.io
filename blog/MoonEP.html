Forked from MoonshotAI/MoonEP

The Problem

Expert parallelism (EP) in Mixture-of-Experts models is fundamentally unbalanced: router output skews token loads across ranks, so some ranks receive far more than S × K tokens. This drives up iteration time (the hottest rank sets the pace) and fragments GPU memory until training OOMs. Existing libraries like DeepEP v2 suffer from both problems.

What This Does

MoonEP is a communication library for EP that guarantees every rank receives exactly S × K tokens per layer, regardless of routing imbalance. It achieves this by online planning (moonep/planning.py) of a small number of redundant experts per rank, which are prefetched (moonep/prefetch.py) before expert computation. The dispatch (moonep/dispatch.py) and combine (moonep/combine.py) phases use zero-copy fused permute/unpermute kernels—tokens are written directly to expert-grouped positions on remote ranks, eliminating the comm-buffer-to-user-buffer copy that dominates epilogues in other libraries.

The weight buffer layout is a single contiguous VMM range [E+B, H, H'] (active experts plus prefetch slots), identically structured on every rank (moonep/buffer.py). Static shapes mean no per-layer host synchronization. The planning kernel runs on GPU with negligible overhead (csrc/bindings.cu).

Real-World Use

A training framework integrating MoonEP replaces its existing dispatch/combine calls with MoonEP's API. The framework provides a symmetric weight tensor per expert projection, and MoonEP returns a cuseqlens array that selects which expert rows are active. The critical path adds only a planning kernel and a weight-prefetch kernel; benchmarks (benchmarks/benchvsdeepep.py) show total dispatch time on par with DeepEP v2's dispatch alone, and combine significantly faster.

Code Health & Issues

Medium — No CI/CD pipeline: No .github/ directory or CI config found. The 11 tests (tests/) are present and structured (conftest.py, separate test files for each module), but there is no automated gate to prevent regressions. Adding GitHub Actions or similar would be straightforward. Low — Missing input validation in public APIs: moonep/api.py and moonep/dispatch.py expose functions that take raw tensors and shape parameters; no explicit shape/device checks are visible. Production use would benefit from defensive assertions, especially given the static-shape contract. Low — CUDA kernel in csrc/ has no separate test harness: bindings.cu and nvlsharedbuffer.cuh are only exercised via Python tests (teste2e.py, test_dispatch.py). No unit tests for the GPU kernels in isolation. Clean structure: Separation of concerns is good—planning, dispatch, combine, prefetch, buffer management are each in their own module. The README provides clear performance benchmarks with reproducible scripts. License (MIT) is present.

The Bottom Line

MoonEP solves a real, painful problem in large-scale MoE training with a well-engineered approach: perfect load balance via online redundant-expert planning, zero-copy communication, and static memory shapes. The code is clean and modular, with solid benchmarks. The missing CI is the main gap for production adoption. Teams training MoE models with EP should evaluate this as a drop-in replacement for existing dispatch/combine libraries—especially if router imbalance is causing OOMs or variable iteration times.
