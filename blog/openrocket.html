openrocket

Model-rocketry aerodynamics and trajectory simulation software

Forked from openrocket/openrocket

The Problem Model‑rocketry designers need a reliable way to evaluate aerodynamic performance and flight trajectories before building hardware. Manual calculations are error‑prone and cannot capture six‑degree‑of‑freedom (6‑DOF) dynamics, stability margins, or motor‑selection effects across multiple stages.

What This Does OpenRocket implements a full‑featured 6‑DOF simulator in Java. Core physics lives under core/src/main/java/info/openrocket/core/aerodynamics/, e.g.:

BarrowmanCalculator.java – computes lift/drag using the Barrowman method. LookupTableDragCalculator.java – interpolates drag from empirical tables.

Rocket definition, component hierarchy, and simulation control are in core/src/main/java/info/openrocket/core/document/ (Simulation.java, OpenRocketDocument.java).

The UI layer (core/src/main/java/info/openrocket/core/appearance/ and Swing run‑configurations in .idea/runConfigurations/) renders 2‑D/3‑D models and plots simulation results. All source files compile into a single JAR published to Maven Central (info.openrocket:core).

How To Use It Clone & build – the project uses Gradle wrappers located in core/.

git clone https://github.com/openrocket/openrocket.git cd openrocket/core ./gradlew clean build # compiles Java sources, runs the two unit tests

The top‑level build.gradle aggregates the core sub‑project, so the same command works from the repository root. Run the application – the Gradle run task launches the Swing UI.

./gradlew :core:run

The launch configuration (.idea/runConfigurations/openrocketjar.xml) shows the main class info.openrocket.swing.Startup (implicit in the Gradle application plugin). Configuration – no external secrets are required. Optional runtime settings (e.g., UI theme, default units) are read from the info/openrocket/core/appearance/AppearanceBuilder.java and persisted in the user’s home directory; no repository‑level config files are needed. Command‑line simulation – advanced users can invoke the core library directly from Java code. Example snippet (not part of the repo but demonstrative):

Simulation sim = new Simulation(); sim.setRocket(myRocket); sim.run();

The Simulation class resides in core/src/main/java/info/openrocket/core/document/Simulation.java.

Real‑World Use A hobby club integrates OpenRocket into its launch‑day workflow:

RocketDesign design = RocketFactory.createStandardRocket(); design.setMotor(new Motor("K1400", 1500)); // uses MotorDatabase classes Simulation sim = new Simulation(design); sim.run(); Chart chart = sim.getResultChart(); // uses AerodynamicCalculator output chart.saveAs("flightprofile.png");

The generated chart is then posted to the club’s website, providing members with a data‑driven safety briefing.

Code Health & Issues Low – Missing lockfile – Gradle dependencies are declared in build.gradle and core/build.gradle without a lockfile, which can lead to non‑reproducible builds. Medium – Test coverage – Only two test files exist (core/src/test/java/...). Core physics modules have limited automated verification. Low – CI configuration – GitHub Actions (.github/workflows/build.yml) builds the project on push, but does not enforce static analysis (Checkstyle/SpotBugs configs exist but are not invoked). Low – Documentation – README and ReadTheDocs provide user‑level guides; API Javadoc is generated but not bundled in the repository. Low – Dependency hygiene – No explicit version constraints for third‑party libraries (e.g., exp4j), increasing risk of upstream breaking changes.

Overall the code follows conventional Java packaging, with clear separation between physics (aerodynamics), persistence (database), and UI (appearance). The build scripts are straightforward, and the Maven Central artifact demonstrates successful release engineering.

The Bottom Line OpenRocket delivers a mature, Java‑based 6‑DOF rocket simulation engine with a usable GUI and extensible core library. Build and run steps are well defined, but the project would benefit from a dependency lockfile, expanded test suite, and tighter CI enforcement. It is suitable for hobbyists, educational programs, and small‑scale research that can accommodate a Java runtime and are comfortable with modest testing coverage.
