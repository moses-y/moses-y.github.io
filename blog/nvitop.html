The Problem

GPU‑process oversight in heterogeneous clusters is usually split between ad‑hoc nvidia-smi calls, fragmented Python wrappers, and dashboards that require separate exporters. Teams end up maintaining custom scripts just to see who is using a GPU, why utilization spikes, and how to export metrics for monitoring stacks.

What This Does

nvitop is an interactive TUI that visualises NVIDIA‑GPU processes, resource usage, and device topology in real time. It also ships nvitop‑exporter, a Prometheus‑compatible endpoint that translates the same data into metrics for Grafana/Prometheus.

Key components (from the responsibility map):

  • nvitop/api/device.py – 148 functions, 12 types; defines transmit, receive, __repr__, is_available, driver_version. Called from 13 other files; runs an external command (_parse_cuda_visible_devices via subprocess.check_output).
  • nvitop/api/process.py – 66 functions, 2 classes; provides add_quotes, command_join, auto_garbage_clean.
  • nvitop/api/collector.py – 26 functions, 4 classes; snapshot collection (take_snapshots, collect_in_background).
  • nvitop/tui/tui.py – the TUI entry; max indentation depth 6, control flow hard to follow.
  • nvitop/api/__init__.py – hub module; 17 other modules import it, making it a high‑blast‑radius point.

The exporter lives in nvitop-exporter/nvitop_exporter/ (cli.py, exporter.py, utils.py) and exposes Prometheus metrics via a simple HTTP server.

Real‑World Use

A ML ops team runs a cluster of 8 A100 nodes. They start nvitop via SSH (ssh user@node nvitop) to instantly see which PID owns each GPU, memory‑copy rates, and kernel launch queues. When a job stalls, they switch to the exporter (nvitop-exporter/cli.py) and feed the Prometheus metrics into Grafana, where they correlate GPU utilisation with training loss. The same metrics also trigger alerts if a process exceeds a configurable memory‑threshold, all without writing custom polling scripts.

The Bottom Line

nvitop delivers a capable, single‑pane TUI and exporter for GPU‑process visibility, with solid API surface and Prometheus integration. However, the codebase suffers from import cycles, oversized files, duplicated logic, and missing reproducibility guards (no lockfile, mutable Docker base, unpinned Actions). Teams that need rapid GPU utilisation insights will find immediate value, but anyone planning to extend or ship the tooling should budget time to break the import cycles, split the large API files, and add a lockfile + CI dependency scanning before production use.

Pin third-party GitHub Actions to a commit SHAhigh4 occurrences

pypa/gh-action-pypi-publish@release/v1, docker/setup-buildx-action@v4, docker/login-action@v4, docker/build-push-action@v7
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
