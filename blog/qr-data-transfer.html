The Problem

Transferring files between devices without a network connection, cable, or cloud intermediary remains impractical for most users. Existing QR-based approaches fail on files larger than a few kilobytes because static QR codes have severe capacity limits.

What This Does

QRFerry encodes a file into a live animated QR stream that a receiving phone scans with its camera. The sender and receiver run entirely in the browser—the file never touches a server. The lib/ directory contains the core pipeline: compression (compression.ts), fountain encoding via RaptorQ (qr-transfer.ts), QR rendering with WebAssembly (qr-renderer.ts), and scanning with ZXing-C++ WebAssembly (qr-scanner.ts).

The protocol uses raw byte mode QR codes with a binary header, a RaptorQ symbol, and CRC-32 per frame. Multiple transfer profiles trade speed for reliability: Turbo 15 (one V30-L code), Turbo 30, Turbo 60 (dual V30-L lanes), and a 1 Mbps lab profile (dual V40-L). The receiver can join mid-transfer, discard blurry frames, and reconstruct after collecting enough symbols.

Real-World Use

An engineer needs to move a 2 MB firmware update to an air-gapped tablet. Open the root page on a laptop, select the file, and start the QR stream. Open /scan on the tablet, point the camera at the screen, and wait for RaptorQ recovery and CRC checks to reach 100%. No USB cable, no network share, no cloud upload.

The Bottom Line

QRFerry solves a real pain point with a clever protocol and solid engineering choices (WebAssembly, RaptorQ, dual-lane QR). The codebase is well-structured and the README is unusually detailed. However, the lack of CI, license, and community validation makes it risky for production use today. Worth evaluating for internal prototypes or as a reference implementation, but not for customer-facing deployments without hardening.
