vexa

Open-source meeting transcription API for Google Meet, Microsoft Teams & Zoom. Auto-join bots, real-time WebSocket transcripts, MCP server for AI agents. Self-host or use hosted SaaS.

Forked from Vexa-ai/vexa

The Problem Enterprises that need meeting transcription and bot automation must either rely on SaaS vendors (e.g., Otter.ai, Recall.ai) or build a custom stack from scratch. SaaS solutions expose raw audio to third‑party clouds, creating data‑sovereignty concerns, and their per‑seat pricing can be prohibitive for large teams.

What This Does Vexa delivers a self‑hostable API that can (1) join Google Meet, Microsoft Teams, or Zoom calls as an automated participant, (2) capture audio, run Whisper‑based transcription in real‑time, and (3) expose the transcript via REST and WebSocket endpoints.

The implementation lives under several top‑level directories:

deploy/compose/ – a Docker‑Compose stack (docker-compose.yml) that spins up all required services (Postgres, Redis, MinIO, the various API containers, and the Next.js dashboard). deploy/lite/ – a minimal single‑container build (Dockerfile.lite) suitable for local testing; it installs Python dependencies from deploy/lite/requirements.txt and starts the process via deploy/lite/entrypoint.sh. docs/ – extensive Markdown/MDX documentation, including API reference (docs/api/.mdx) and deployment guides (docs/deployment.mdx).

Key runtime code is organized by feature (e.g., features/realtime-transcription/, features/bot-lifecycle/) and referenced from the Helm charts in deploy/helm/charts/vexa/.

How To Use It

Setup Clone the repo git clone https://github.com/Vexa-ai/vexa.git cd vexa

Copy the example env file and edit required values (DB creds, S3 bucket, JWT secret) cp deploy/env-example .env

Build and launch the full stack (requires Docker & Docker‑Compose) make up # defined in the root Makefile – runs docker-compose -f deploy/compose/docker-compose.yml up -d

If only a quick local run is needed, the lightweight image can be used: cd deploy/lite docker build -t vexa-lite -f Dockerfile.lite . docker run -p 8000:8000 --env-file ../.env vexa-lite

Configuration Environment variables – listed in deploy/env-example (e.g., POSTGRESURL, REDISURL, MINIOENDPOINT, JWTSECRET). Helm values – for Kubernetes deployments, edit deploy/helm/charts/vexa/values.yaml (image tags, replica counts, resource limits).

Running the API The API gateway is exposed on port 8000 (default) and routes to sub‑services (/api/v1/meeting, /api/v1/transcript). Real‑time transcript streams are available via WebSocket at ws://<host>:8000/ws/transcript/<meetingid>. The Next.js dashboard runs on port 3000 (defined in the dashboard-deployment.yaml Helm template).

All services are orchestrated by the Compose file; stopping the stack is make down (root Makefile).

Real‑World Use A SaaS product that records client calls can embed Vexa as follows:

import requests, websockets, json, asyncio

Obtain a scoped token from the auth endpoint token = requests.post( "https://my‑vexa‑host/api/v1/auth", json={"apikey": "MYPRODUCTKEY"} ).json()["accesstoken"]

Command the bot to join a Zoom meeting resp = requests.post( "https://my‑vexa‑host/api/v1/meeting/bot", headers={"Authorization": f"Bearer {token}"}, json={"platform": "zoom", "meetingid": "123‑456‑789"} )

Consume the live transcript async def listen(): async with websockets.connect( f"wss://my‑vexa‑host/ws/transcript/{resp.json()['meetingid']}", extraheaders={"Authorization": f"Bearer {token}"} ) as ws: async for msg in ws: print(json.loads(msg)["text"])

asyncio.run(listen())

The transcript can then be stored, indexed, or fed to downstream LLM agents via the MCP server (/api/v1/mcp).

Code Health & Issues

Low – Missing pip lockfile – deploy/lite/requirements.txt has no corresponding requirements.lock; builds may yield inconsistent dependency versions. Low – Sparse test coverage – Only 8 test files are present; many feature directories lack unit tests, increasing risk of regressions. Low – CI only runs lint/packaging – GitHub Actions workflows (test-.yml) exercise API containers but do not run integration tests against real meeting platforms. Low – Secret handling – No .env.example for the dashboard UI; required secrets are documented only in deploy/env-example, which could be overlooked. Low – Documentation depth – Docs are extensive, but the quick‑start section in README.md does not list exact make targets; users must infer from the Makefile.

No obvious security red flags (no hard‑coded credentials, Apache‑2.0 license present).

The Bottom Line Vexa provides a complete, open‑source alternative to commercial meeting‑bot and transcription services, with a clear Docker‑Compose deployment path and detailed documentation. The main drawbacks are the lack of a Python lockfile and limited automated test coverage, which may require extra diligence for production use. It is well‑suited for teams that need full data control and are comfortable managing containerized services.
