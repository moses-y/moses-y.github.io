The Problem

Space‑grade software is notoriously opaque, making it difficult for security teams to practice realistic exploitation without costly flight hardware. Teams need a low‑cost, deliberately vulnerable platform that mirrors satellite subsystems and communication stacks so that training, research, and tooling can be validated safely on‑premise.

What This Does

FlatSat delivers a complete hardware‑plus‑software stack that emulates a satellite on a Raspberry Pi RP2040 board. The firmware lives in Firmware/ (e.g., firmware.ino, securelink.cpp, spacecan.cpp) and is built with PlatformIO (Firmware/platformio.ini). It intentionally contains exploitable bugs such as unchecked command parsing and weak authentication, providing concrete attack surfaces.

Eight attack modules are provided under Attacks/, each with an RF and USB variant (e.g., Attacks/03commandinjection/03commandinjectionrf.py). Helper libraries in Attacks/lib/ (e.g., flatsatusb.py, pwnsatlorarx.py) abstract the LoRa and USB interfaces, letting users focus on the exploit logic rather than low‑level radio handling.

The hardware design is fully open in the KiCad files under Hardware/flat-sat/ and the legacy backup directory, exposing schematics, part libraries, and 3‑D models for custom modifications or board‑level debugging.

How To Use It

Setup

Clone the repository

git clone https://github.com/Pwnsat/FlatSat.git cd FlatSat

Install PlatformIO (requires Python)

pip install platformio

Build and flash the firmware to the RP2040

platformio run -t upload # uses Firmware/platformio.ini

Python attack scripts require a recent Python 3 interpreter and the GNU Radio runtime. The repository includes a guard module Attacks/lib/requiregnuradio.py that aborts if the dependency is missing; install it via the system package manager (e.g., apt install gnuradio on Debian/Ubuntu).

Example: run the RF recon script

python Attacks/00reconapidenum/00reconapidenumrf.py

All attack entry points are individual .py files; no additional command‑line wrappers are provided.

Configuration

Firmware build options (e.g., LoRa frequency) are defined in Firmware/platformio.ini. Attack scripts expect the radio hardware to be reachable via the USB or HackRF interface; no explicit config files are present, so users must edit the scripts or set environment variables manually if they diverge from defaults.

Running It

Flash the UF2 image (Firmware/build/flatsat-firmware.uf2) onto the RP2040. Power the board and verify UART output (default baud 115200). Execute a chosen attack script; the script will open the appropriate interface (USB or SDR) and interact with the board automatically.

Real‑World Use

A penetration‑testing team can integrate FlatSat into a CI pipeline that validates a new radio‑hardening patch. After flashing the patched firmware, the team runs python Attacks/06replay/06replayusb.py to confirm that replay attacks no longer succeed. The script returns a pass/fail status that can be consumed by a Jenkins job (though the repo lacks built‑in CI support).

Minimal example of automated validation

import subprocess, sys

result = subprocess.run( ["python", "Attacks/06replay/06replayusb.py"], captureoutput=True, text=True )

if "Replay prevented" in result.stdout: sys.exit(0) # success else: sys.exit(1) # failure

Code Health & Issues

Med – No automated tests – No tests/ directory; all code paths are unverified by unit or integration tests. Med – No CI pipeline – Repository lacks .github/workflows/, Makefile, or other CI configuration; gate checks are absent. Low – License fragmentation – Separate LICENSEFIRMWARE.md and LICENSEHARDWARE.md exist, but no top‑level SPDX identifier; downstream users may need clarification. Low – Sparse input validation – Attack scripts directly feed crafted packets to the firmware without sanitising user‑supplied arguments; this mirrors the intended vulnerability but also poses a risk when reused as a library. Low – Dependency opacity – Required Python packages are not enumerated in a requirements.txt or pyproject.toml; developers must infer them from Attacks/lib/require_gnuradio.py.

No obvious secret keys or hard‑coded credentials are present in the visible source.

The Bottom Line

FlatSat offers a complete, open‑source satellite emulator with deliberately vulnerable firmware and a ready‑made exploit suite, making it valuable for hands‑on aerospace security training and proof‑of‑concept research. The primary drawbacks are the lack of automated testing, CI, and explicit dependency documentation, which means teams will need to invest effort in establishing their own quality gates before adopting it in production‑grade workflows.
