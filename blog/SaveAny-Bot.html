The Problem

Telegram users often need to archive media or documents, but the platform blocks “restrict saving” content and limits where files can be stored. Existing solutions require manual downloads or rely on unofficial APIs. A bot that can accept any Telegram file or link, bypass restrictions, download it, and push it to a chosen backend would streamline collaboration and backup workflows.

What This Does

The repository implements SaveAny‑Bot, a Go‑based Telegram bot with a web UI.

  • cmd/root.go launches the CLI, wiring commands that start the HTTP server (api/server.go) and the Telegram bot (client/bot/bot.go).
  • Task creation lives in api/factory.go where helper functions like CreateTask and registerAndEnqueueTask instantiate concrete task types (core/tasks/...).
  • Storage adapters are defined under config/storage/ (e.g., alist.go, s3.go, webdav.go) and used by the workers in core/tasks/....
  • The UI is served from web/ and built with pnpm, while Dockerfiles and docker-compose.yml enable containerized deployment.

How It Is Wired

Execution starts in cmd/root.go: the main function calls Execute(). Execute() registers sub‑commands (e.g., run, watch, upload) which delegate to cmd/run.go, cmd/watch/cmd.go, etc. During a run, cmd/run.go calls initAll() → cleanCache() → api/server.go.Start(). api/server.go creates a Gin router that routes /webhook to api/telegram.go, which uses common/tdler/dler.go to receive updates. A media message triggers listenMediaMessageEvent → Execute → processBatch (see traced path: init -> Register -> listenMediaMessageEvent -> Execute -> processBatch). processBatch creates a task via api/factory.go, persisting its record with GORM (config/db.go). The worker pool in core/tasks/... pulls tasks from the DB, downloads content (e.g., via pkg/aria2/client.go or cmd/ytdlp.go), and pushes it to the chosen storage backend. Key high‑impact functions:

  • FromContext (client/bot/handlers/utils/dirutil/context.go) – 56 callers, central to context propagation.
  • T (common/i18n/i18n.go) – 37 callers, used for all user‑facing strings.
  • NewUploader (cmd/watch/uploader.go) – 28 callers, orchestrates file uploads.

The call graph shows FromContext as the most referenced helper, while TaskFactory and CreateTask are the main entry points for task creation. No circular dependencies are detected, but duplicated logic appears in api/tgfiles.go, common/utils/tgutil/resolve.go, and various handler files.

How To Use It

Setup

# Clone the repo
git clone https://github.com/moses-y/SaveAny-Bot
cd SaveAny-Bot

# Build the Docker image (or use the published one)
docker build -t saveany-bot .

# Or run locally with Go
go build -o saveany-bot ./cmd/run.go

Configuration Environment variables are read by config/config.go. The README shows the key one:

export SAVEANY_LISTEN=0.0.0.0:28080

Other variables such as SAVEANY_DATA_DIR, SAVEANY_DOWNLOADS_DIR, and SAVEANY_CACHE_DIR are mounted via Docker volumes.

Running

# Docker
docker run -d --name saveany-bot \
  -p 28080:28080 \
  -e SAVEANY_LISTEN=0.0.0.0:28080 \
  -v ./data:/app/data \
  -v ./downloads:/app/downloads \
  -v ./cache:/app/cache \
  ghcr.io/krau/saveany-bot:v1-beta

# Binary
./saveany-bot --listen 0.0.0.0:28080

The container logs the UI URL and admin password.

Real‑World Use

A team shares a Telegram channel where members post large datasets. By adding the bot to the channel and configuring a WebDAV backend in config/storage/webdav.go, every media message is automatically saved to a shared drive, indexed by the bot’s UI. The bot also parses URLs from messages, downloading content via yt‑dlp (cmd/ytdlp.go) for sites that block direct downloads.

The Bottom Line

SaveAny‑Bot delivers a feature‑rich Telegram media archiving solution with a clean CLI and web UI. The codebase is well‑structured around tasks and storage adapters, but duplicated logic and deep nesting in some handlers raise maintainability concerns. For teams needing automated media backup across multiple backends, this is a solid foundation, provided the highlighted security and CI issues are addressed.

Pin third-party GitHub Actions to a commit SHAhigh6 occurrences
.github/workflows
docker/setup-buildx-action@v4, docker/login-action@v4, docker/build-push-action@v7, softprops/action-gh-release@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.

The pinned version is the one that installs, so a published advisory against it describes this deployment rather than a hypothetical one, and the advisory is also a public description of how to exploit it.
Fix: Upgrade to the fixed version named in the advisory, then commit the lockfile.
