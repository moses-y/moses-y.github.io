The Problem

Developers who use coding agents often spend more time supervising the agents than delivering value. Missing isolation, unclear hand‑off points, and ad‑hoc tooling make it hard to treat “work items” as autonomous, reproducible runs. The result is fragile pipelines and constant manual triage.

What This Does

Symphony provides a reference implementation (the elixir sub‑project) that treats each work item as a self‑contained execution. The core runtime lives in elixir/lib/symphony_elixir/*.ex – e.g. orchestrator.ex decides which agent to launch, app_server.ex and workspace.ex manage the isolated environment, and cli.ex exposes a command‑line entry point. Docker support for end‑to‑end tests is in elixir/test/support/live_e2e_docker/. The repository also ships a small .codex helper library used by the original OpenAI spec.

How It Is Wired

  • Entry point – elixir/lib/symphony_elixir/cli.ex implements main/1. The Mix task mix symphony (defined in mix.exs) invokes CLI.run/1.
  • Orchestration – CLI.run/1 calls SymphonyElixir.Orchestrator.start/0. The orchestrator loads configuration from elixir/lib/symphony_elixir/config.ex (which reads config/config.exs) and creates a Workspace (workspace.ex).
  • Workspace – Workspace provisions an isolated directory, writes a temporary spec, and hands it to AppServer.start/1 (app_server.ex). The app server spawns an Elixir process that runs the agent code (agent_runner.ex) and streams logs via LogFile.ex.
  • Agent execution – AgentRunner selects a tool (e.g. Linear adapters in linear/) and runs the work payload. Results are posted back through HttpServer.ex and recorded in Tracker (tracker.ex / tracker/memory.ex).
  • Status reporting – StatusDashboard.ex aggregates live metrics; tests in core_test.exs snapshot its output. The LiveView dashboard_live.ex renders the dashboard in the Phoenix web UI.

All side‑effects (filesystem writes, network calls) are confined to the Workspace directory and the HTTP server port configured in config.ex. No circular dependencies appear in the import graph (1 internal module, 0 import edges). The biggest blast‑radius modules are orchestrator.ex, status_dashboard.ex, and the core test suite (core_test.exs), each exceeding 1 300 lines.

How To Use It

# Clone the repo
git clone https://github.com/moses-y/symphony
cd symphony/elixir

# Install deps (Mix)
mix deps.get

# Run unit tests
mix test

# Start the server (example)
mix run --no-halt   # invokes CLI → Orchestrator → AppServer

The Docker‑based live‑E2E tests can be exercised with the provided Dockerfile:

cd elixir/test/support/live_e2e_docker
docker compose up --build

Configuration lives in elixir/config/config.exs; adjust the :http_port or workspace root as needed before running.

Real‑World Use

A product team that tracks tickets in Linear can point Symphony at a board. When a new ticket appears, the orchestrator creates a workspace, runs the agent (via AgentRunner), and posts a PR with CI status. The team reviews the PR and merges; Symphony then archives the workspace automatically. The whole flow requires only the CLI start command and a Linear API token placed in config.exs.

The Bottom Line

Symphony offers a concrete, Docker‑enabled Elixir reference for turning work items into isolated runs, with a clear call chain from CLI to workspace to agent. The codebase is functional but suffers from duplicated logic, oversized modules, and several CI‑security hygiene gaps that should be addressed before production use. It is best suited for teams comfortable with Elixir/Phoenix who need a sandboxed agent execution framework and are prepared to refactor the identified hotspots.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
jdx/mise-action@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.

.github/workflows/make-all.yml
2 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.

An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.
Fix: Use image:tag@sha256:<digest> and enable Dependabot's docker ecosystem.

One repository here carries twenty blobs over 5MB including a 10.9MB spreadsheet, so every clone and every CI checkout pays for data nobody diffs.

Add a non-root USER to the imagemedium
elixir/test/support/live_e2e_docker/Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
