The Problem

Provisioning and maintaining large numbers of LXC containers on Proxmox VE is error‑prone when done manually. Teams need a repeatable, version‑controlled workflow that can bootstrap the control plane itself and keep the desired state in sync with Git.

What This Does

Proxmox‑GitOps packages a self‑contained GitOps pipeline that:

Stores the entire container topology in a monorepo (see config/, base/, libs/). The repository is the single source of truth for both infrastructure code and container images. Boots the pipeline inside a Docker container (local/Dockerfile) so the same environment can be used for local testing and CI (.github/workflows/build.yml). Drives provisioning on Proxmox via Ansible (base/roles/) and Chef/Cinc (config/recipes/.rb). For example, config/recipes/deploy.rb orchestrates the end‑to‑end flow, while base/roles/container/tasks/create.yml creates the LXC container.

How To Use It

Setup

Build the local execution image docker build -f local/Dockerfile -t proxmox-gitops:latest .

(Optional) Run the CI build locally docker run --rm -v "$(pwd)":/repo proxmox-gitops:latest /repo/local/run.sh

The Dockerfile pulls a Ruby‑based image, installs required gems (see Gemfile.lock if present) and copies the repository into /repo.

Configuration

Environment – The container expects the variables defined in container.env (root) and local/config.json. Typical entries include PROXMOXAPIURL, PROXMOXUSER, PROXMOXPASSWORD, and a Git token for submodule access. Repository layout – Place any additional container definitions under libs/<name>/ following the existing pattern (attributes/default.rb, recipes/default.rb, templates/.erb). Pipeline template – Adjust the default CI pipeline in config/templates/taskpipeline.yml.erb if custom stages are required.

Running it

The primary entry point is the shell script local/run.sh. It loads the environment file, initializes the Git submodule tree (config/recipes/repo/init.rb), and invokes the Chef runner (config/recipes/runner.rb). Example invocation:

docker run --rm \ -v "$(pwd)":/repo \ -e PROXMOXAPIURL=https://pve.example.com:8006/api2/json \ -e PROXMOXUSER=root@pam \ -e PROXMOXPASSWORD=secret \ proxmox-gitops:latest /repo/local/run.sh deploy

The deploy argument maps to config/recipes/deploy.rb, which triggers the full provisioning sequence.

Real‑World Use

A DevOps team can store a complete LXC stack (web, DB, monitoring) in libs/web/, libs/db/, libs/monitor/. After committing changes, the CI pipeline (.github/workflows/build.yml) builds the Docker image, runs run.sh deploy, and the updated containers appear on the target Proxmox cluster automatically—no manual SSH or pct commands needed.

Example CI step (from .github/workflows/build.yml)

name: Deploy to Proxmox run: | docker run --rm -v ${{ github.workspace }}:/repo \ -e PROXMOXAPIURL=${{ secrets.PVEURL }} \ -e PROXMOXUSER=${{ secrets.PVEUSER }} \ -e PROXMOXPASSWORD=${{ secrets.PVEPASS }} \ proxmox-gitops:latest /repo/local/run.sh deploy

Code Health & Issues

Med – No automated tests – The repository contains zero _spec.rb or similar test files; code paths in config/recipes/*.rb are unverified. Med – Limited CI coverage – GitHub Actions only build the Docker image; they do not execute the provisioning steps, leaving runtime failures undetected. Low – Secret exposure risk – Sample environment files (container.env) are committed without redaction; real credentials must be supplied via CI secrets, but the repo lacks documentation of required secret names. Low – Inconsistent documentation – README provides high‑level concepts but omits a concrete “quick start” command; the only usage hint is the local/run.sh script. Low – Mixed tooling – Uses both Chef (Cinc) and Ansible; the hand‑off between them is not clearly delineated, which could cause maintenance friction. Low – No explicit dependency lock – No Gemfile.lock observed; gem versions may drift between builds.

The Bottom Line

Proxmox‑GitOps delivers a coherent, container‑based GitOps pipeline for LXC provisioning on Proxmox, with a clear repo layout and Docker‑first workflow. However, the lack of test coverage, incomplete CI validation, and sparse onboarding docs make it a better fit for teams comfortable with Ruby/Chef and willing to invest in additional testing and documentation before production use.
