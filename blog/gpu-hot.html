gpu hot

🔥 Real-time NVIDIA GPU dashboard

Forked from psalias2006/gpu-hot

The Problem Operators of compute nodes need live visibility into GPU utilization, temperature, power draw, and per‑process usage. Existing tools (nvidia‑smi, proprietary dashboards) either require manual polling, lack a web UI, or cannot aggregate multiple hosts without custom glue.

What This Does gpu-hot runs a lightweight web server that polls the NVIDIA Management Library (NVML) or falls back to nvidia‑smi and pushes JSON snapshots over a Socket.IO connection to a React front‑end. The back‑end lives in app.py (FastAPI + Socket.IO) and delegates GPU collection to core/monitor.py, which uses the NVML wrapper in core/metrics/collector.py. Multi‑node aggregation is handled by core/hub.py and its WebSocket handlers in core/hubhandlers.py. The UI assets (static/js/.js, templates/index.html) render real‑time charts and a process table.

How To Use It

Setup – Build and run the provided Docker image (the repo supplies a Dockerfile and docker‑compose.yml). git clone https://github.com/psalias2006/gpu-hot cd gpu-hot docker compose up --build # builds the image defined in Dockerfile

For a single‑machine deployment, the README’s Docker command is also valid: docker run -d --gpus all -p 1312:1312 ghcr.io/psalias2006/gpu-hot:latest

Configuration – All runtime knobs are environment variables read in core/config.py. Typical settings:

VariablePurposeDefault
NVIDIAVISIBLEDEVICESComma‑list of GPUs to exposeall
NVIDIASMIForce nvidia‑smi fallback (older cards)false
GPUHOTMODEhub to run aggregation nodesingle
NODENAMEHuman‑readable identifier (fallback: hostname)hostname
NODEURLSComma‑separated URLs of peer nodes (required for hub mode)–
UPDATEINTERVALNVML poll interval (seconds)0.5
NVIDIASMIINTERVALFallback poll interval (seconds)2.0

Set them when launching the container, e.g.: docker run -d --gpus all -p 1312:1312 \ -e GPUHOTMODE=hub \ -e NODENAME=gpu‑server-1 \ -e NODEURLS=http://server1:1312,http://server2:1312 \ ghcr.io/psalias2006/gpu-hot:latest

Running – The container starts uvicorn app:app (see app.py). For local development without Docker:

python -m venv .venv && source .venv/bin/activate pip install -r requirements.txt uvicorn app:app --host 0.0.0.0 --port 1312

Open http://localhost:1312 to view the dashboard.

Real‑World Use A research cluster can deploy one hub container on a non‑GPU node and a “worker” container on each GPU server. The hub aggregates per‑node streams and presents a single pane of glass. Example orchestration (Kubernetes) would mount the same image, set GPUHOTMODE=hub on the hub pod, and GPUHOTMODE=single on workers, relying on the NODEURLS list for discovery.

Code Health & Issues Low – Missing lockfile – requirements.txt is present but no requirements.lock or pipfile.lock; reproducible builds depend on exact package versions. Low – Docker build cache – Dockerfile does not pin base image tags (uses python:3.10-slim implicitly), potentially pulling newer layers unintentionally. Low – Limited CI coverage – GitHub Actions workflow (.github/workflows/publish.yml) builds and pushes the image but does not run the unit test suite; test failures could go unnoticed. Low – No secret management – Environment variables are injected directly; no guidance for handling credentials if future extensions need them. Low – Minimal type safety – Python code lacks type hints; static analysis tools would be less effective. Low – Front‑end test scope – Front‑end tests exist (tests/frontend/.test.js) but no linting or coverage enforcement is configured.

No critical bugs are evident; the repository includes 30 test files covering backend units (tests/unit/*.py) and front‑end components, and the Docker images run successfully in the provided examples.

The Bottom Line gpu-hot delivers a functional, containerized real‑time GPU dashboard with multi‑node aggregation, backed by a modest test suite. It is ready for small‑to‑medium clusters where quick visibility outweighs the need for hardened CI pipelines or pinned dependencies. Teams should add a lockfile, tighten CI to include tests, and consider adding type hints before adopting it for production‑critical monitoring.
