CyberStrikeAI

CyberStrikeAI is an AI-native security testing platform built in Go. It integrates 100+ security tools, an intelligent orchestration engine, role-based testing with predefined security roles, a skills system with specialized testing skills, and comprehensive lifecycle management capabilities.

Forked from Ed1s0nZ/CyberStrikeAI

The Problem Security testing teams spend excessive time stitching together disparate tools, managing manual orchestration, and tracking results across ad‑hoc scripts. The lack of a unified, auditable workflow hampers repeatability and collaboration, especially when multiple analysts need role‑based access to the same engagement.

What This Does CyberStrikeAI delivers an end‑to‑end testing platform written in Go. The core orchestration lives in internal/agent/ and internal/handler/, where agents represent individual security tools (e.g., agents/penetration.md, agents/vulnerability-triage.md). The server entry point cmd/server/main.go starts a REST‑ful web console and a lightweight C2 framework (internal/c2/), exposing listeners, encrypted payloads, and task queues. Role‑based permissions, skill definitions, and knowledge‑base indexing are implemented under internal/knowledge/ and internal/handler/role.go, enabling AI‑driven decision making (internal/app/visiontools.go) and reproducible attack‑chain generation (internal/attackchain/builder.go).

How To Use It

Setup Install Go (>=1.22) then fetch dependencies go mod tidy

Build the server binary go build -o cyberstrike-server ./cmd/server

Build the MCP stdio client (optional) go build -o mcp-stdio ./cmd/mcp-stdio

Configuration Edit config.yaml (present at the repo root) to set server ports, TLS certificates, and AI model endpoints. The file is parsed by internal/config/config.go. Example keys include server.port, tls.certpath, and ai.provider. No environment‑variable overrides are defined in the code base.

Running Start the web console and C2 services ./cyberstrike-server -config ./config.yaml

The server listens on the port defined in config.yaml and serves the UI assets bundled in images/. For command‑line interaction use the MCP client:

./mcp-stdio -mode stdio # talks to the running server via the native MCP protocol

The repository also contains test harnesses (cmd/test-config/main.go, cmd/test-external-mcp/main.go) that can be executed to validate configuration and MCP connectivity.

Real‑World Use A red‑team lead can create a new engagement via the UI, assign the “Penetration” role to an analyst, and invoke an AI‑driven attack chain:

// Pseudo‑code using internal packages engage := handler.NewProject("Acme Corp") engage.AddRole("Penetration", handler.RolePenTest) engage.Start()

The platform automatically runs the selected security tools, records each step in the audit log (internal/audit/), and indexes findings into the SQLite knowledge base (internal/knowledge/einosqliteindexer.go). Results are viewable in the dashboard (images/dashboard.png) and can be exported via handler/auditexportcsv.go.

Code Health & Issues Med – Missing CI/CD – No .github/workflows, Makefile, or other pipeline files; automated builds/tests are not enforced. Low – Limited documentation for env/config – README.md describes UI screenshots but does not list required config keys; developers must read internal/config/.go to infer settings. Med – Potential race conditions – C2 manager (internal/c2/manager.go) spawns goroutine listeners without explicit synchronization on shared maps; tests exist (managerstarttest.go) but coverage of concurrent paths is unclear. Low – License present but empty – LICENSE file exists but contains no SPDX identifier; may cause downstream compliance questions. Low – Test coverage – 29 test files cover many packages (_test.go), indicating reasonable unit testing, though integration tests for the full server flow are absent.

Overall the code follows Go idioms, uses modules (go.mod), and separates concerns into packages (agent, handler, c2, knowledge). No obvious secret leakage or hard‑coded credentials were found.

The Bottom Line CyberStrikeAI offers a solid, Go‑native framework for orchestrating AI‑augmented security testing, with a built‑in C2 and role‑based UI. It is best suited for teams that can invest in configuring config.yaml and adding their own CI pipeline. The primary gaps are automated testing pipelines and clearer configuration docs; otherwise the codebase is well‑structured and ready for internal adoption.
