MemMachine

Abstract

Universal memory layer for AI Agents. It provides scalable, extensible, and interoperable memory storage and retrieval to streamline AI agent state management for next-generation autonomous systems.

The Problem

Stateless LLM‑driven agents lose context after each request, forcing developers to re‑implement ad‑hoc persistence layers. The result is duplicated code, fragile serialisation, and limited ability to build truly personalised assistants.

What This Does

MemMachine delivers a reusable memory service that stores three tiers of data – working, episodic (graph‑based), and profile (SQL) – and exposes them via a RESTful MCP server and language‑specific client libraries. The core server lives under packages/server/ (e.g., memmachine_server/episodic_memory/ and memmachine_server/common/embedder/). Client SDKs are in packages/client/, with the Python entry point memmachine_client/client.py. Example applications (e.g., examples/simple_chatbot/app.py) show a five‑line integration pattern that creates a MemMachineClient, obtains a project, and calls memory.add() / memory.search().

Integrations for LangChain, CrewAI, LlamaIndex, etc., are under integrations/ and each provides a thin wrapper that imports the client and registers a memory backend.

How It Is Wired

Execution starts at the chosen entry point, for instance examples/simple_chatbot/app.py:

  1. app.py creates a MemMachineClient (class defined in packages/client/src/memmachine_client/client.py).
  2. The client reads configuration from packages/client/src/memmachine_client/config.py and builds a Project object (packages/client/src/memmachine_client/project.py).
  3. Calling project.memory(...) returns a Memory instance (packages/client/src/memmachine_client/memory.py).
  4. Memory.add() packages the payload and issues an HTTP POST to the server (memmachine_server/episodic_memory/service_locator.py routes the request).
  5. The server’s service locator forwards to the appropriate service (memmachine_server/episodic_memory/long_term_memory/long_term_memory.py) which persists data via the embedder (memmachine_server/common/embedder/embedder.py) and the Neo4j driver (configured in deployments/helm/templates/neo4j-deployment.yaml).

The most connected module is packages/server/src/memmachine_server/common/reranker/reranker (imported by eight other modules). The client side shows a small cycle among client.py, memory.py, and config.py (four modules in a circular import) that inflates the blast radius for any change to shared types. The longest nesting depth reaches eight levels in long_term_memory.py, making the control flow hard to follow.

All network I/O passes through the thin HTTP client in client.py; the server’s public API is defined in packages/server/src/memmachine_server/api/. No file currently maps a direct file‑system write outside the database layers, so the persistence side‑effects are confined to the Neo4j and PostgreSQL Helm charts (deployments/helm/templates/*.yaml).

How To Use It

# Clone the repo
git clone https://github.com/moses-y/MemMachine
cd MemMachine

# Build the server container (Dockerfile at repo root)
docker build -t memmachine/server:dev .

# Start dependencies (Neo4j, PostgreSQL) and the server
docker-compose up -d   # uses docker-compose.yml

# Install the Python client in a virtualenv
python -m venv .venv
source .venv/bin/activate
pip install -r examples/simple_chatbot/requirements.txt

Configuration files:

  • deployments/helm/values.yaml – overrides for Neo4j/Postgres credentials.
  • .env.example in integrations/dify/plugin/ – shows required env vars for that plugin.

Run the demo chatbot:

python examples/simple_chatbot/app.py

The script prints a prompt, stores user utterances via the client, and retrieves them on subsequent turns.

Real‑World Use

A SaaS product that offers travel planning can embed memmachine_client in its backend service. Each user session creates a Memory tied to a user_id. The episodic graph records prior itinerary discussions, while profile memory keeps static preferences (seat type, airline loyalty). When the user returns weeks later, a single memory.search("flight preferences") call restores context without rebuilding a custom DB layer.

The Bottom Line

MemMachine offers a coherent, multi‑tier memory service with ready‑made client SDKs and a breadth of integrations. The architecture is functional but hampered by deep nesting, import cycles, and duplicated logic that raise maintenance costs. Teams that need a plug‑and‑play memory layer and can allocate effort to refactor the client/server cores will find it valuable; projects with strict code‑quality mandates should address the highlighted health issues first.

Pin third-party GitHub Actions to a commit SHAhigh9 occurrences
.github/workflows
docker/setup-qemu-action@v3, docker/setup-buildx-action@v3, docker/login-action@v3, docker/metadata-action@v5
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Install from the lockfile in CImedium
.github/workflows
npm install with a committed package-lock.json
A fresh resolution in CI means the tested dependency set is not the locked one, so the failure only appears after merge.
Fix: Use npm ci, yarn install --immutable, or pnpm install --frozen-lockfile.

The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.

Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
