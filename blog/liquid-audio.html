The Problem

Real-time speech-to-speech AI requires a model that generates audio and text tokens with low latency, typically on resource-constrained devices. Most systems either stream text or audio separately, or rely on large backbones that cannot run interactively. Liquid Audio targets this gap with a lightweight end-to-end audio foundation model that interleaves text and audio token generation.

What This Does

Liquid Audio is a speech-to-speech model built on the LFM2 backbone. It supports two generation modes: generate_interleaved (fixed interleaved text/audio token pattern, minimal time-to-first-audio) and generate_sequential (model decides modality switches via special tokens, suited for ASR/TTS). The codebase is a PyTorch implementation with a Moshi-style architecture: streaming convolution modules, a transformer backbone, residual vector quantization for audio codecs, and conditioners for text/audio inputs.

The repo includes a server (src/liquid_audio/moshi/server.py) with a client (client.py), a Gradio demo (client_gradio.py), and inference scripts (run_inference.py, run_tts.py).

How To Use It

Setup: Install via pip as documented in the README:

pip install liquid-audio
pip install "liquid-audio [demo]" # optional, demo dependencies
pip install flash-attn --no-build-isolation  # optional, flash attention 2

Running it: Launch the Gradio demo with liquid-audio-demo. For programmatic use, the README documents LFM2AudioModel.generate_interleaved and generate_sequential, plus LFM2AudioProcessor for token/data conversion. The server entry point is src/liquid_audio/moshi/server.py.

Real-World Use

A customer-support voice agent: the model receives a user's spoken query, the processor converts the waveform to log-mel features, generate_interleaved streams back text-then-audio responses with sub-second latency, and the detokenizer (detokenizer.py) converts audio tokens back to a waveform. The ChatState helper manages multi-turn context.

The Bottom Line

A credible, working speech-to-speech implementation with a clean streaming architecture and a real server/client split. The code quality issues are maintenance concerns, not blockers. Use it if you need a reference implementation for low-latency audio generation or want to build on the LFM2 backbone; the duplicated conformer code and thin test suite mean you should budget for refactoring before treating it as production infrastructure.
