codeburn

Free, local tool to track AI coding token usage and cost across 37 tools and agents (Claude Code, Cursor, Codex, Gemini and more), by model, project, and task. npx codeburn

Forked from getagentseal/codeburn

The Problem Developers using AI‑assisted coding tools rarely see how many tokens each model consumes or the resulting cost. Billing dashboards aggregate usage at the account level, making it hard to attribute spend to specific projects, languages, or agents. This opacity can lead to unexpected charges and difficulty budgeting for large codebases or CI pipelines.

What This Does codeburn is a local Electron‑based desktop app that intercepts token‑count metadata from 37 supported AI coding agents (Claude, Cursor, Codex, Gemini, etc.) and aggregates the data by model, project, and task. The UI lives under app/renderer/ (e.g., app/renderer/App.tsx) while the core telemetry logic lives in app/electron/quota/ (files such as claude.ts, codex.ts, and the shared index.ts).

The CLI wrapper in app/electron/cli.ts enables a headless invocation (npx codeburn) that launches the Electron process without the menubar UI. Build configuration is handled by Vite (app/vite.config.ts) and TypeScript settings (app/tsconfig.json, app/tsconfig.electron.json).

How To Use It Setup git clone https://github.com/getagentseal/codeburn.git cd codeburn/app npm ci # installs exact versions from package‑lock.json Configuration The app expects API keys for each provider to be present as environment variables. The naming convention follows the provider’s official SDK (e.g., ANTHROPICAPIKEY, OPENAIAPIKEY). These are read in the quota modules (app/electron/quota/.ts). No sample .env file is shipped, so create one manually or export the variables in your shell before launching. Running the UI # Start the full desktop app (menubar + renderer) npm run dev # defined in app/package.json scripts → Vite + Electron

# Or run the CLI only (no UI) npx codeburn # invokes app/electron/cli.ts

The main Electron process is defined in app/electron/main.ts; the renderer entry point is app/renderer/main.tsx. Packaging CI workflows (.github/workflows/.yml) produce platform‑specific bundles (DMG, AppImage, .deb, .rpm). To build locally, run the stage-cli.mjs script invoked by the build workflow, which uses electron-builder under the hood.

Real‑World Use A CI job that runs npx codeburn before each test suite can record token usage per test run and push a JSON summary to a team dashboard. Example snippet: name: Record AI usage run: | export OPENAIAPIKEY=${{ secrets.OPENAIAPIKEY }} npx codeburn > usage.json curl -X POST -H "Content-Type: application/json" \ -d @usage.json https://metrics.myteam.com/ai-usage

The usage.json file is generated by the telemetry module app/electron/telemetry.ts.

Code Health & Issues Low – Missing provider config docs – No .env.example or README section describing required env vars. Users must infer names from source (app/electron/quota/*.ts). Medium – Limited error handling in quota modules – API failures are logged but not surfaced to the UI; could cause silent loss of usage data (app/electron/quota/security.ts). Low – No type‑guard for external responses – Quota parsers assume fields (totalTokens, cost) exist; malformed responses could crash the renderer. Low – Tests are present but coverage unknown – 43 test files exist, but no coverage badge; risk of untested edge cases in newer provider integrations. Low – CI is configured – Multiple GitHub Actions run lint, build, and tests; license (LICENSE) and lockfile are present, indicating good SDLC hygiene.

Overall the repository shows a solid structure: separate Electron main, preload, and renderer layers; clear TypeScript typings (app/electron/quota/types.ts); and a consistent test suite.

The Bottom Line codeburn delivers a practical, local way to audit AI coding spend across many providers, with a usable desktop UI and a CLI for automation. It’s production‑ready for solo developers or small teams that can manage the required API keys manually. The main gaps are sparse documentation of environment configuration and modest robustness around API error handling; addressing those would make the tool safer for larger CI/CD deployments.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
softprops/action-gh-release@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Make CI invoke the test suite it hashigh256 occurrences
.github/workflows
256 test files, no test command in the 4 workflows read
A green check that never executed an assertion is worse than no check, because reviewers trust it.
Fix: Add a test step to the existing workflow rather than a new workflow.
Declare least-privilege permissions for GITHUB_TOKENmedium
.github/workflows/ci.yml
1 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Enable Dependabot or Renovatemedium
3 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
Fix: Commit .github/dependabot.yml covering the repo ecosystems plus github-actions.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Remove generated build output from version controlmedium5 occurrences
app
5 generated files committed
The reviewer reads src, production runs dist, and a stale bundle means the fix that was reviewed is not the code that executes.
Fix: Gitignore the output directory and build in CI.
Set persist-credentials: false on checkoutmedium
.github/workflows/build-snap.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
