The Problem

Running large open‑source models requires dedicated hardware that is usually hosted in third‑party clouds. When the cloud disappears or imposes new terms, the model becomes unavailable. Teams that need guaranteed uptime and full data control must provision and maintain their own compute, but there is no end‑to‑end guide that covers hardware selection, chassis design, BIOS tuning, and software stack in a single, reproducible package.

What This Does

The repository supplies a complete, hardware‑first reference implementation for three self‑contained AI compute boxes (2‑GPU, 4‑GPU, 8‑GPU). All design artefacts live under builds/:

builds/2x/README.md, builds/4x/README.md, builds/8x/README.md describe the target configuration, bill of materials, and assembly workflow. CAD files (.step, .stl) and a 3‑D‑print/CNC‑ready package are stored in builds/<size>/stepmodels/ and builds/<size>/stl-models/. Assembly photos and PDF manuals (docs/) give a step‑by‑step visual guide.

The software side is confined to the software/ folder, which documents OS setup, driver installation, BIOS tweaks, and model‑serving options (Ollama, vLLM, llama.cpp). No source code is shipped; the repo is a documentation‑driven blueprint rather than a runnable codebase.

How To Use It

Choose a configuration – read the table in README.md and open the matching guide, e.g. builds/4x/README.md. Procure hardware – follow the BOM file (builds/4x/bom/bom.md) for part numbers and quantities. Fabricate the chassis – download the STEP files from builds/4x/stepmodels/ or the STL files from builds/4x/stl-models/ and run them through your CNC/3‑D printer. Assemble – follow the photo series in builds/4x/photos/ and the written guide builds/4x/docs/assembly.md. Install software – the software/setup.md file outlines the OS (Ubuntu 22.04 LTS recommended), NVIDIA driver version, and BIOS settings (software/README.md references a bios.cfg example). Execute the steps manually; there is no automated installer. Run a model – after driver and CUDA are functional, use the instructions in software/run-models.md, e.g.:

Example for vLLM

vllm serve path/to/model --tensor-parallel-size 8

Replace the placeholder with the actual model path you have downloaded.

If any of the above documents are missing concrete commands (e.g., exact driver version), the user must infer or look up current NVIDIA recommendations.

Real‑World Use

A data‑science team can spin up the 4‑GPU “Team” build, install Ubuntu, follow software/testing.md to validate GPU health with nvidia-smi, then launch a vLLM endpoint that serves a quantized Llama‑405B model. Their internal API points to http://<box‑ip>:8000/v1/completions, guaranteeing that the model stays on‑prem and never leaves the corporate network.

Code Health & Issues

Low – No CI/CD pipeline – .github/ only contains issue templates; there is no workflow file to run tests or linting. Low – Missing automated install – software/ provides step‑by‑step markdown but no scripts (setup.sh, Makefile) to enforce reproducibility. Low – No executable code – the repo contains no source files (.py, .cpp, etc.), so functional testing is limited to the four test files whose content is unknown. Low – License present – LICENSE is MIT, satisfying legal requirements. Low – Documentation heavy – 27 Markdown files and many PDFs; the breadth is a strength, but the depth of software instructions is still “in progress” per the README.

Overall, the repository is well‑organized for hardware documentation but lacks software automation and test gating.

The Bottom Line

The repo delivers a thorough, hardware‑centric guide for building on‑prem AI boxes, ideal for teams that can allocate mechanical‑fabrication resources and prefer full control over model hosting. Its main weakness is the absence of automated software provisioning and CI, meaning deployments rely on manual steps that can be error‑prone. Use it if you have the expertise to follow detailed hardware manuals and are prepared to script the software stack yourself.
