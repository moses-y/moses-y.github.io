100% open-source IoT Platform - Integrate your devices, add intelligence, build custom apps

Forked from openremote/openremote

The Problem Organizations that need a self‑hosted IoT platform with rich protocol support, multi‑tenant capabilities, and custom rule engines often wrestle with fragmented tooling or vendor lock‑in. This repo attempts to fill that gap by providing a single code base that can integrate diverse devices, run automation rules, and expose a manager UI—all under an open‑source licence.

What This Does The core of the platform is a Java agent framework (agent/src/main/java/org/openremote/agent/) that implements dozens of protocol adapters—Artnet, Bluetooth Mesh, MQTT, HTTP/REST, and more. Protocol‑specific classes such as AbstractProtocol, AgentModelProvider, and the extensive Bluetooth‑mesh model hierarchy (BluetoothMeshAgent, MeshManagerApi, etc.) let developers plug in new device types without rewriting the whole stack.

CI/CD is driven by GitHub Actions (.github/workflows/) that build Docker images, run unit tests, and publish Maven packages. The platform is assembled with Docker Compose; the root docker-compose.yml (outside the scanned structure) defines services for the manager UI, database, and protocol agents. Configuration is injected via environment variables, most notably ORHOSTNAME which the README explicitly calls out for custom host/port setups.

How To Use It

Setup The fastest path is the documented Docker quickstart:

Pull the composed stack docker compose pull

Start the platform (add ORHOSTNAME if you’re not using localhost) ORHOSTNAME=192.168.1.1 docker compose -p openremote up -d

If you prefer to build from source, the agent/ module uses Gradle:

cd agent ./gradlew build # compiles the Java agents and protocol models

Configuration Environment variables live in .cicd/env/. The .env file (marked as a possible secret source) contains credentials such as SMTP details and SSH whitelist values; these should be rotated out of the repo and stored in a secret manager. The ORHOSTNAME variable, documented in the README, is the only required var for a custom host deployment.

Running it After docker compose up -d the manager UI is reachable at https://localhost. Accept the self‑signed certificate (see the README’s Chrome bypass notes) and log in with admin / secret. The UI then lets you create assets, agents, rules, users, and realms.

Real‑World Use A smart‑building deployment can use the Bluetooth‑mesh agent to provision BLE light fixtures. The BluetoothMeshAgent class (under agent/src/main/java/org/openremote/agent/protocol/bluetooth/mesh/) discovers provisioned nodes, configures application keys, and sends on/off commands via the SendSingleDataSegmentCommand. Rules defined in the manager’s “when‑then” engine can trigger lighting scenes based on occupancy sensors published over MQTT, demonstrating the platform’s ability to blend low‑power mesh networks with higher‑level automation.

Code Health & Issues Dependency lockfile missing – agent/build.gradle declares dependencies without a corresponding gradle.lockfile (or equivalent), risking non‑reproducible builds. Potential secrets in the repo – .cicd/env/.env contains SMTP credentials, SSH whitelist values, and other secrets that should be externalised; the .gitignore in that directory does not fully prevent commit. Test coverage limited – 8 test files are present, but the bulk of the Java code (especially the mesh protocol stack) lacks unit‑test scaffolding, making regression risk higher when protocol logic changes. CI breadth vs depth – Over 30 GitHub Actions workflows exist, indicating active integration, yet the pipeline’s primary focus is building/publishing images rather than exhaustive static analysis or security scanning.

The Bottom Line This repo delivers a capable, extensible IoT platform out‑of‑the‑box: a Java‑based agent framework, a rich UI, multi‑tenant support, and a full Docker‑compose deployment model. It’s well‑suited for medium‑to‑large teams that need to integrate heterogeneous devices and build custom automation without being locked into a SaaS vendor. The main caveats are the absent dependency lockfile and secrets stored in the repository—both easy to remediate by adding a gradle.lockfile and moving credentials to a secret manager. Teams comfortable with self‑hosting and Gradle‑driven builds will find the most value here.
