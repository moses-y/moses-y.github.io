Cairn

A AI general-purpose state-space search engine, validated first on autonomous penetration testing.

Forked from oritera/Cairn

The Problem Security teams need a repeatable way to explore an unknown attack surface from a known target to a defined objective (e.g., gaining a shell). Traditional scripts are static; they cannot adapt when the environment changes or when new findings appear. A framework that continuously reasons over collected facts, proposes intents, and executes them can automate this directed search while still allowing human hints.

What This Does Cairn implements a blackboard‑style state‑space search engine. The shared graph lives in the Cairn Server (cairn/src/cairn/server/app.py) exposing a REST API for reading/writing facts, intents, and hints. The Dispatcher (cairn/src/cairn/dispatcher/) monitors the board, creates three task types—bootstrap, reason, explore—and hands them to Worker adapters (cairn/src/cairn/dispatcher/workers/adapters/). Workers run an OODA loop: they read the full graph, decide the next intent, claim it, execute the associated action (e.g., a curl request, a Codex prompt, a mock step), and write back a new fact.

Key files: cairn/src/cairn/cli.py – command‑line entry that starts a dispatcher instance. cairn/src/cairn/server/models.py – Pydantic models for facts/intents. cairn/src/cairn/dispatcher/tasks/.py – logic for each task type. container/Dockerfile & root Dockerfile – two container images: one for the server, one for the dispatcher runtime.

How To Use It

Setup Install Python dependencies (uv is recommended, fallback to pip) uv sync # reads cairn/pyproject.toml; creates a lockfile if missing Or: pip install -r <(uv pip compile cairn/pyproject.toml) # manual lockfile generation Build the server container (optional) docker build -f Dockerfile -t cairn-server . Build the dispatcher container (optional) docker build -f container/Dockerfile -t cairn-dispatcher .

Configuration Environment variables expected by the server are defined in cairn/src/cairn/server/app.py (e.g., DATABASEURL). The repository does not ship a sample .env; users must create one before launching. Hints can be posted via the /hints endpoint; no static config file for hints is provided.

Running Start the server (development mode): python -m cairn.server.app

or, using the container: docker run -p 8000:8000 cairn-server

Start a dispatcher worker: python -m cairn.cli --project-id <PROJECTUUID>

The CLI reads the server URL from CairnSERVERURL (default http://localhost:8000). Once both processes are up, the dispatcher will bootstrap, reason, and explore until the goal fact is reached or no intents remain.

Real‑World Use A red‑team can launch Cairn against a target subnet. The server stores each discovered open port as a Fact. Workers generate Intents such as “attempt SSH login with credential X”. When a successful login fact is created, the Reason task evaluates the goal (“obtain root shell”) and may spawn new intents (e.g., privilege‑escalation exploits). Human analysts can inject Hints* (e.g., “skip port 22”) via the /hints endpoint, instantly influencing the next exploration cycle.

Code Health & Issues Low – Missing lockfile – cairn/pyproject.toml declares dependencies but no uv.lock or requirements.txt; builds are non‑reproducible. Low – Limited test coverage – Only 2 test files (tests/ not listed) exist; core dispatcher logic is untested. Low – No secret management – Server expects DATABASE_URL but provides no template or validation, increasing risk of misconfiguration. Low – Incomplete CI – GitHub Actions workflow (.github/workflows/build-container-ghcr.yml) builds containers but does not run unit tests or lint checks. Low – Documentation gaps – README shows a demo video but lacks a quick‑start guide; the docs/ folder contains design specs but no user‑level instructions. Low – Potential race condition – Workers claim intents via cairn/src/cairn/dispatcher/runtime/containers.py without explicit transaction isolation; concurrent workers could process the same intent.

No obvious security‑critical bugs are visible, and the code follows a clear modular layout (server ↔ dispatcher ↔ workers). The presence of a Dockerfile and docker‑compose.yaml suggests container‑first deployment is intended.

The Bottom Line Cairn offers a concrete implementation of a blackboard‑driven search engine, suitable for teams that need automated, iterative exploration of large, unknown state spaces (e.g., penetration testing, red‑team ops). The architecture is clean and extensible, but the project lacks reproducible builds, thorough testing, and production‑grade CI/CD. It is ready for pilot use by security engineers comfortable with Python and Docker, but it will require additional hardening before broader deployment.
