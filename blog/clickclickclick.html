The Problem

Operating a computer or Android device through an LLM requires stitching together screen capture, UI element detection, and action execution—all while managing different model providers. Most solutions are locked to a single vendor or require custom glue code for each task. This repo aims to abstract that pipeline into a reusable framework.

What This Does

clickclickclick is a Python framework that turns natural-language tasks into GUI actions on macOS or Android. It splits the work into two roles: a planner (decides the next action) and a finder (locates UI elements on screen). Both are implemented as interchangeable modules under clickclickclick/planner/ and clickclickclick/finder/, with providers for OpenAI, Gemini, Anthropic, and local Ollama models.

The execution layer lives in clickclickclick/executor/ with platform-specific handlers for android.py and osx.py. Configuration is YAML-driven: clickclickclick/config/models.yaml holds model settings, prompts.yaml contains the system prompts, and functiondeclarations/ defines the tool schemas per platform. The project exposes four interfaces: a CLI (main.py), a Gradio web UI (interface.py), a REST API (api.py), and a Python API.

How To Use It

Setup: Install dependencies with pip install -r requirements.txt after cloning. There's no lockfile, so pin versions manually if you need reproducible builds.

Configuration: Edit clickclickclick/config/models.yaml to set your model choices and export the API keys referenced there. Run python main.py setup to walk through selecting planner and finder models interactively.

Running it: Use the CLI directly:

python main.py run "Open Google news" --platform=android --planner-model=openai --finder-model=gemini

For local models with reduced image size:

python main.py run "Open Reddit" --platform=android --planner-model=ollama --finder-model=gemini --image-quality=45

The web UI starts via interface.py and the REST API via api.py, though the README doesn't document their exact invocation commands.

Real-World Use

A support automation pipeline: a ticketing system receives "check the printer queue on the office Mac," calls clickclickclick via its REST API with --platform=osx, and the framework captures screenshots, plans clicks, and executes the navigation. The same setup can run Android emulator tests for QA teams, using the same planner with a different executor.

Code Health & Issues

Med - No CI/CD - No .github/ or CI config detected. There's a .pre-commit-config.yaml for local linting, but no automated test gate before merges. Low - No dependency lockfile - pyproject.toml and requirements.txt declare ranges, not pinned versions. Reproducible installs aren't guaranteed. Low - Light test coverage - Only tests/testandroid.py and tests/test_osx.py exist. The planner/finder logic, which is the core value, has no direct tests. Low - Experimental disclaimer - README states the code is "highly experimental" and best results come from a specific Gemini model, suggesting the model-agnostic claim is aspirational rather than proven. Low - No license file - The repo has a LICENSE file, so this is likely fine, but it wasn't verified.

The Bottom Line

A pragmatic starting point for anyone who wants to prototype LLM-driven computer use without building the plumbing themselves. The modular planner/finder/executor split is clean, and supporting local models via Ollama is a genuine plus. It's not production-ready—no CI, minimal tests, and the README's own caveats make that clear. Best suited for developers evaluating the approach or building a proof of concept, not for teams needing a reliable automation layer today.
