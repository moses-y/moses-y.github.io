mcp unity

Model Context Protocol (MCP) plugin to connect with Unity Editor — designed for Cursor, Claude Code, Codex, Windsurf and other IDEs

Forked from CoderGamester/mcp-unity

The Problem Unity developers using AI‑assisted IDEs (Cursor, Claude Code, etc.) lack a reliable bridge that lets the assistant read Unity’s compiled package cache and invoke editor actions (e.g., create objects, run tests) from a language model. Without such a bridge, AI‑generated code cannot be validated or applied inside the Unity editor, forcing manual copy‑paste cycles.

What This Does mcp-unity implements the Model Context Protocol (MCP) for the Unity editor. The Editor folder (108 files) contains the Unity side of the bridge, e.g. Editor/UnityBridge/McpUnityEditorWindow.cs which opens a custom editor window and spawns McpUnityServer.cs to listen for TCP messages. The Server~ folder (≈50 files) hosts a Node.js service (Server~/src/index.ts) that speaks MCP, exposing resources like getGameObjectResource.ts and tools such as addAssetToSceneTool.ts. The Dockerfile (Server~/Dockerfile) packages the server into a container, enabling reproducible deployment independent of a local Node runtime.

Together, the Unity plugin forwards requests (create prefab, run tests, query scene hierarchy) to the server, which executes them via the Unity editor API and returns structured results that an LLM can consume.

How To Use It

Setup Unity side – Import the Editor folder as a Unity package (copy into <Project>/Assets/McpUnity). Unity will automatically compile the C# scripts. Server side – From the repository root:

cd Server~ npm ci # installs exact versions from package-lock.json

If you prefer containerised execution:

docker build -t mcp-unity-server Server~ docker run -p 5000:5000 mcp-unity-server

Configuration Server~/src/unity/unityConnection.ts expects the Unity editor to open a TCP socket on localhost:5000 (default). Change the port by editing the constant PORT in that file and rebuilding the Unity side. No external secrets are bundled; any API keys required by custom LLM prompts must be supplied at runtime (e.g., via environment variable OPENAIAPIKEY referenced in Server~/src/prompts/gameobjectHandlingPrompt.ts if used).

Running Start the Unity editor; the custom window appears under Window → MCP Unity. Click Start Server – this launches McpUnityServer which connects back to the Node service. In a terminal, launch the Node server (if not using Docker):

npm start # defined in Server~/package.json scripts

Once both ends report “connected”, LLM‑driven tools can issue commands through the MCP endpoint (e.g., POST to http://localhost:5000/api/addAssetToScene).

Real‑World Use A CI pipeline that runs automated UI tests could invoke the server from a script:

import { runTestsTool } from '../Server~/src/tools/runTestsTool'; await runTestsTool({ testFilter: 'Gameplay/' });

The tool calls GetTestsResource in Unity, executes the selected tests, and returns a JSON payload with pass/fail details, which a downstream LLM can summarise for developers.

Low – Docker entrypoint unclear – Dockerfile copies source but does not define a CMD or ENTRYPOINT; container will exit unless a command is supplied at run time. Low – Limited documentation – README explains high‑level purpose but lacks concrete install commands or configuration examples; developers must infer steps from source. Low – Test coverage – 28 test files exist (Server~/src/tests/.test.ts and Editor/Tests/*.cs), indicating reasonable coverage for core tooling. Low – License present – MIT license is included (LICENSE.md). Low – No secret leakage – No hard‑coded credentials observed.

Overall, the code follows a clear separation: C# editor integration vs. TypeScript server logic. Error handling is centralized in utils/errors.ts and logging via utils/logger.ts, which are referenced throughout both sides.

The Bottom Line mcp-unity delivers a functional MCP bridge that lets AI assistants manipulate Unity projects directly, with a clean split between editor plugins and a Node server. It is usable today but would benefit from a defined CI pipeline, clearer Docker startup instructions, and richer onboarding docs. Suitable for teams that already embed AI tooling into their Unity workflow and can allocate a small amount of setup effort.
