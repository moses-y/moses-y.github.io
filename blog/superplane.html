The Problem

Engineering teams need an automated way to turn backlog issues into verified pull requests. Manual coordination of agents, CI, and approvals is error‑prone and slows delivery.

What This Does

SuperPlane provides a control plane for agentic engineering. The core CLI (cmd/cli/main.go) orchestrates agent actions, verifies outcomes, and pushes changes back to GitHub. Agent logic lives in pkg/agents/agent_tools, where each tool (e.g., access.go, anthropic/provider.go) implements an action that can be called by the orchestrator. The renderer (pkg/cli/core/renderer.go) formats responses for human consumption, while the authorization service (pkg/authorization/service.go) enforces permission checks on every request.

The database layer (db/ and pkg/database/db_context.go) stores secrets, agent state, and audit logs. Web components (web_src/) expose a UI that visualises the factory workflow, but they do not drive the core logic.

How It Is Wired

Execution starts at main in cmd/cli/main.go (line 10). It creates a CommandContext and calls Execute.

  • Execute (pkg/agents/agent_tools/actions/access.go) is the most‑called hub (276 callers). It parses user input, resolves the organization ID (ResolveOrganizationID), and emits results.
  • Setup (pkg/components/addmemory/add_memory.go) is invoked by 210 callers and prepares memory‑backed tools.
  • Run (pkg/cli/core/command.go) drives the command loop and delegates to Execute.

The only outbound operation from the repo is Execute → ResolveEnvironment, which calls secrets.GetIntegrationKeys (crypto). File activity: main → Execute reads files via os.ReadFile. Database writes occur in pkg/authorization/service.go when checking permissions.

Key files with the widest blast radius:

  • pkg/agents/agent_tools/actions/access.go – 14 functions, 4 types, 101 callees, 66 callers.
  • pkg/components/addmemory/add_memory.go – 20 functions, 26 callees, 105 callers.
  • pkg/authorization/service.go – 53 functions, 8 callees, 19 callers.

A cycle exists between Execute and ResolveEnvironment, making any change to the permission model ripple through the entire orchestrator.

How To Use It

Setup

# Clone the repo
git clone https://github.com/moses-y/superplane
cd superplane

# Install Go dependencies
go mod download

# Build the CLI
make build   # Makefile target exists

Configuration Copy .env.example to .env and set required keys (e.g., GITHUB_TOKEN, OPENAI_API_KEY).

Running

# Start the CLI
go run cmd/cli/main.go run <issue-id>

The CLI will parse the issue, run the relevant agent action, and push a PR back to the repository.

If you prefer Docker:

docker build -t superplane .
docker run -e GITHUB_TOKEN=... -e OPENAI_API_KEY=... superplane run <issue-id>

Real‑World Use

A team uses SuperPlane to auto‑fix unit tests:

go run cmd/cli/main.go run ISSUE-123

The orchestrator invokes the access tool, which calls the Anthropic model to suggest changes, validates the PR, and merges it if confidence is above a threshold.

Code Health & Issues

  • High – No CI workflow for builds or tests (repo has 5566 files).
  • High – No deploy gate for Dockerfile artifacts.
  • Medium – Dependabot/renovate not configured.
  • Medium – Container base image not pinned by digest.
  • Low – Missing .editorconfig, .gitattributes, formatter config.

The repo contains tests (test/), a Dockerfile, and a license, but lacks automated build and deployment validation.

The Bottom Line

SuperPlane offers a robust, Go‑centric control plane that ties agent actions to GitHub workflows. Its modular design allows teams to plug in new tools, but the lack of CI and image pinning introduces risk. It is best suited for teams willing to add their own pipeline around the provided CLI and Docker image.
