The Problem

Managing a multi-node Kubernetes homelab with diverse workloads (media serving, AI tools, databases, monitoring) typically requires stitching together disparate configuration tools, secrets management, and deployment pipelines. Without a unified GitOps approach, configuration drift, manual interventions, and inconsistent environments become the norm.

What This Does

This repository implements a complete GitOps-driven homelab infrastructure using Flux CD for Kubernetes, Ansible for node provisioning, and Docker Compose for services outside the cluster. The kubernetes/ directory contains 116 files organized by application domain (arr/, databases/, monitoring/, default/) with each app following a consistent pattern: a helmrelease.yaml for the chart, source.yaml for the Helm repository, and ks.yaml for the Flux Kustomization. The ansible/ directory handles OS-level tasks like ntp.yml, qemu-guest-agent.yml, and weekly maintenance via apt.yml and docker-prune.yml.

Secrets management uses SOPS with age encryption, referenced in .sops.yaml. The docker/ directory provides standalone services (Caddy reverse proxy, Jellyfin, Wazuh) with docker-compose.yml files and custom configurations like Caddy's fail2ban-jail.conf and caddy-limit.conf. CI/CD runs through GitHub Actions workflows including CD.yml for Flux reconciliation, trivy.yml for vulnerability scanning, and ansible-playbooks.yml for node management.

Real-World Use

A developer forks this repo, points Flux at their cluster, and immediately gets a media stack (Sonarr, Radarr, Prowlarr, Sabnzbd), AI tooling (MCP Hub, CLI Proxy API), databases (Crunchy Postgres, Dragonfly), and monitoring (Blackbox exporter, Fluent Bit) with secrets encrypted via age keys. Weekly Ansible playbooks handle apt upgrades and Docker pruning automatically.

Code Health & Issues

High - No automated tests detected across any layer (Kubernetes manifests, Ansible playbooks, Docker configurations). Configuration drift and regressions will go undetected until runtime. Med - Hardcoded secrets patterns: external-secret.yaml files reference secret names without validation that backing stores exist. Missing a validation step in the CD pipeline. Med - No license file in repository root despite LICENSE being listed in structure. Unclear usage rights for the Ansible roles and custom Dockerfiles. Low - .gitleaks.toml present but no evidence of secrets scanning in CI workflows. Gitleaks configured but not enforced.

The Bottom Line

A well-organized, opinionated GitOps homelab that demonstrates production patterns (Flux, SOPS, external-secrets-operator) applied to personal infrastructure. The lack of tests and validation pipelines makes it risky for production adoption, but it's an excellent reference for anyone building a Kubernetes homelab with similar service requirements. Best suited for experienced operators who can add testing and validation as needed.
