llama.cpp

LLM inference in C/C++

Forked from ggml-org/llama.cpp

The Problem Organizations seeking local LLM inference often face a trade‑off between ease of deployment, hardware compatibility, and performance. Many solutions require heavy frameworks, GPU‑specific binaries, or complex compilation pipelines, limiting adoption on heterogeneous fleets of CPUs, Apple silicon, and embedded RISC‑V or GPU devices.

What This Does llama.cpp is a plain C/C++ implementation that runs LLM inference with minimal runtime dependencies. The core inference engine lives in common/ – files such as common/arg.cpp/common/arg.h handle CLI parsing, common/sampling.cpp/common/sampling.h implement token‑selection strategies, and common/preset.cpp/common/preset.h configure quantization and backend selection. Model files in GGUF format are produced by conversion scripts at the repo root: converthftogguf.py, convertloratogguf.py, and convertllamaggmltogguf.py. Hardware back‑ends are defined under docs/backend/ (CUDA, ROCm, Metal, Vulkan, SYCL, CANN, ZenDNN) and corresponding Dockerfiles (.devops/cpu.Dockerfile, .devops/cuda.Dockerfile, .devops/rocm.Dockerfile, etc.) provide pre‑built environments for each target. CMake configuration is centralized in CMakeLists.txt (root) and common/CMakeLists.txt, while a Makefile at the project root offers quick make‑based builds.

How To Use It

Setup Package managers – brew install llama.cpp, nix-shell -p llama.cpp, or winget install ggml.llama.cpp. Docker – pull the official image described in docs/docker.md or build from .devops/cpu.Dockerfile (CPU), .devops/cuda.Dockerfile (NVIDIA GPU), or .devops/rocm.Dockerfile (AMD GPU). Source – clone the repo and run make (uses the root Makefile) or cmake --build . --config Release (uses CMakeLists.txt). Example build commands:

Using make make

Using CMake mkdir build && cd build cmake -DLLAMA_CUBLAS=ON .. # enable CUDA if desired make -j$(nproc)

Configuration No environment variables are required beyond pointing at a model file. The CLI expects a .gguf model path; model‑specific settings (context size, seed, etc.) are passed as flags.

Running it Command‑line client – llama-cli -m path/to/model.gguf -p "Prompt" (as shown in README.md). Server mode – llama-server -m path/to/model.gguf -p 8080 launches an OpenAI‑compatible REST API; the server binary is built the same way as the CLI.

Real‑World Use A machine‑learning engineer needs to run a 7 B‑parameter model on a developer laptop with an Apple M‑series chip. They pull a quantized GGUF model (e.g., ggml-org/gemma-3-1b-it-GGUF), then execute:

llama-cli -m model.gguf -p "Summarize this text:" \ --ctx-size 4096 --temp 0.7

The backend automatically selects NEON/Accelerate kernels (see common/preset.cpp). For a small prototype service, the same model is launched via llama-server and consumed by a front‑end calling http://localhost:8080/completion, leveraging the OpenAI‑compatible endpoint.

Code Health & Issues Tests & CI – Five test files exist under test/ and GitHub Actions workflows (build.yml, docker.yml, python‑lint.yml, etc.) cover build, packaging, and Python‑binding checks. License – LICENSE file contains the MIT license; CODEOWNERS and SECURITY.md are present. Build system – CMake and Makefile are well‑structured; cmake/license.cmake and cmake/build-info.cmake enforce reproducible builds. Potential gaps – Test coverage is limited to a subset of back‑ends; some niche Dockerfiles (e.g., .devops/cann.Dockerfile) lack recent updates. No formal Python package wraps the C library, but Python scripts for conversion and testing live in ci/ and .devops/nix/.

No critical bugs or missing error‑handling patterns were identified from the static structure; the CLI argument parsing in common/arg.cpp validates required flags and returns descriptive messages on failure.
