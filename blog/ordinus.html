The Problem

Ordinus addresses the fragmentation of AI agent workflows where users must manually compose roles, manage conversations, and coordinate between different AI CLIs (Codex, Claude) without a unified local interface. The pain point is the lack of a local-first command center that connects these agents to existing tools while keeping data on-premise.

What This Does

Ordinus is a local-first Electron desktop app (200 files, primarily in app/) that lets you compose AI agents from your local Codex/Claude CLIs into scheduled workflows. The core app lives in app/ with Electron Vite configuration (app/electron.vite.config.ts) and builder setup (app/electron-builder.yml). It uses SQLite for persistence via Drizzle ORM (app/drizzle.config.ts) with 51 migration files in app/resources/db/migrations/ defining the data model. A Workflow Designer (app/resources/screenshots/workflow-designer.png per README) visually wires agents and tasks into a DAG that compiles to runnable plans. The app/resources/google-mcp/ directory provides Google API integration (Gmail, Calendar, Drive) with OAuth credentials stored encrypted on machine. Agent profiles and skills are configured through YAML files in .claude/skills/ and .codex/skills/ directories, with openai.yaml runtime adapters for each skill. Connections run under your own accounts—Google, WhatsApp, and X credentials are stored encrypted locally, not in the cloud.

How To Use It

Setup: Install from the latest release (ordinus-<version>-setup.exe for Windows, Ordinus-<version>.dmg for macOS). The app is Electron-based with npm dependencies (app/package.json). First-launch on macOS requires stripping the quarantine attribute: xattr -dr com.apple.quarantine /Applications/Ordinus.app then open /Applications/Ordinus.app. Windows launches through SmartScreen with "More info → Run anyway."

Configuration: Environment variables and API keys are configured within the app UI for each connection type. The Google MCP integration lives in app/resources/google-mcp/ with server.mjs, tools.mjs, and auth.mjs. No .env files are visible in the repo structure, suggesting config is managed through the app's internal settings rather than file-based env vars.

Running it: Launch the Ordinus desktop application. No CLI entry point is exposed in the repository structure—the primary interface is the Electron app itself.

Real-World Use

A knowledge worker composes an "article writer" agent with a profile from app/resources/profiles/content-production/article-writer.md, wires it through the Workflow Designer (app/resources/screenshots/workflow-designer.png) to fetch research from Google Calendar and draft in Gmail, then schedules the DAG to run nightly. The same engine handles manual runs and scheduled executions, with the Workboard (app/resources/screenshots/workboard.png) showing real-time provider output and allowing runtime steering. The agent's conversation space persists locally via SQLite migrations.

Code Health & Issues

Build & CI: GitHub Actions workflows present (.github/workflows/ci.yml, .github/workflows/release.yml) with Electron builder release pipeline. No structural red flags detected—tests, CI, license, and lockfiles are where expected. SQLite migrations: 51 migration files in app/resources/db/migrations/ indicate a evolving schema; migration 0048 drops workspacename and ordinusdisplay_name columns, suggesting a recent refactor that may require data migration attention. Electron signing: Builds are unsigned (README explicitly notes this), causing Gatekeeper/SmartScreen prompts on first launch—acceptable for local-first tools but impacts deployment friction. No visible test files: Only 1 test file found in the structure; test coverage is minimal or the tests are stored elsewhere. Dependency hygiene: app/package-lock.json present, but no npm audit or security scanning evidence in the CI workflows observed.

The Bottom Line

Ordinus is a competent local-first Electron app for composing and scheduling AI agents backed by your own CLIs and connected to your existing tools—Google, WhatsApp, X—with data staying on your machine. It's well-structured for its scope but limited by unsigned builds, sparse test coverage, and a migration set that's seen recent structural changes. Best for individual or small team users who want a desktop interface for agent workflows without cloud dependencies; less suited if you need rigorous CI/CD or multi-user deployment out of the box.
