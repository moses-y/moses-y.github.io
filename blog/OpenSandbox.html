The Problem

AI agents need a controlled execution environment that isolates code, restricts network egress, and injects credentials safely. Without a unified sandbox, teams cobble ad‑hoc containers, risk secret leakage, and spend effort on custom networking policies.

What This Does

OpenSandbox delivers a full sandbox platform built around Docker/Kubernetes runtimes. The core runtime lives in components/egress/ (e.g., main.go, Dockerfile, go.mod) and implements network egress control, credential vault, and nftables‑based policy enforcement. The user‑facing CLI resides in cli/src/opensandboxcli/, with commands such as sandbox, file, egress, and credentialvault wired in commands/.py. SDKs for multiple languages are generated from the same protocol (see specs/), but the repository focuses on the Go egress component and the Python CLI.

How To Use It

Setup

Build the egress component container cd components/egress docker build -t opensandbox/egress:latest -f Dockerfile .

Install the CLI in a virtual environment

cd ../../cli python -m venv .venv source .venv/bin/activate pip install -e .

The pyproject.toml defines the CLI package; pip install -e . pulls in all dependencies declared there.

Configuration

Network policy: edit components/egress/pkg/policy/policy.go or supply a JSON policy file referenced by the --policy flag of the CLI (see cli/src/opensandboxcli/commands/egress.py). Credential vault: place secrets in a JSON file and point the CLI via --vault-file (handled in pkg/credentialvault/vault.go). Docker/K8s runtime selection is controlled by flags in cli/src/opensandboxcli/commands/sandbox.py.

Running it

Start the egress service container: docker run -d --name osb-egress -p 8080:8080 opensandbox/egress:latest

Create a sandbox and execute a command: opensandboxcli sandbox create --runtime docker --image python:3.11 opensandboxcli sandbox exec <sandbox-id> "python -c 'print(42)'"

The CLI entry point is cli/src/opensandboxcli/main.py, which invokes opensandboxcli/main.py.

Real‑World Use

A CI pipeline for a coding‑assistant agent can spin up a sandbox, run user‑submitted code, and destroy the environment automatically: name: Run user code run: | sandboxid=$(opensandboxcli sandbox create --runtime docker --image python:3.11) opensandboxcli sandbox exec $sandboxid "python solution.py" opensandboxcli sandbox delete $sandboxid

Network egress is automatically filtered by the egress component, preventing the code from reaching external services unless whitelisted.

Code Health & Issues

Low – Test coverage – 60 test files exist (components/egress/_test.go, cli/tests/.py), but integration tests for full sandbox lifecycle are limited to CI workflows (.github/workflows/real-e2e.yml). Medium – Documentation gaps – The README outlines features but lacks a quick‑start guide; docs/ folder is sparse, and required CLI flags are only described in code comments (commands/.py). Low – Platform assumptions – Egress code uses Linux‑specific nftables and iptables (pkg/iptables/.go), which will fail on non‑Linux hosts without a fallback. Low – Secret handling – Credential vault expects a JSON file; the repository does not ship a template or validation schema, increasing risk of malformed input. None – Licensing/CI – A LICENSE file is present, and CI pipelines cover linting, unit tests, and end‑to‑end builds, indicating a disciplined SDLC.

The Bottom Line

OpenSandbox offers a well‑structured, container‑based sandbox with strong egress controls and a usable Python CLI. It is ready for teams that need reproducible, isolated AI agent execution and are comfortable managing Docker/Kubernetes runtimes. Minor work is needed on onboarding documentation and cross‑platform support, but the codebase is test‑covered and CI‑driven, making it a solid foundation for production workloads.
