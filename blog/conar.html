Technical Briefing: conar

The Problem

Conar addresses the pain point of complex database interactions across multiple database platforms. Developers working with PostgreSQL, MySQL, MSSQL, and Clickhouse often face fragmented tooling, inconsistent SQL dialects, and security concerns around connection string management. The project aims to consolidate these interactions under an AI-assisted interface with secure cloud storage.

What This Does

Conar is a full-stack application with a React/TypeScript frontend (apps/app) and Hono-based API (apps/api). The API layer uses oRPC for type-safe RPC, Drizzle ORM for database schema management, and Better Auth for authentication. AI-powered SQL assistance runs through the AI SDK with multiple LLM providers (Anthropic, OpenAI, Gemini, XAI) wired in apps/api/lib/posthog.ts and apps/api/lib/resend/ for email handling. Database dialect support is implemented per vendor under apps/app/src/entities/connection/dialects/—PostgreSQL, MySQL, MSSQL, and Clickhouse each have dedicated schema generators and format adapters (drizzle, kysely, prisma, prisma, typescript, zod). Connection management flows through apps/api/orpc/routers/connections/, while query routing lives in apps/api/orpc/routers/queries/. The frontend UI is built with shadcn/ui components under apps/app/src/components/ and a Monaco-based SQL editor in apps/app/src/components/monaco.tsx.

How To Use It

Setup: Clone the repo and run pnpm install at the root. The project uses Bun as its package manager (per package.json files in both apps/).

Configuration: Copy apps/api/.env.example and apps/app/.env.example to .env files. Required vars include database connection strings, API keys for Stripe, Resend, PostHog, and AI provider keys (Anthropic/OpenAI/Gemini/XAI). The apps/api/env.ts file likely validates these at runtime.

Running it: Start infrastructure with pnpm run docker:start (PostgreSQL + Redis). Then run database migrations via pnpm run drizzle:migrate. Launch all development servers with pnpm run dev, which uses Turbo to concurrently start the API and Electron frontend.

Entry points: The API entry is apps/api/index.ts; the Electron/Renderer app starts from apps/app/index.html with Vite dev server.

Real-World Use

A data analyst connects a PostgreSQL warehouse to Conar and prompts the AI: "Show me the top 5 customers by churn rate from the last quarter, and generate a LEFT JOIN query to combine orders and support tickets." The AI SDK returns optimized SQL, which Conar executes via the connections router. The analyst can then save the query, share the connection string (encrypted), and iterate with follow-up prompts to refine results or add pagination. This workflow replaces manual SQL writing and reduces reliance on GUI clients for routine analysis.

Code Health & Issues Dependencies declared without a lockfile (Low risk) — apps/api/package.json lists dependencies but no pnpm-locky or similar lockfile is present in the root, meaning pnpm install on a fresh clone may resolve to different dependency versions, causing non-reproducible builds. No lockfile — The root has no pnpm-locky or package-lock.json, only package.json files in apps/api/ and apps/app/. This is the primary build reproducibility risk. E2E tests require manual server setup — The README notes E2E tests require running pnpm run test:start and a PostgreSQL connection before execution. This manual gate may lead to skipped or flaky test runs in CI. CI configured — GitHub Actions workflows exist for lint (lint-check.yml), publishing CLI/memoize, and releases, indicating some SDLC maturity. Secrets in repo — .env.example files are present but presumably safe since they’re examples; however, no .env files should be committed. The .gitignore at root should be verified to exclude them. Strong type safety — oRPC routers, Drizzle schemas, and Arktype usage suggest intentional type boundaries across the stack.

The Bottom Line

Conar is a functional, well-structured full-stack project that successfully integrates AI-assisted SQL generation with multi-database connection management. The codebase shows thoughtful layering—oRPC for RPC, Drizzle for ORM, per-dialect schema generators—and the README provides clear onboarding. The absence of a lockfile and the manual E2E test setup are the most concrete risks. It’s worth evaluating for teams that regularly switch between PostgreSQL, MySQL, MSSQL, and Clickhouse and want AI assistance for query writing, but the lockfile gap and manual test requirements should be addressed before production adoption.
