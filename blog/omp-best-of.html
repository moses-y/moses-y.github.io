omp best of

Best-of-N coding agents with LLM-as-a-Verifier selection for Oh My Pi: isolated git worktrees, verifier-ranked trajectories, winner-only patch application

Forked from wolfiesch/omp-best-of

The Problem When a single Oh My Pi (OMP) run fails to produce a correct fix, developers must manually iterate, which is time‑consuming and error‑prone. Selecting the best solution from multiple candidate agents adds further friction because there is no built‑in ranking or safe patch application.

What This Does omp‑best‑of runs N independent OMP agents in isolated copy‑on‑write workspaces, captures each full execution trajectory (exit code, usage, generated patch), and ranks the results with an LLM‑as‑a‑Verifier backend or a sampled OMP judge. The CLI (src/cli.ts) outputs the winning patch and, when --apply is supplied, applies only that patch to the original HEAD if the working tree remains clean.

Key files:

src/cli.ts – entry point that parses --n, --apply, and verifier options. bench/run.ts – orchestrates workspace creation, parallel OMP sessions, and artifact collection. bench/tasks//repo/.js – concrete candidate implementations (e.g., memoize.js, circuit-breaker.js). bench/tasks//oracle/.test.js – reference oracle tests used by the verifier.

The plugin is deliberately modular: each benchmark task ships its own package.json, allowing per‑task npm dependencies while the core runner stays language‑agnostic.

How To Use It Clone the repo git clone https://github.com/moses-y/omp-best-of cd omp-best-of Install Bun (required runtime) curl -fsSL https://bun.sh/install | bash export PATH="$HOME/.bun/bin:$PATH" (Optional) Install per‑task npm deps – the runner will npm install lazily. No root package.json, so no global install step is needed. Ensure OMP 17+, a clean git tree, and uv (for the logprob verifier) are available. Example: omp --version and uv --version. Run the CLI bun run src/cli.ts --n 5 --apply "Fix the failing authentication test"

Configuration – The CLI reads OMP model/thinking flags from the current session; you can override them with --model and --thinking. The logprob verifier defaults to the deepseek/deepseek-v4-flash model and requires a reachable OMP model‑registry endpoint. No additional config files are required; all defaults are hard‑coded in src/cli.ts and bench/run.ts.

Running tests – The repository ships 57 test files (e.g., bench/tasks/async-memoize/repo/memoize.test.js). Execute them with the bundled CI workflow (.github/workflows/ci.yml) or manually via bun test inside each task directory.

Real‑World Use A CI pipeline for a microservice can invoke omp-best-of on failing integration tests. The pipeline checks out the repository, runs bun run src/cli.ts --n 3 to generate three candidate patches, lets the logprob verifier rank them, and automatically applies the winning patch if the repository remains clean. This reduces mean‑time‑to‑repair from hours (manual debugging) to minutes, while preserving auditability through the generated trajectory artifacts.

Code Health & Issues Low – Missing lockfiles – Each bench/tasks/*/repo/package.json lacks a corresponding package-lock.json or pnpm-lock.yaml, making builds non‑reproducible. (bench/tasks/async-memoize/repo/package.json is representative). Medium – No root package manager config – The top‑level directory has no package.json or lockfile, so dependency management relies on per‑task files; this can cause version drift across tasks. Low – No test coverage for CLI – Tests exist for individual task implementations but none target src/cli.ts, leaving the orchestration layer unvalidated. Info – CI present – GitHub Actions workflow (.github/workflows/ci.yml) runs the test suite on push, indicating an automated quality gate. Info – Documentation – README provides usage examples and high‑level architecture; additional docs are limited to task‑specific markdown files.

No critical security issues (e.g., exposed secrets) are evident from the file list.

The Bottom Line omp-best-of delivers a practical “run‑many‑candidates‑and‑pick‑the‑best” workflow for Oh My Pi users, with a clear CLI and automated ranking. It is well‑structured for extension but suffers from inconsistent dependency lock management and limited test coverage of the core orchestrator. Teams that already use OMP and need faster patch selection will find it useful; small or security‑sensitive projects should address the lockfile and test gaps before adopting.
