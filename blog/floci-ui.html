The Problem

Developers running local multi‑cloud runtimes need a single UI that mirrors the look‑and‑feel of a cloud console while showing only real resources. Maintaining separate dashboards or hand‑crafting mock data quickly becomes a maintenance burden and obscures the true state of the local emulators.

What This Does

floci-ui delivers a browser‑based console that aggregates services from the API (packages/api/src/index.ts) and presents them in a unified explorer (packages/frontend/src/App.tsx). The service catalog lives in packages/api/src/cloud-spi/serviceCatalog.ts; adapters for AWS, Azure, and GCP are under packages/api/src/adapter‑. The frontend pulls data via the generated client in packages/frontend/src/api/cloudProxyClient.ts. Dockerfiles (docker/Dockerfile, packages/api/Dockerfile, packages/frontend/Dockerfile.dev) enable containerised builds, and the monorepo is managed with pnpm (pnpm-workspace.yaml).

How To Use It

Clone and install dependencies git clone https://github.com/floci-io/floci-ui.git cd floci-ui pnpm install # workspace installs all packages Provide runtime configuration cp .env.example .env # edit as needed; currently only Docker ports are required Start the full stack (API + UI) locally docker compose up # AWS‑only profile docker compose --profile multicloud up # include Azure & GCP adapters Access the console open http://localhost:4500

Build the service matrix (required after adding a new adapter):

cd packages/api && bun run scripts/service-matrix.ts

The UI entry point is packages/frontend/index.html served by the API server at http://localhost:4500/api.

API routes are defined in packages/api/src/routes/*.ts; for example, GET /api/clouds/:cloud/services is implemented in packages/api/src/routes/clouds.ts.

Real‑World Use

A CI pipeline runs a local Floci runtime (e.g., floci-runtime-aws) alongside the UI. After docker compose up, developers can:

In a test script

curl http://localhost:4500/api/clouds/aws/services | jq . → JSON list of available AWS services (EC2, EKS, S3, …)

The UI then displays live EC2 instances, EKS clusters, or S3 buckets without any placeholder data, letting engineers validate infrastructure code against their local emulator.

Code Health & Issues

High – Runtime gaps – Azure Serverless adapter exists but the Azure runtime returns 501 (see packages/api/src/azure.test.ts & packages/api/src/azure.ts). UI will show “coming soon” rows, which may confuse users if not documented. Medium – Inconsistent Dockerfiles – Separate Dockerfile.package and per‑package Dockerfiles duplicate base image logic; a single multi‑stage Dockerfile could reduce image size and maintenance. Medium – Missing environment documentation – .env.example is present but does not list required variables for connecting to local runtimes (e.g., endpoint URLs). Consumers must infer these from code. Low – Linting scope – Frontend has eslint.config.js; the API package lacks an explicit ESLint config, potentially allowing style drift. Low – Test coverage uneven – 22 test files cover many adapters, but critical paths like packages/api/src/cloudProxy.ts have no dedicated unit tests.

Overall the repository includes a CI workflow (.github/workflows/ci.yml), a lockfile (pnpm-lock.yaml), and a reasonable test suite, indicating an active quality process.

The Bottom Line

floci-ui provides a functional, container‑ready console that accurately reflects locally emulated cloud resources. It is well‑structured for a monorepo and ships with CI and tests, but teams should be aware of incomplete Azure Serverless support and the need to flesh out environment configuration documentation. Suitable for organizations that already run Floci runtimes and want a single pane of glass for multi‑cloud development.
