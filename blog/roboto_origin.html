Technical Briefing – robotoorigin (aggregation snapshot)

The Problem

Building a DIY humanoid robot from scratch requires coordinated hardware designs, ROS2 middleware, and sensor drivers. Managing dozens of sub‑repositories and keeping them in sync is a source of friction for teams that want a reproducible development environment.

What This Does

robotoorigin is a snapshot‑only repository that aggregates the core modules needed to assemble and run the ROBOTOORIGIN prototype. The top‑level layout groups the most active components under modules/robopartydeploy:

ROS2 deployment framework – modules/robopartydeploy/src/camera/ contains the RealSense driver (realsense2camera), ONNX inference assets (encoder.onnx), and launch scripts (depth.launch.py). Python utilities – motion‑player and IMU examples (modules/robopartydeploy/scripts/motionplayer.py, imupyexample.py). Configuration – YAML files for motion profiles (scripts/config/motionplayer.yaml) and zero‑position calibration (scripts/config/setzero.yaml).

The repository also bundles documentation (README.md, READMEcn.md, assets/BOM.md) and a CI workflow that updates a star‑history badge.

How To Use It

Prerequisites – Ubuntu 22.04 (or any ROS 2 Humble‑compatible distro) with colcon, python>=3.10, and the Intel® RealSense SDK. The presence of CMakeLists.txt and package.xml in modules/robopartydeploy/src/camera/ implies a standard ROS 2 build. Workspace setup

Clone the aggregation repo

git clone https://github.com/Roboparty/robotoorigin.git cd robotoorigin

Initialise sub‑modules (hardware, deploy, etc.)

git submodule update --init --recursive

Create a ROS2 workspace and symlink the modules

mkdir -p rosws/src ln -s $(pwd)/modules/robopartydeploy rosws/src/robopartydeploy Build

cd rosws colcon build --symlink-install source install/setup.bash Configuration – Edit the YAML files under modules/robopartydeploy/scripts/config/ to match the robot’s joint offsets or desired motion sequences. No environment variables are required beyond the ROS domain. Run – Launch the depth camera node and a simple motion player:

ros2 launch robopartydeploy camera/depth.launch.py ros2 run robopartydeploy motionplayer.py

The Python script reads motionplayer.yaml and publishes joint trajectories to the robot’s controller (the controller code lives in the rpohardware sub‑repo, not in this snapshot).

Real‑World Use

A research lab can pull this snapshot, build the ROS2 stack on a Jetson Orin, and immediately start streaming depth data from a D435i sensor (realsensed435i.yaml). By swapping motionplayer.yaml for a reinforcement‑learning policy generated with Isaac Lab, the same hardware can be used for gait‑learning experiments without modifying the underlying driver code.

Code Health & Issues

Bugs / Risks

Med – Missing hardware‑abstraction layer – The snapshot contains only the ROS2 middleware; low‑level motor drivers reside in rpohardware, so the robot cannot be driven without that sub‑repo. Low – Hard‑coded file paths – modules/robopartydeploy/scripts/motionplayer.py references ../assets/ relative to the script location; moving the script breaks execution. SDLC / Hygiene Low – License present – GPL‑v3 at root and in sub‑modules. Low – CI only updates star badge – No automated build or test jobs for the snapshot itself; the actual driver (realsense2camera) ships its own CI in modules/robopartydeploy/src/camera/thirdparty/realsense-ros/.github/workflows. Low – Documentation – README explains the snapshot purpose and links to the hardware and deploy sub‑repos, but does not provide a step‑by‑step “quick start” guide; users must infer the build flow from ROS conventions.

Overall, the repository is well‑structured, with clear separation of third‑party drivers and project‑specific scripts. The presence of 31 test files in the RealSense driver and a fully defined CMakeLists.txt suggests reasonable test coverage for the sensor stack.

The Bottom Line

robotoorigin offers a convenient aggregation point for the ROS2 middleware and example scripts needed to operate the ROBOTOORIGIN humanoid platform. It is most useful for teams that already have access to the hardware sub‑repo (rpo_hardware) and are comfortable with ROS2 build workflows. The snapshot itself is clean and well‑documented, but it does not include the low‑level motor control code, so it cannot be used as a standalone robot stack without pulling the missing sub‑modules.
