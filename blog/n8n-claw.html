The Problem

Standing up a personal AI agent means stitching together an LLM, a chat frontend, memory, tool execution, and scheduling — then hosting it somewhere. Most solutions lock you into a vendor or require significant glue code. n8n-claw addresses this by building the entire agent on top of n8n, a self-hosted workflow automation platform, with PostgreSQL for memory and Claude as the reasoning engine. Everything runs on your own infrastructure behind a single setup script.

What This Does

n8n-claw is a collection of 18 n8n workflow JSON files (in workflows/) that together form an autonomous agent. The core orchestration lives in workflows/n8n-claw-agent.json, with supporting workflows for memory consolidation, reminders, background checks, and sub-agent delegation. The agent persists long-term memory to PostgreSQL via Supabase migrations in supabase/migrations/, using hybrid search (semantic + full-text + entity match fused via RRF) with time decay and category-based expiry.

Three lightweight bridge services handle external integrations: browser-bridge/src/main.py drives a real Chromium via Browser Use, email-bridge/server.js and file-bridge/server.js are small Express servers. The discord-bridge/bot.js provides a Discord interface. Communication happens over Telegram or HTTP webhooks, and the agent can build its own MCP tools on demand via workflows/mcp-builder.json.

How To Use It

Setup: The repo ships a setup.sh script and a docker-compose.yml that orchestrates n8n, PostgreSQL, SearXNG, and the bridge services. The browser-bridge/requirements.txt implies pip install -r requirements.txt for that component.

Configuration: Copy .env.example to .env and set your Anthropic API key, Telegram bot token, and PostgreSQL credentials. The supabase/migrations/ directory contains the full schema — 001schema.sql through 009agents_rename.sql — applied automatically by the setup script.

Running it:

From the repo root

./setup.sh

This script handles environment setup, applies the Supabase migrations, and starts the Docker stack. After startup, import the workflow JSON files from workflows/ into n8n and connect them to your Telegram bot. The README.md documents the full process, including connecting Claude Desktop or external tools via MCP.

Real-World Use

A practical deployment: you run n8n-claw on a small VPS with docker-compose.yml. You message your agent on Telegram: "Check my email every 15 minutes and remind me about anything urgent." The background-checker.json workflow polls the email bridge, the heartbeat workflow (workflows/heartbeat.json) pushes overdue-task reminders, and the memory-consolidation.json workflow periodically summarizes conversations into long-term storage. When you ask "What did I discuss with Sarah last week?", the hybrid search in the memory workflows retrieves the relevant context.

Code Health & Issues

Med — No test files detected — zero test coverage across all 69 files. The workflow JSONs and bridge services have no automated verification, making regressions likely during updates. Med — No LICENSE file — usage and redistribution rights are unclear. The repo is forked from a 547-star project, so licensing ambiguity is a real concern for commercial use. Low — Dependencies declared without lockfile — browser-bridge/requirements.txt pins no versions, so builds are non-reproducible. The Docker images will pull whatever is current at build time. Low — CI is minimal — .github/workflows/mirror-to-codeberg.yml only mirrors to Codeberg; there's no build, test, or lint pipeline. Low — Heavy reliance on n8n internals — the workflows are JSON exports tied to specific n8n node configurations. Upgrading n8n could break them, and they're not easily diffable in version control.

The Bottom Line

n8n-claw is a genuinely ambitious project that packs a lot of functionality into a self-hosted package. The architecture is sound — n8n for orchestration, PostgreSQL for memory, and a clean bridge pattern for external services. The lack of tests and a license, plus the fragility of versioned workflow JSONs, makes it better suited to tinkerers and small teams who can debug issues themselves than to production deployments. If you're comfortable with n8n and want a self-hosted agent without vendor lock-in, it's worth a serious look.
