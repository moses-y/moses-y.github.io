Technical Briefing – Jitsu (fork of jitsucom/jitsu)

The Problem

Collecting event streams from web, mobile and server sources and reliably loading them into modern data warehouses often requires a proprietary SaaS stack (e.g., Segment) or a heavyweight custom pipeline. Teams that need full control over data residency, cost, or integration flexibility lack a lightweight, self‑hosted alternative that can be deployed quickly and scaled with Kubernetes.

What This Does

Jitsu provides an open‑source ingestion layer that receives events via HTTP, Segment proxy, or SDKs and writes them to a configurable set of destinations (ClickHouse, Snowflake, BigQuery, etc.).

The core ingestion engine lives in bulker/ – a Go module that implements destination adapters (bulker/bulkerlib/implementations/sql/.go, .../filestorage/.go). The admin UI and re‑processing workers are in bulker/admin/ (main.go, router.go). The runnable service is built from bulker/bulkerapp/main.go, which wires configuration sources (Postgres, Redis, file) and starts the HTTP API (bulker/bulkerapp/app/router.go).

How To Use It

Setup

Clone the repository (the fork contains the 2.0 code) git clone --depth 1 https://github.com/jitsucom/jitsu cd jitsu/docker # docker‑compose entry point Copy the example env and adjust as needed cp .env.example .env.local Start all containers (Jitsu UI, ClickHouse, PostgreSQL, etc.) docker compose up -d

The docker-compose.yml lives in docker/ (not listed above but referenced from the README) and pulls the pre‑built image defined in bulker/bulker.Dockerfile.

Configuration

Required variables are documented in .env.example (e.g., CLICKHOUSEHOST, POSTGRESDSN). Destination‑specific settings are stored in bulker/bulkerapp/app/configurationsource.go and can be overridden via the config.yaml test fixture (bulker/bulkerapp/app/testdata/config.yaml).

Running the service locally (without Docker)

Build the Go binary cd bulker/bulkerapp go build -o jitsu . Run with a config file ./jitsu -config ./app/testdata/config.yaml

The binary reads bulker/bulkerapp/app/appconfig.go for flag parsing.

Real‑World Use

A typical pipeline: Front‑end code sends events to http://<jitsu-host>/v1/event (handled by bulker/bulkerapp/app/router.go). The Bulker engine selects the destination based on the event’s destinationId and streams batches to ClickHouse via the clickhouse.go adapter. If a batch fails, the admin re‑processor (bulker/admin/deadletterreprocessor.go) can replay from the dead‑letter table.

This pattern fits a SaaS product that needs low‑latency ingestion into an analytical warehouse while retaining full control over schema evolution.

Overall, the codebase is well‑structured, with clear separation between core ingestion (bulkerlib), service orchestration (bulkerapp), and admin tooling (admin).

The Bottom Line

Jitsu delivers a production‑ready, self‑hosted event ingestion platform built in Go, with a comprehensive test suite and Docker/Kubernetes deployment support. It is best suited for teams that need full control over data pipelines and are comfortable managing Go services and container orchestration. The main caution is the multi‑module Go setup, which requires disciplined dependency management during upgrades.
