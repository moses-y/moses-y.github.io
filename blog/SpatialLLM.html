The Problem

SpatialLLM attempts to bridge Large Language Models with urban spatial intelligence through point cloud processing, OSM data integration, and scene graph generation. However, the codebase shows significant structural fragility: no test coverage, no CI/CD gate, and critical/high severity vulnerabilities in pinned dependencies that are reachable without credentials or user interaction. A consultant would flag the dependency hygiene issues as the highest priority remediation, as they represent immediate exploitable risk.

What This Does

SpatialLLM is a 24-file framework (Python/pip) that processes urban spatial data through a three-step pipeline: OSM extraction (process/osm_process.py), point cloud annotation (process/auto_annotate.py), and scene graph generation (process/generate_scene_graph.py). The inference layer (infer/inference.py) then exposes a chat interface over a model client. The repository contains no test files, no CI configuration, and a 10.8MB overview.png checked into version control — each clone and CI checkout incurs that data transfer cost. Four internal modules exist with zero import edges between them, and the two entry points (run and main) each reach 11-12 functions but are called from only a single place in the repo, indicating low internal connectivity and high external dependency.

How To Use It

Setup: Create a conda environment and install dependencies as documented in README.md:

conda create -n spatialllm python=3.8
conda activate spatialllm
conda install -c conda-forge geopandas
conda install -c conda-forge geopy
conda install -c conda-forge gdal
pip install -r requirements.txt

Configuration: The inference layer reads infer/config.yaml for client setup. No environment variables are documented beyond the conda install steps.

Running the pipeline:

  1. OSM extraction: python process/osm_process.py --shp_path <dir> --output <json>
  2. Point cloud annotation: python process/auto_annotate.py --work_dir <path> --shp_dir <dir> --pc_file <filename> --control_txt <file> --res <resolution>
  3. Scene graph generation: python process/generate_scene_graph.py --pc_file <annotated> --shp_dir <dir> --osm_map_file <file> --osm_json_file <input> --output_json <output>
  4. Inference: python infer/inference.py

Real-World Use

A city planning team could extract OSM building footprints via Step 1, annotate a LiDAR point cloud with semantic labels via Steps 2–3, then feed the resulting scene graph into infer/inference.py to enable natural-language queries like "which buildings in this district exceed 10 stories and have underground parking?" The structured text output could further power a web-based LLM interface for interactive spatial reasoning across stakeholders.

Code Health & Issues

The static analysis produced the following findings:

  • [CRITICAL] Upgrade the pinned dependency carrying a critical advisory: pillow@10.0.0 CVE-2023-50447. The manifest pins the exact vulnerable version, so the risk is active. Fix: upgrade and commit the lockfile.
  • [HIGH] Upgrade the pinned dependency carrying a published advisory: gdal@3.7.0 CVE-2026-49014. The pinned version is the one that installs. Fix: upgrade and commit the lockfile.
  • [MEDIUM] Enable Dependabot or Renovate: 1 manifest, no update bot configured. Without a bot, published advisories sit unpatched.
  • [MEDIUM] Move large binaries to Git LFS or out of the repository: overview.png is 10.8MB. Every clone pays for undiffed data.
  • [MEDIUM] Pin the resolution so a vulnerable version cannot install: no lockfile, and declared ranges reach geopandas@0.10.0 CVE-2025-69662 (high). Fix: commit the lockfile.

Beyond these measured findings: no test files, no CI/CD pipeline, no Dockerfile, and a 10.8MB binary committed directly to the repo.

The Bottom Line

SpatialLLM has a clear, functional pipeline for urban spatial reasoning, but the codebase is held back by critical dependency vulnerabilities, absent tooling (tests, CI, lockfile), and a large binary checked into version control. The four isolated modules work but lack internal cohesion — changing one step requires touching multiple files with no shared abstractions. Teams needing quick prototyping with urban spatial data could benefit from the pipeline structure, but they should pin dependency upgrades and address the hygiene gaps before production use.
