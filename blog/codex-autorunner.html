Purpose – CAR (codex‑autorunner) is a meta‑harness that schedules long‑running AI‑agent tickets, persists state in a local “hub”, and notifies via Telegram/Discord. It does not implement an agent; it orchestrates any ACP‑compatible agent (Codex, Hermes, OpenCode, etc.).

1. High‑level Architecture

  • Core orchestration lives under src/codex_autorunner/core/. The most depended‑on modules are:
  • core/utils (79 inbound imports, part of a circular import)
  • core/logging_utils (76 inbound imports, also circular)
  • core/text_utils (74 inbound imports)
  • Hub – src/codex_autorunner/core/hub.py and src/codex_autorunner/core/hub_control_plane/ expose the public API used by the CLI, web UI and agents.
  • Agents – concrete adapters live in src/codex_autorunner/agents/ (e.g., agents/acp/client.py, agents/opencode/supervisor.py).
  • Surfaces – CLI (src/codex_autorunner/cli.py), browser UI (src/codex_autorunner/browser/server.py), and webhook endpoints (src/codex_autorunner/server.py).
  • State & persistence – a SQLite‑backed “state roots” directory (src/codex_autorunner/core/state_roots.py) stores ticket markdown, execution logs and a small DB (≈181 DB‑access functions).
  • External I/O – the code reads/writes files (175 functions), runs external commands (31 functions), makes network calls (13 functions) and performs cryptographic ops (12 functions). The shortest external paths are:
  • start → from_result → session.get (network)
  • main → build_paths → state_dir.mkdir (filesystem)

3. Configuration

  • Environment – template at .env.example. Required keys include CAR_HUB_ROOT (path to the hub) and optional TELEGRAM_BOT_TOKEN, DISCORD_WEBHOOK_URL.
  • CLI – car init --mode hub creates the hub directory and writes codex_autorunner/config.yaml.
  • Web UI – launched by the entry point src/codex_autorunner/browser/server.py (start function, line 374). It binds to localhost:8000 by default.

All configuration files are version‑controlled; no secrets are committed.

4. Running the System

# Start the hub (blocks until stopped)
python -m codex_autorunner.browser.server start

# Or run the CLI entry point (useful for scripts)
python -m codex_autorunner.cli run --repo /path/to/repo

The start entry point reaches 232 internal functions and ultimately calls log_event (154 callers) before performing any external I/O.

5. Real‑World Use‑Case

A development team stores a backlog of feature tickets as markdown files under ~/car-hub/tickets. After car init --mode hub, they run car run. The orchestrator picks the first incomplete ticket, invokes the configured Codex agent via the ACP client (agents/acp/client.py), writes the agent’s output back to the ticket, and posts a Telegram message when the ticket stalls. All state lives in the local hub directory; no external service is required unless the team enables the optional webhook surfaces.

  • High – Deep nesting (max depth 8) in core/state.py, manifest.py, bootstrap.py. Refactor with early returns or helper functions.
  • High – “Hub module” (core/utils.py, core/logging_utils.py, core/text_utils.py) is a blast‑radius hotspot; keep it small and stable.

  • Medium – Oversized TypeScript file static_src/utils.ts (716 LOC); split by responsibility.

All findings include concrete fix suggestions in the analysis output.

7. Bottom Line

CAR provides a well‑structured, test‑covered orchestration layer for AI‑agent ticket execution, with clear entry points and extensive documentation. The main technical risk is the prevalence of import cycles and a few high‑complexity modules that increase change‑impact; refactoring those will improve maintainability. CI configuration should be hardened by pinning actions, limiting token scope, and adding vulnerability scans. The project is ready for production use by teams comfortable managing local state and secret handling.

Pin third-party GitHub Actions to a commit SHAhigh2 occurrences
.github/workflows
pypa/gh-action-pypi-publish@release/v1, softprops/action-gh-release@v2
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Declare least-privilege permissions for GITHUB_TOKENmedium2 occurrences
.github/workflows/agent-compatibility.yml
2 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Set persist-credentials: false on checkoutmedium
.github/workflows/agent-compatibility.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.

3 workflow(s) declare no job timeout
A wedged step runs to the six-hour platform default, which on a two-hourly schedule means three runs overlap behind it.
Fix: Add timeout-minutes with a realistic bound to each job.

Fix: Add .editorconfig, .gitattributes with text=auto eol=lf, and a formatter config.
