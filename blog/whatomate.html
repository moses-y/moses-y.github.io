The Problem

Organizations that need a WhatsApp Business integration must stitch together separate messaging APIs, authentication, UI dashboards, and analytics. Existing commercial solutions are costly and lock‑in, while open‑source alternatives rarely ship a single binary that includes both API server and a ready‑to‑run UI.

What This Does

whatomate delivers a self‑contained WhatsApp Business Platform. The Go backend (cmd/whatomate/main.go) builds a single binary that embeds the Vue‑based UI (frontend/). Core capabilities such as multi‑tenant data isolation, role‑based access control, webhook handling for Meta’s Cloud API, real‑time WebSocket chat, template & campaign management, and AI‑driven chatbot flows live in the internal/ and pkg/ packages. The docs/ folder holds a static site generated with Astro that documents the REST API and UI features.

Key files:

  • cmd/whatomate/main.go – entry point, parses CLI flags, runs DB migrations, starts HTTP server.
  • internal/handlers/*.go – HTTP handlers for agents, analytics, campaigns, etc.
  • frontend/src/components/** – Vue 3 components (shadcn‑vue) that render the dashboard.
  • docker/docker-compose.yml – orchestration of the Go service, a PostgreSQL container, and optional Redis worker.

How It Is Wired

Execution begins in cmd/whatomate/main.go. After flag parsing it calls server.Start() (in internal/server). That function:

  1. Loads configuration from config.example.toml (or a user‑provided config.toml).
  2. Initializes the PostgreSQL connection (via pkg/db).
  3. Registers routes defined in internal/router.go, wiring each endpoint to a handler in internal/handlers.
  4. Starts a WebSocket hub (internal/ws/hub.go) that pushes real‑time messages to connected Vue components.

Handlers such as internal/handlers/campaigns.go invoke service layer functions in pkg/service/*, which in turn use repository structs in pkg/repo/* to perform CRUD against the DB. The only circular import detected involves the toast UI (frontend/src/components/ui/toast/index.ts ↔ frontend/src/components/ui/toast/use-toast.ts). The most connected module is frontend/e2e/helpers/index.ts, imported by 13 test pages, indicating a high‑impact area for test‑suite stability.

How To Use It

# Clone the upstream repository
git clone https://github.com/moses-y/whatomate.git
cd whatomate

# Build the single binary (requires Go 1.24+)
make build-prod          # produces ./whatomate

# Prepare configuration
cp config.example.toml config.toml   # edit as needed (DB credentials, Meta API keys)

# Run migrations and start the server
./whatomate server -migrate

# UI is served at http://localhost:8080
# Default login: admin@admin.com / admin

Docker alternative (requires Docker Engine):

curl -LO https://raw.githubusercontent.com/shridarpatil/whatomate/main/docker/docker-compose.yml
curl -LO https://raw.githubusercontent.com/shridarpatil/whatomate/main/config.example.toml
cp config.example.toml config.toml
docker compose up -d

Both paths rely on the embedded frontend; no separate npm install is needed for production runs.

Real‑World Use

A contact‑center can deploy whatomate behind an internal reverse proxy, point the Meta WhatsApp Cloud webhook at https://myhost/api/webhook, and let agents log in via the dashboard. Campaign JSON files can be dropped into a watched directory (handled by internal/worker/campaign_worker.go), triggering bulk sends with automatic retry on failure.

The Bottom Line

whatomate offers a functional, single‑binary WhatsApp Business platform with a complete UI and extensible Go backend. It is production‑ready but carries technical debt: deep nesting, large Vue files, and a few import cycles that will increase maintenance cost. Teams comfortable with Go and Vue can adopt it quickly, especially if they address the high‑severity findings and tighten CI/CD hygiene.

Pin third-party GitHub Actions to a commit SHAhigh4 occurrences
.github/workflows
docker/setup-buildx-action@v3, docker/login-action@v3, goreleaser/goreleaser-action@v6, golangci/golangci-lint-action@v6
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Declare least-privilege permissions for GITHUB_TOKENmedium2 occurrences
.github/workflows/e2e-tests.yml
2 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Enable Dependabot or Renovatemedium
3 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
Fix: Commit .github/dependabot.yml covering the repo ecosystems plus github-actions.
Pin the container base image by digestmedium2 occurrences
docker/Dockerfile
golang:1.24.5-alpine, alpine:3.19
An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.
Fix: Use image:tag@sha256:<digest> and enable Dependabot's docker ecosystem.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Set persist-credentials: false on checkoutmedium
.github/workflows/deploy-docs.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Add a non-root USER to the imagemedium
docker/Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
Set timeout-minutes on the workflow jobslow3 occurrences
.github/workflows/deploy-docs.yml
3 workflow(s) declare no job timeout
A wedged step runs to the six-hour platform default, which on a two-hourly schedule means three runs overlap behind it.
Fix: Add timeout-minutes with a realistic bound to each job.
