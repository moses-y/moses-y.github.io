TREK

A self-hosted travel/trip planner with real-time collaboration, interactive maps, PWA support, SSO, budgets, packing lists, and more.

Forked from liketrek/TREK

The Problem Coordinating travel plans across multiple participants is fragmented: spreadsheets for budgets, separate chat tools for discussion, and ad‑hoc map screenshots for routing. Teams waste time syncing updates and reconciling expenses, especially when itineraries change on the fly.

What This Does TREK delivers a single self‑hosted web app that combines real‑time collaboration, interactive mapping, budgeting, packing lists, and a journal. The front‑end lives under client/ (the bulk of the repo, 160 files) and is built with React + TypeScript. Core UI components such as the drag‑and‑drop planner (client/src/components/Planner/...) and the collaborative chat (client/src/components/Collab/CollabChat.tsx) are shipped as reusable TSX modules. Backend services are packaged in the same Docker image defined by the top‑level Dockerfile, allowing the whole stack to run behind a single container.

How To Use It

Setup Clone the repo git clone https://github.com/liketrek/TREK.git cd TREK

Build the Docker image (the Dockerfile copies the client build) docker build -t trek .

The Dockerfile pulls Node, runs npm ci (note: no lockfile, see Issues), builds the React app, and serves it with a lightweight web server.

Configuration API endpoint and authentication details are read from client/src/api/client.ts. Adjust the BASEURL constant or inject environment variables at container start (e.g., APIURL). Optional SSO settings are stored in the Helm chart under charts/trek/values.yaml; the chart creates ConfigMaps and Secrets (templates/configmap.yaml, templates/secret.yaml).

Running Run the container, exposing the web UI on port 3000 docker run -d -p 3000:3000 --name trek trek

The entry point is the built client/index.html, which loads the bundled SPA (client/src/App.tsx). Access the UI at http://localhost:3000.

For development without Docker, inspect client/package.json for the standard scripts (npm install, npm run dev) and run them from the client/ directory.

Real‑World Use A small travel agency can deploy TREK on an internal server, point the BASE_URL to its own authentication provider, and let clients collaboratively edit itineraries. Changes appear instantly in the planner and map view, while the budget panel (client/src/components/Budget/BudgetPanel.tsx) automatically recalculates cost splits for each participant.

Code Health & Issues Low – Missing lockfile – client/package.json declares dependencies but no package-lock.json or yarn.lock; reproducible builds depend on the npm registry state. Low – Limited secret handling – No encrypted secret management in the repo; any API keys must be supplied via environment variables or Helm secrets (charts/trek/templates/secret.yaml). Medium – Potential runtime errors – Several WebSocket utilities (client/src/api/websocket.ts) lack explicit reconnection logic; edge‑case disconnections could crash the UI. Low – Test coverage – 37 test files (e.g., client/src/components/Budget/BudgetPanel.test.tsx) indicate decent unit coverage, and CI runs them via the test.yml workflow. Low – CI/CD – GitHub Actions include linting (lint-prettier.yml), Docker builds (docker.yml), and security scans (security.yml), showing an active pipeline. Low – Documentation – Core README provides feature overview and Docker badge, but lacks explicit env‑var docs; the README.md does not list required configuration keys.

Overall the codebase follows modern TypeScript practices, component separation is clear, and the presence of Helm charts (charts/trek/) suggests ready‑to‑deploy Kubernetes support.

The Bottom Line TREK offers a well‑structured, feature‑rich travel‑planning SPA that can be self‑hosted via a single Docker image, making it suitable for teams that need collaborative itinerary management on‑premise. The primary drawbacks are the missing lockfile (affecting deterministic builds) and sparse runtime documentation; these are straightforward to address. Deployers comfortable with Docker/Kubernetes will find the project ready for production use.
