The Problem: Superlog solves the problem of fragmented observability by ingesting traces, logs, and metrics, then grouping noisy signals into actionable incidents. It is designed for teams who need a local-first surface to debug production systems without navigating disjointed tooling.

What This Does: The repository is structured into distinct application layers. apps/api serves as the HTTP API backend, handling authentication, management schemas, and incident grouping logic. apps/proxy functions as the OTLP intake proxy, accepting telemetry data at http://localhost:4101. The frontend is apps/web, a Vite/React application. Supporting infrastructure includes packages/db for Drizzle ORM schemas and migrations, and packages/fingerprint for telemetry fingerprinting helpers. The codebase contains 37 test files, primarily located within apps/api/src and apps/proxy/src, indicating a focus on unit and integration testing for the API and proxy layers.

How To Use It: Setup requires Node.js 20+, pnpm 9+, and Docker. pnpm install docker compose up -d pnpm --filter @superlog/db db:migrate pnpm dev

The default local services are Web at http://localhost:5173, API at http://localhost:4100, and OTLP intake at http://localhost:4101.

Configuration requires environment variables defined in apps/api/.env.example and apps/proxy/.env.example. These files should be copied and populated with appropriate values for database connections and service keys.

Real-World Use: In a typical workflow, an instrumented service sends OTLP traces to the Superlog proxy at http://localhost:4101. The proxy forwards these to the API, where they are stored in Postgres and indexed in ClickHouse. Engineers then investigate the resulting incidents via the apps/web interface, where grouped signals and incident details are displayed for debugging.
