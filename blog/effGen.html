The Problem

Small‑language‑model (SLM) agents lack a production‑ready runtime: they need consistent prompting, tool orchestration, memory handling, and a way to expose protocols without writing boilerplate. Teams building autonomous agents spend most of their effort on glue code rather than on the model logic itself.

What This Does

effGen supplies a full‑stack framework that turns an SLM into a multi‑tool agent. Core orchestration lives in effgen/core/agent.py, which builds system prompts, resolves guardrails and drives the model’s generate calls (effgen/models/*_adapter.py). Built‑in tools such as the Python REPL, calculator and web search are under effgen/tools/builtin/.

Configuration is declarative: configs/config.yaml, configs/models.yaml and configs/tools.yaml describe agents, model endpoints and tool bindings. The CLI (effgen/cli.py) parses these files, sets up logging (effgen/utils/logging.py), and launches either a local run (agent_main) or a protocol server (effgen/tools/protocols/acp/server.py, .../mcp/server.py).

The repository also ships example agents (examples/basic/, examples/advanced/) that demonstrate single‑agent, multi‑agent and streaming use‑cases, plus a Docker deployment (Dockerfile, examples/deployment/docker-compose.yml).

How It Is Wired

Execution starts at effgen/cli.py – the main function (line 1959) is the top‑level entry point used by the effgen console script. main:

  1. Calls setup_logging → effgen/utils/logging.py.
  2. Loads configuration via effgen/config/loader.py (27 functions, 3 classes, 41 callers).
  3. Instantiates Agent (effgen/core/agent.py) – the hub module (43 inbound imports). Agent.__init__ builds a AgentConfig, registers tools (effgen/tools/base_tool.py), and creates a MessageBus.

From there run_all_tests (used by CI) and run_agent drive the core loop:

  • Agent._generate → model adapters (effgen/models/anthropic_adapter.py, .../openai_adapter.py, etc.) perform the outbound inference call (10 functions call a model).
  • Tool calls are dispatched via effgen/core/tool_calling.py, which looks up the tool class in the registry (effgen/tools/registry.py) and executes its run method (e.g., effgen/tools/builtin/calculator.py).

How To Use It

# Clone and install
git clone https://github.com/moses-y/effGen
cd effGen
python -m pip install -e .   # installs from pyproject.toml

Configuration – edit configs/config.yaml (agent defaults), configs/models.yaml (API keys, model identifiers) and configs/tools.yaml (enable/disable built‑ins). Example keys are referenced in configs/api_keys.yaml (not committed).

Run a basic agent

python -m effgen.cli --config configs/config.yaml --agent basic_agent

Start the ACP protocol server

python -m effgen.tools.protocols.acp.server --host 0.0.0.0 --port 8000

Docker

docker build -t effgen:latest .
docker run --rm -p 8000:8000 effgen:latest

The repository’s examples/ directory contains ready‑to‑run scripts (basic_agent.py, advanced_multi_tool_agent.py) that can be invoked with the same CLI flags.

Real‑World Use

A SaaS platform that offers “AI‑assisted research” can embed effGen as a microservice. The platform supplies an OpenAI key in configs/api_keys.yaml, selects the research_agent preset, and runs the ACP server behind an API gateway. Incoming requests are forwarded to the server, which spawns an Agent instance, calls the model for reasoning, and uses the built‑in retrieval tool to fetch indexed documents from the vector store (effgen/memory/vector_store.py). The whole flow touches the model (network), the SQLite memory DB (disk), and logs to stdout via the structured logger.

Additional observations: no lockfile, circular imports, deep nesting (max indentation depth 9) and oversized modules (effgen/core/agent.py ≈ 1850 LOC) increase maintenance cost. Broad except Exception clauses appear in several core files, reducing error visibility.

The Bottom Line

effGen delivers a usable, Docker‑compatible stack for turning SLMs into autonomous agents, with a clear separation of configuration, model adapters, and built‑in tools. The codebase is functional but suffers from high cognitive load (large hub modules, import cycles) and lacks reproducible builds (no lockfile, unpinned dependencies). It is suitable for teams ready to invest in refactoring the core modules and tightening the CI/CD pipeline before production deployment.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
nwtgck/actions-netlify@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Commit a lockfile beside the manifesthigh
pyproject.toml
manifest with no lockfile in scope
An unlocked range means the artifact you tested and the artifact you ship can contain different transitive code, so a malicious patch release reaches production with no diff.
Fix: Run the package manager once and commit the generated lockfile.
Declare least-privilege permissions for GITHUB_TOKENmedium4 occurrences
.github/workflows/ci.yml
4 workflow(s) declare no permissions, 1 of them reference secrets
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Enable Dependabot or Renovatemedium
3 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
Fix: Commit .github/dependabot.yml covering the repo ecosystems plus github-actions.
Pin the container base image by digestmedium
Dockerfile
python:3.11-slim
An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.
Fix: Use image:tag@sha256:<digest> and enable Dependabot's docker ecosystem.
Set persist-credentials: false on checkoutmedium
.github/workflows/ci.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Add a non-root USER to the imagemedium
Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
