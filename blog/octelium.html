The Problem

Organizations need secure remote access to private infrastructure, but existing tools force a choice: VPNs (broad network access, weak identity controls), ZTNA platforms (complex, commercial), or tunnel services (limited, no identity layer). Teams often end up running multiple tools—a VPN, a reverse proxy, an API gateway—each with separate auth and access policies. Octelium attempts to collapse that stack into one self-hosted platform.

What This Does

Octelium is a Go-based zero trust access platform that combines several functions: a WireGuard/QUIC-based remote access VPN, a ZTNA layer with per-request policy enforcement, a reverse tunnel service (ngrok alternative), and an API/AI gateway. The client/octelium/commands/connect/ directory contains the core client logic, including controller/ for the main connection lifecycle, essh/ for SSH-based access, and esocks5/ for SOCKS5 proxying. The apis/ directory holds the protobuf definitions and gRPC stubs for client, cluster, and resource management services.

The platform uses a dual-license model (Apache-2.0 and AGPL-3.0) and ships with Docker support, GitHub Actions CI, and packaging scripts for macOS (build-pkg.sh) and Windows (build-msi.ps1). The client/common/ package contains reusable CLI utilities, authentication flows (including TPM support), and a local database layer.

How To Use It

The repo is structured as a Go workspace with two modules: apis/go.mod and client/common/go.mod. The main client binary lives in client/octelium/. The Makefile at the root drives builds.

Build the client (assuming Go 1.21+ and make) make build

Or use Docker docker build -f client/octelium/Dockerfile -t octelium-client .

Run the client ./octelium connect

The README references CLI installation, cluster installation via k3s/RKE2 scripts in .github/scripts/cluster-install/, and a demo environment. The client/octelium/commands/connect/ entry points (server.go files in esshmain/, esocks5/, and essh/) suggest a connect subcommand with multiple transport modes. Exact CLI flags and configuration formats are not documented in the repo—you'd need the external docs at octelium.com/docs for full setup.

Real-World Use

A homelab operator wants to expose a self-hosted web app to the internet without opening ports. They run Octelium's cluster components on a k3s node, install the client on their laptop, and use the connect command to establish a WireGuard tunnel. The app is then reachable via an Octelium-managed domain, with access controlled by identity-based policies rather than network rules. For a team, the same infrastructure can serve as an API gateway for internal microservices, with per-request auth and rate limiting.

Code Health & Issues Med - Monorepo complexity: Two Go modules (apis/, client/common/) plus a client binary create a non-trivial build graph. The Makefile is the only build entry point; there's no root go.mod, which may complicate IDE support and tooling. Med - Platform-specific code sprawl: Files like controllerdarwin.go, controllerlinux.go, controller_windows.go suggest heavy platform branching. This is expected for a VPN client but increases testing burden. Low - Test coverage: 26 test files exist, but the majority of the client code (142 files) has no tests. The controller/ and connect/ directories are the most complex and least tested. Low - Documentation gap: The README is marketing-heavy and links to external docs. There's no in-repo API reference or configuration guide, which hurts self-hosting adoption. Positive: CI is thorough (unit tests, e2e, cluster installs, release workflows), and the dual-license approach is clear.

The Bottom Line

Octelium is an ambitious, well-architected attempt to unify secure access tooling. The Go codebase is organized and CI is solid, but it's a young project (0 stars, no release history visible) with a steep setup curve and sparse in-repo documentation. It's best suited to teams that need a self-hosted ZTNA platform and are willing to invest in learning the system; for a quick VPN or tunnel, simpler tools exist.
