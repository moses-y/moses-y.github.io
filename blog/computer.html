The Problem

Developers need a reproducible, sandboxed filesystem that can be accessed from Cloudflare Workers while keeping a single source of truth. Existing approaches either require custom infrastructure or expose the state to external storage, making coordination, security, and migration difficult.

What This Does

cloudflare/computer implements a virtual filesystem stored in a Durable Object backed by SQLite. The Durable Object exposes three interchangeable runtimes through workspace.runtime.exec(source, { backend }):

Container backend – mounts the SQLite state into a Linux container via a FUSE daemon (computerd). See the implementation in examples/container/src/index.ts and the Docker build in examples/container/Dockerfile. Isolate shell backend – runs just‑bash inside a Dynamic Worker and talks to the Durable Object over RPC (examples/worker-shell/src/index.ts). Isolate JavaScript backend – evaluates an ECMAScript module in a Dynamic Worker with a virtual node:fs/promises implementation (examples/worker-javascript/src/index.ts).

The repository is a small monorepo; each example is a self‑contained Worker project with its own package.json, TypeScript config, and optional Dockerfile. Core interface definitions live in the docs/ folder (e.g., docs/04filesysteminterface.md, docs/08capnwebinterface.md).

How To Use It

Setup

From the repo root git clone https://github.com/cloudflare/computer.git cd computer Install dependencies for a specific example, e.g. the container demo cd examples/container npm ci # lockfile missing in some examples; npm install works as fallback

Configuration

Durable Object – create a Cloudflare Workers KV namespace and bind a Durable Object named Computer in wrangler.toml (each example ships a wrangler.jsonc that contains the required bindings). Backend selection – the runtime ID is passed to workspace.runtime.exec (see examples/think/src/agent.ts for a concrete call).

Running

Container backend – build and run the Docker image:

docker build -t computer-demo -f Dockerfile . docker run -p 8787:8787 computer-demo

Worker backends – publish the Worker with Wrangler:

npx wrangler deploy

The HTTP entry point is defined in each example’s src/index.ts (e.g., examples/container/src/index.ts exports a request handler that forwards /write, /read, and /exec to the runtime).

Real‑World Use

A CI pipeline can generate temporary build artefacts inside a workspace, run a containerized toolchain (e.g., pandoc in examples/tutorial), and store the resulting PDF back to Cloudflare Artifacts via the assets backend. Sample flow:

// inside a Worker await workspace.runtime.exec( pandoc /workspace/input.md -o /workspace/output.pdf , { backend: "container" });

const pdf = await workspace.fs.readFile("/workspace/output.pdf"); await fetch("https://api.cloudflare.com/client/v4/accounts/.../artifacts", { method: "POST", body: pdf, });

Code Health & Issues

Low – Missing lockfiles – examples/artifacts/package.json (and several others) lack a package-lock.json/pnpm-lock.yaml, making builds non‑reproducible. Low – Duplicate dependency declarations – Each example bundles its own @cloudflare/computer version; drift can occur between examples. Medium – Limited test coverage for core runtime – Tests exist mainly in the think-compare-runtimes worker (examples/think-compare-runtimes/worker//.test.ts) but the container daemon (computerd) has no unit tests. Low – CI configured – GitHub Actions (.github/workflows/ci.yml) runs npm test across examples, indicating basic CI health. Low – Documentation – The docs/ folder provides a thorough specification; however, the README warns that the API is “preview only” and may change. Low – License present – LICENSE file included, satisfying legal compliance.

No obvious secret leakage or insecure default configurations were found.

The Bottom Line

cloudflare/computer delivers a flexible, Durable‑Object‑backed filesystem with interchangeable execution backends, suitable for prototyping complex Worker‑based pipelines. The codebase is well‑structured and documented, but missing lockfiles and limited core‑runtime tests mean production adoption should be preceded by a security and stability audit. Teams building experimental Cloudflare Worker tooling will find it immediately useful; production teams need to address the reproducibility and testing gaps first.
