docktail

Abstract

Expose Docker containers as Tailscale Services using label-based configuration.

Forked from marvinvr/docktail

The Problem

Docker containers need zero-configuration exposure as Tailscale services, but currently require manual service definition creation in the Tailscale Admin Console. Teams running Dockerized workloads must either maintain static service definitions or accept that containers aren't easily discoverable within their tailnet. This repo attempts to automate that discovery via label-based configuration, but the implementation carries structural risks that affect production readiness.

What This Does

docktail is a Go application that watches Docker for containers with specific labels and automatically creates corresponding Tailscale Services. The code flows through a small, resolvable call graph: main.go:21 (main) reaches 54 functions, with Run in reconciler/reconciler.go:31 as the central hub called from 18 places. Execution starts at main → setupLogging → getEnv (called x7 from main), then flows into Reconcile which orchestrates the sync between Docker container state and Tailscale service definitions.

The docker integration lives in docker/client.go (15 functions, 3 types) which defines NewClient, Close, WatchEvents, isServiceEnabled, and isFunnelEnabled. This module is called from 3 other files and handles the low-level Docker API interaction. On the Tailscale side, tailscale/client.go defines NewClient, RoundTrip, ReconcileServices, and syncServiceDefinitions - the 7 functions, 11 types module called from 2 files. Funnel configuration lives in tailscale/funnel.go (12 functions, 4 types) which defines extractPort, detectFunnelProtocol, and desiredFunnelDestination. The reconciler in reconciler/reconciler.go (3 functions) ties these together with NewReconciler, Run, and Reconcile.

Configuration reads from environment variables parsed by main.go:136's getEnv and getEnvDuration. Label parsing occurs in tailscale/funnel.go via parseFunnelConfig and in docker/client.go via parseIndexedPorts and detectFunnelProtocol. Service state management lives in tailscale/service.go with addService, removeService, and DrainService.

Outside this repository, the process mounts /var/run/docker.sock for Docker API access and /var/run/tailscale for the Tailscale socket. It emits no external HTTP server - its entire effect is mediated through the Tailscale API and Docker API calls.

How To Use It

Setup: Build from source or pull the published image:

docker compose up -d
# or
go build -o docktail main.go

Configuration: Three modes are supported. The README documents environment variables in main.go:

  • TAILSCALE_OAUTH_CLIENT_ID / TAILSCALE_OAUTH_CLIENT_SECRET - recommended for auto-service-creation
  • TAILSCALE_API_KEY - auto-creates but expires every 90 days
  • No credentials - manual service definitions required in Tailscale Admin Console

Required volumes from the README (docker-compose.yaml):

volumes:
  - /var/run/docker.sock:/var/run/docker.sock:ro
  - /var/run/tailscale:/var/run/tailscale

Running it: Start with docker compose:

docker compose up -d

Containers with labels docktail.service.enable=true, docktail.service.name=<name>, and docktail.service.port=<port> will be automatically exposed as Tailscale services. Access via http://<service-name>.your-tailnet.ts.net.

Real-World Use

A development team runs Docker Compose for their micro-service architecture. They add docktail as a sidecar service mounting the Docker socket and Tailscale socket. Their myapp service gets this label configuration:

labels:
  - "docktail.service.enable=true"
  - "docktail.service.name=myapp"
  - "docktail.service.port=80"

After docker compose up, curl http://myapp.your-tailnet.ts.net routes through Tailscale to the container IP without needing port mappings or manual DNS configuration. When the container stops, docktail drains the Tailscale service automatically.

Code Health & Issues

The static analysis found 8 findings across 5 severity levels:

  • [HIGH] Pin third-party GitHub Actions to a commit SHA - .github/workflows: golangci/golangci-lint-action@v7, docker/setup-buildx-action@v3, docker/login-action@v3, docker/metadata-action@v5. A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed.
  • [HIGH] Drop privileged mode and host networking - docker-compose.yaml: network_mode: host, the docker socket mounted. privileged hands the container every capability including direct device access, which makes escaping to the host a documented one-liner.
  • [MEDIUM] Declare least-privilege permissions for GITHUB_TOKEN - .github/workflows/ci.yaml: 1 workflow(s) declare no permissions, 1 of them reference secrets.
  • [MEDIUM] Enable Dependabot or Renovate - no update bot configured.
  • [MEDIUM] Pin the container base image by digest - Dockerfile: golang:1.25-alpine, tailscale/tailscale:latest, alpine:latest (mutable tag).
  • [MEDIUM] Gate pull requests on a dependency vulnerability scan - no dependency scan in CI.
  • [MEDIUM] Add a non-root USER to the image - Dockerfile: CMD or ENTRYPOINT with no USER directive.
  • [LOW] Set timeout-minutes on the workflow jobs - .github/workflows/docker-build.yaml: 1 workflow(s) declare no job timeout.

The Bottom Line

docktail delivers on its promise: label-configured Docker containers become Tailscale services without manual intervention. The code is resolvable with a clear call graph and reasonable structure for a small Go service. However, the HIGH findings demand attention before production use - particularly the privileged mode/docker socket combination and unpinned GitHub Actions. The deep nesting issue in three files suggests refactoring effort if the team values debuggability. Teams already invested in Tailscale who need zero-config service exposure will find immediate value; those requiring hardened supply-chain guarantees should address the pinning and privilege issues first.

golangci/golangci-lint-action@v7, docker/setup-buildx-action@v3, docker/login-action@v3, docker/metadata-action@v5
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.

docker-compose.yaml
network_mode: host, the docker socket mounted
privileged hands the container every capability including direct device access, which makes escaping to the host a documented one-liner, and host networking removes the network boundary so every port the container opens is open on the host.
Fix: Grant the specific capability the workload needs with cap_add, and publish ports explicitly.
