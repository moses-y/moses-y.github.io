The Problem

Reading a large, unfamiliar codebase costs hours of manual browsing. Traditional documentation goes stale. LLM coding assistants re-read entire folders on every query, burning tokens and context windows. No tool surfaces hidden structure—cross-references, design rationale, community clusters—in a persistent, queryable form.

What This Does

graphify runs as a skill inside Claude Code, Codex, OpenCode, OpenClaw, or Factory Droid. It scans any folder—code, docs, PDFs, images—and builds a knowledge graph (graphify/ingest.py, graphify/build.py). The first pass uses tree-sitter AST parsing across 19 languages (tests/fixtures/ contains sample files for each). The second pass dispatches Claude subagents to extract concepts and relationships from non-code files.

The output lives in graphify-out/: an interactive graph.html, a plain-language GRAPHREPORT.md, and a persistent graph.json. Every edge is tagged EXTRACTED, INFERRED (with confidence score), or AMBIGUOUS. Clustering uses Leiden community detection on the graph topology—no embeddings, no vector DB (graphify/cluster.py). A SHA256 cache (graphify/cache.py) means re-runs only process changed files.

Real-World Use

Drop graphify on a repository with a /raw folder of papers, screenshots, and notes—Andrej Karpathy's documented workflow. The tool returns a graph that reduces token consumption by ~71.5x per query versus reading raw files, and persists across sessions. Add a .graphifyignore file to exclude vendor/ or nodemodules/.

Code Health & Issues

Low - No dependency lockfile (pyproject.toml declares dependencies but no poetry.lock or requirements.txt). Builds are non-reproducible across environments. Low - 51 test files exist, and CI is configured (.github/workflows/ci.yml), but the test suite covers only unit tests on individual modules—no end-to-end tests that run the full pipeline against a real folder. Low - graphify/security.py exists but its scope is unclear from the README. No documented threat model for what happens when a malicious file enters the ingestion pipeline.

The codebase is well-structured with clear separation of concerns. Tests and CI are present, which is better than most open-source projects at this stage.

The Bottom Line

A practical, well-architected tool for teams that use LLM coding assistants on large or heterogeneous codebases. The two-pass design (deterministic AST + LLM extraction) is sensible, and the no-embeddings clustering avoids unnecessary complexity. Best suited for teams already using Claude Code or Codex who need persistent codebase understanding. Less useful for solo developers on small projects where manual browsing suffices.

manifest with no lockfile in scope
An unlocked range means the artifact you tested and the artifact you ship can contain different transitive code, so a malicious patch release reaches production with no diff.
Fix: Run the package manager once and commit the generated lockfile.
Declare least-privilege permissions for GITHUB_TOKENmedium
.github/workflows/ci.yml
1 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Enable Dependabot or Renovatemedium
1 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
Fix: Commit .github/dependabot.yml covering the repo ecosystems plus github-actions.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Set persist-credentials: false on checkoutmedium
.github/workflows/ci.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Set timeout-minutes on the workflow jobslow
.github/workflows/ci.yml
1 workflow(s) declare no job timeout
A wedged step runs to the six-hour platform default, which on a two-hourly schedule means three runs overlap behind it.
Fix: Add timeout-minutes with a realistic bound to each job.
