The Problem

Developers often need to run ad‑hoc SQL against many different back‑ends, but launching a full‑featured GUI (SSMS, DBeaver, VS Code extensions) is heavyweight for quick queries. Switching between CLI tools, driver installations, and connection strings adds friction, especially when working across cloud providers or Docker containers.

What This Does

sqlit provides an ncurses‑style TUI that discovers local Docker containers, reads cloud‑CLI credentials (AWS, Azure, GCP), and presents a modal editor with Vim‑style keybindings. The core entry point is sqlit/cli.py, which boots the Textual UI and wires the connection manager (sqlit/core/connectionmanager.py). Provider implementations live under sqlit/domains/connections/providers/ (e.g., postgresql, mysql, duckdb, aws/athena). The discovery layer in sqlit/domains/connections/discovery/cloud/ parses the respective cloud CLIs to build connection profiles. Themes and keymaps are defined in sqlit/core/keymap.py and docs/screenshots/.

How To Use It

Setup

The project uses a standard pyproject.toml. Installation is documented in the README:

pipx install sqlit-tui # recommended, isolates the tool or, from source python -m pip install . # run from the repository root

Configuration

Default settings are stored in config/sqlit-config/settings.json. Users can copy the template config/settings.template.json and edit fields such as defaulttheme, keymappath, or keyringbackend. Credentials are stored securely via the OS keyring; no clear‑text passwords are committed.

Running

Launch the TUI with the installed entry point:

sqlit # invokes sqlit/cli.py or, for a direct run from source python -m sqlit.cli

The UI presents a connection picker, which draws from: Docker discovery (sqlit/domains/connections/discovery/dockerdetector.py) Cloud discovery (.../cloud/aws/provider.py, .../azure/provider.py, .../gcp/provider.py) Saved profiles (sqlit/core/connectionmanager.py)

From there, users can edit queries, run them, and explore results with built‑in filters (sqlit/core/actionvalidation.py).

Real‑World Use

A data‑engineer on a Linux workstation needs to query a PostgreSQL instance running in a Docker compose stack and a Snowflake warehouse accessed via the AWS CLI. After installing sqlit:

sqlit # pick the Docker‑detected PostgreSQL container run quick SELECTs, copy results sqlit # switch to the Snowflake profile auto‑populated from AWS credentials

The engineer never leaves the terminal, avoids driver installation hassles (the “dependency wizard” in sqlit/domains/connections/app/installstrategy.py), and can filter millions of rows instantly.

Code Health & Issues

Low – Missing lockfile – Dependencies declared only in pyproject.toml; no poetry.lock or uv.lock → builds are not reproducible. Low – Test coverage – Only one test file detected; CI runs but does not enforce extensive testing (.github/workflows/ci.yml exists). Medium – Cloud provider error handling – Cloud discovery modules (aws/provider.py, azure/provider.py) assume CLI tools are present; missing fallback could raise FileNotFoundError. Low – License present – MIT license is included, no violation. Low – Secrets exposure – No secret keys are hard‑coded; credentials are stored via OS keyring. Medium – Tight coupling to Textual – UI logic (sqlit/cli.py) is intertwined with core connection handling, making headless usage harder without additional wrappers.

Overall, the repository follows a clear package layout, includes CI pipelines, and documents usage in the README. The primary gaps are reproducible dependency management and limited automated testing.

The Bottom Line

sqlit delivers a functional, terminal‑first experience for managing and querying a wide range of databases with minimal setup. It is well‑structured and documented, making it suitable for solo developers or small teams that prefer CLI workflows. The main drawbacks are the lack of a lockfile and thin test coverage, which should be addressed before adopting it in environments where reproducible builds and high reliability are required.
