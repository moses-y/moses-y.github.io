The Problem

This repository provides the sdk.v1 protobuf contract for driving Cursor agents from any language without depending on the official TypeScript or Python SDKs. It serves as a protocol bridge that embeds the TypeScript SDK locally and exposes its surface over Connect RPC/gRPC-Web. The primary value is enabling adapter development for new languages, but the repository itself is a thin scaffolding around generated protobuf definitions.

What This Does

The repository contains the sdk.v1 protobuf contract in proto/sdk/v1/ — seven .proto files defining agent services, bridge control, custom tools, callbacks, messages, and errors. These are generated — do not edit per the README, and are rewritten on every Cursor SDK release. The proto/manifest.json tracks protocol metadata and source commit. An examples directory contains a Python adapter under examples/python-adapter/ with 15 files including cursoradapter/ modules (bridge.py, client.py, proto.py, transport.py, errors.py, run.py, agent.py, init.py) and supporting config (pyproject.toml, requirements.txt). A standalone bridge binary is distributed per platform from releases, and the adapter's job is to spawn this bridge and speak sdk.v1 Connect RPCs to it.

Key files: proto/sdk/v1/sdkagentservice.proto, proto/sdk/v1/sdkbridgecontrolservice.proto, proto/sdk/v1/sdkerrors.proto, examples/python-adapter/cursoradapter/bridge.py, examples/python-adapter/pyproject.toml

How To Use It

Setup: Install the Python adapter dependencies from examples/python-adapter/pyproject.toml and requirements.txt via pip install -e examples/python-adapter or pip install -r examples/python-adapter/requirements.txt. The repo has no lockfile, so builds are non-reproducible at the dependency level — a pip freeze after install will resolve whatever is currently available.

Configuration: No environment variables or keys are documented in the excerpt. The bridge spawns as a local process; authentication appears to be handled through the Connect RPC layer, but no .env or config file naming is evident in the structure.

Running it: The entry point is examples/python-adapter/demo.py or examples/python-adapter/smoke.py — these likely invoke the bridge binary and issue Connect RPCs against the local socket. The fetch-bridge.sh script suggests downloading the platform-specific standalone bridge binary. A buf.gen.yaml in the examples directory indicates Protocol Buffer code generation is configured for the Python adapter.

Command reference (from repo): pip install -e examples/python-adapter or pip install -r examples/python-adapter/requirements.txt Download bridge: curl -L https://github.com/cursor/sdk-bridge/releases/latest/download/cursor-sdk-bridge-standalone-linux-x8664.tar.gz | tar -xz

Real-World Use

A TypeScript developer wants to control Cursor agents from a Go backend. Instead of using the @cursor/sdk npm package, they clone this repo, point a codegen agent at proto/sdk/v1/ to generate sdk.v1 stubs, follow the "Agent: start here" milestone plan in the README, and implement an adapter that spawns the standalone bridge binary and proxies Connect RPCs. The adapter handles agent creation, message sending, streaming runs, and custom tool callbacks over the sdk.v1 contract. The Go adapter would implement the callback services (sdkcustomtoolcallbackservice, sdkstorecallbackservice) defined in the proto files to accept tool outputs and artifact writes from the Cursor runtime.

Code Health & Issues

Low/Risk — Dependencies declared without a lockfile: examples/python-adapter/pyproject.toml lists dependencies but has no requirements-lock.txt or similar. pip install will resolve to latest compatible versions, making builds non-reproducible across environments. Low/Risk — No test files visible: Only 1 test file was detected in the analysis; the repository has no apparent test suite in the listed structure. CI (GitHub Actions) is configured via .github/workflows/proto-check.yml, but it only checks proto definitions, not adapter correctness. Med/Risk — proto/ is owned by release automation: The README explicitly states PRs must never touch proto/. This creates a hard boundary: adapters must codegen against released proto versions, but there's no tooling in this repo to manage local proto version alignment beyond buf.gen.yaml in each example. Low — No license file evidence in excerpt: LICENSE exists at root but isn't described; if absent or restrictive, it could impede adapter reuse.

The Bottom Line

This is a protobuf contract and bridge scaffolding repository, not an end-user SDK. It's well-suited for organizations building custom language adapters or service integrations who need to embed Cursor agent capabilities without depending on the official TypeScript or Python SDKs. The proto definitions are stable and well-documented, but the Python example lacks dependency locking, and there's no test coverage for the adapter code. Teams with existing codegen pipelines and Connect RPC experience will get the most value; solo developers scripting agents are better served by the official @cursor/sdk or cursor-sdk PyPI packages.
