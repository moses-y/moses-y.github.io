Self-hosted deployment platform

Forked from oblien/openship

The Problem The repository provides a self‑hosted deployment platform but declares its runtime dependencies in apps/api/package.json without a lockfile. This means subsequent installs can pull different dependency versions, producing non‑reproducible builds and potential runtime drift across environments.

What This Does Openship is a self‑hostable platform that builds, ships, routes, and TLS‑terminates applications. The code base is organized under apps/api/ (177 files, mostly TypeScript) and a small root-level set of configuration and CI files. Key entry points are apps/api/src/app.ts (the Express/HTTP server), apps/api/src/index.ts (bootstrap), and apps/api/src/config/env.ts (environment configuration). Docker packaging is defined in apps/api/Dockerfile, and the project uses GitHub Actions for CI/CD (.github/workflows/ci.yml, docker-images.yml, release.yml). Environment variables are supplied via apps/api/.env.example and its variants (.env.local-saas.example, .env.saas.example, etc.), which the code reads through config/env.ts.

How To Use It

Setup Desktop (solo) – Download the appropriate binary from the releases page (e.g., Openship-arm64.dmg for macOS Apple Silicon) and run it. The control plane runs locally while the app is open; no permanent server is required. Self‑hosted server – Clone the repo, then run openship up (referenced in the README) to start the control plane on a target machine. The command boots the API server and, by default, brings up Docker Compose services for app hosting.

Configuration Copy apps/api/.env.example to .env and fill the required variables (the file lists keys such as DATABASEURL, REDISURL, and cloud‑provider credentials). For production SaaS installs, use apps/api/.env.saas.example as a reference.

Running it Start the API: npm run start (as defined in apps/api/package.json). Build and push Docker images: the CI workflows use docker build and docker push steps; locally you can invoke docker build -t openship/api . from the apps/api/ directory.

Real‑World Use A development team can point Openship at a Git repository. On each push, the GitHub Action (ci.yml) runs tests, builds a Docker image, and triggers openship up to deploy the new version to the self‑hosted server. The platform automatically provisions TLS via Let’s Encrypt (ACME handling in apps/api/src/lib/acme-config.ts) and routes traffic through the built‑in reverse proxy. Teams benefit from push‑to‑deploy workflows without managing separate CI/CD pipelines.

Code Health & Issues Low/Risk – Missing lockfile: apps/api/package.json lists dependencies but no package-lock.json or yarn.lock is present, risking non‑reproducible installs. Tests & CI: 19 test files exist under apps/api/src/, and GitHub Actions CI is configured; the pipeline runs on every push and pull request, providing basic quality gates. Configuration hygiene: Environment examples are present, but no .gitignore‑level exclusion for secret files is evident beyond the generic .gitignore at root; verify that sensitive .env files are excluded from version control. Documentation: 7 doc files are present (README.md, CONTRIBUTING.md, SECURITY.md, TODO.md, plus i18n docs). The README contains a quick‑start table and interface overview, which is sufficient for onboarding.

The Bottom Line Openship delivers a functional, self‑hosted deployment platform with Docker packaging and GitHub Actions CI, making it suitable for teams that need push‑to‑deploy without managed cloud services. The primary drawback is the absent lockfile, which can cause version drift; adding package-lock.json (or switching to pnpm/yarn with a lockfile) should be the first maintenance item. It is well‑suited for small‑to‑medium teams comfortable with Docker and TypeScript, while solo users may prefer the desktop app for zero‑touch setups.
