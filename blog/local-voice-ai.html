The Problem

Building a production-ready local voice AI agent requires integrating multiple specialized services—STT, LLM, TTS, and WebRTC signaling—while managing subprocess orchestration, model caching, and GPU/Metal backend selection. Most open-source voice AI projects solve one piece (e.g., a Whisper STT demo) but leave the integration, deployment, and configuration burden to the implementer.

What This Does

This repo provides a supervised, single-container (or docker-compose) deployment where a Python supervisor process (localvoiceai serve) manages child processes: a LiveKit Go binary for WebRTC signaling, llama-server for the LLM via llama-cpp, a Nemotron/Whisper STT uvicorn server, and a Kokoro TTS uvicorn server. The frontend is a Next.js app (frontend/components/app/app.tsx) that connects via LiveKit Agents. Configuration is driven entirely by environment variables—point any service at a remote endpoint and the local subprocess is skipped (e.g., LIVEKITURL, LLAMABASEURL, STTBASEURL, TTSBASEURL), documented in localvoiceai/config.py. Models are cached in a named volume (local-voice-ai-models), so subsequent boots are fast and work offline.

How To Use It

Setup: The repo uses pnpm (frontend/package.json) and uv/uv.lock for Python dependencies (pyproject.toml, uv.lock). Install deps with pnpm install in the frontend and uv sync or pip install -e . from the repo root. Docker is the primary entry point: docker compose up --build (or docker compose -f docker-compose.yml -f docker-compose.gpu.yml up --build for NVIDIA GPU). The Dockerfile at the root builds the image; docker-compose.gpu.yml swaps in CUDA-accelerated binaries and grants GPU access via the NVIDIA container toolkit.

Configuration: Required env vars live in .env at the repo root and frontend/.env.local (both flagged in the heuristic analysis). Key vars include LIVEKITURL, LLAMAHFREPO / LLAMABASEURL / LLAMAMODEL for the LLM, STTBASEURL / STTMODEL / STTAPIKEY for speech-to-text, and TTSBASEURL / TTSAPIKEY for text-to-speech. Swap to OpenAI by setting LLAMABASEURL=https://api.openai.com/v1 and LLAMAMODEL=gpt-4o-mini; point at LiveKit Cloud with LIVEKITURL=wss://your-project.livekit.cloud.

Running it: Entry point is python -m localvoiceai serve (from localvoiceai/main.py), which supervises all children. Alternatively, docker compose up --build builds and starts the full stack. First boot downloads weights (Nemotron STT + Gemma 4 E2B LLM ~2.6 GB); later boots use the cached models volume.

Real-World Use

A solo developer wants a private voice interface for a local knowledge base. They set LLAMAHFREPO=org/quantized-llm:Q4KM and STTMODEL=nemotron in .env, run docker compose up --build, and point a browser to http://localhost:8080. The agent connects via WebRTC, streams audio to the local STT, routes through the LLM, and returns Kokoro TTS audio—all within one container, no cloud dependencies. The supervisor serves POST /api/connection-details (localvoice_ai/api.py) for token minting, and the Next.js frontend consumes it via frontend/app/(app)/page.tsx.

Code Health & Issues

Security (High): Possible secrets/credentials committed to the repo—.env and frontend/.env.local are tracked files. These should be gitignored and loaded only at runtime. SDLC: GitHub Actions CI configured (.github/workflows/ci.yml, build-and-test.yaml, sync-to-production.yaml), but no test coverage evidence beyond the tests/ directory (7 test files). License file present (LICENCE), which is positive. Dependency hygiene: uv.lock and pnpm-lock.yaml are present, suggesting dependency locking is enforced. No input validation or separation-of-concerns issues visible at the structural level, but the single .env file pattern risks conflating development and production credentials.

The Bottom Line

This is a well-structured, production-ready local voice AI starter kit that solves the orchestration gap through a single Python supervisor and docker-compose. It’s best for individual developers or small teams needing an offline-capable voice agent without managing separate infra. Swapping to cloud providers is trivial via URL env vars, but the tracked .env files and lack of secret management tooling are the primary risks to lock down before deployment.
