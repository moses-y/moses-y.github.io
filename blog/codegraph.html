The Problem

Coding agents waste context window and tool calls re-reading files they have already seen. Every file open, grep, and directory listing costs tokens, and agents often re-explore the same code paths multiple times in one session. A pre-indexed code graph that updates on file changes gives agents surgical access to code structure without re-scanning the tree.

What This Does

CodeGraph builds a semantic code graph from a repository and exposes it to agent tools through an MCP server. The codegraph-kernel/ directory contains the Rust-powered indexing engine, while src/ holds the TypeScript orchestration layer. The __tests__/ tree (399 files) covers language resolution, graph querying, and daemon behavior, with fixtures for TypeScript, Go, and a kernel-parity/ set spanning C, C++, Rust, Swift, Scala, Dart, PHP, Lua, and more.

The tool indexes symbols, call edges, and framework-aware routes, then serves them locally to multiple agents: Claude Code, Cursor, Codex, OpenCode, Hermes, Gemini, Antigravity, Kiro, and GitHub Copilot. A ui/ directory (97 files, Svelte-based) provides a browser view of the graph, and scripts/ (72 files) handles install, upgrade, and daemon lifecycle.

How It Is Wired

The traced entry points are all test fixtures — __tests__/fixtures/*/src/index.ts and payroll-go/cmd/payrolld/main.go — meaning the internal call graph has not been mapped for the production code paths in this repository yet. The README documents a CLI (codegraph upgrade, codegraph commands) and an MCP tool surface, but the specific function-level flow from CLI invocation through indexing to agent tool responses is not present in the analysis blocks.

What the structure does make clear: the daemon is central. Test names like daemon-manager.test.ts, daemon-registry.test.ts, daemon-socket-fallback.test.ts, and daemon-client-liveness.test.ts indicate a long-running process that agents connect to over a socket, with fallback behavior and liveness checks. The kernel in codegraph-kernel/ is the indexing core, and explore-* tests (allocation, blast radius, ranking, dedup, path pinning) show that query responses are budgeted and ranked, not raw dumps.

Real-World Use

An agent working on a large TypeScript codebase starts a session. Instead of grepping for a function and reading three files to trace a call path, it asks CodeGraph for the callers and callees of the target symbol. The graph returns the relevant edges in a few hundred tokens. When the developer edits a file, the daemon re-indexes the change, so the next query reflects current code without a full rebuild.

CodeGraph targets a real problem: agent context efficiency through pre-indexed code graphs. The fork inherits a substantial upstream codebase with broad language support and a serious test suite. The main open question is fork maintenance — with 0 stars and no topics, this is an unproven distribution of someone else's work, so pin to the upstream release unless you need this specific fork's changes.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
withastro/action@v3
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Stop discarding the exit code of steps whose failure mattershigh
.github/workflows/release.yml
lines 230 discard failure
The job reports green while the artifact it was supposed to produce was never produced, so a crash becomes a successful run built on stale data.
Fix: Let the step fail, or test the specific expected condition instead of discarding all exit codes.
Enable Dependabot or Renovatemedium
6 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
Fix: Commit .github/dependabot.yml covering the repo ecosystems plus github-actions.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.

Set persist-credentials: false on checkoutmedium

The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
