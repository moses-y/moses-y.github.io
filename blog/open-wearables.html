The Problem

Developers building health‑tech apps must write and maintain separate integrations for each wearable provider (Garmin, Apple Health, Whoop, etc.). Each integration brings its own OAuth flow, data schema, and update cadence, creating duplicated effort, fragile code, and data‑privacy concerns when third‑party services are involved.

What This Does

Open Wearables delivers a self‑hosted service that normalises data from dozens of wearables behind a single FastAPI‑based API. The core logic lives under backend/app/, e.g.:

backend/app/main.py – creates the FastAPI app object and includes all route registrations. backend/app/api/routes/v1/ – 30+ endpoint modules (e.g., oauth.py, syncdata.py, healthscores.py) implement provider‑agnostic CRUD and webhook handling. backend/app/constants/ – mapping tables (devicesmap/, workouttypes/, seriestypes/) translate raw vendor payloads into a unified schema used by the models in backend/app/models/.

The platform also ships an asynchronous processing layer built on Celery (backend/app/integrations/celery/) for long‑running tasks such as back‑filling historic data, computing resilience scores, and pushing webhook notifications.

How To Use It

Setup – The repository provides a Dockerfile for the backend (backend/Dockerfile) and a Makefile that wraps common actions. Assuming Docker is installed:

Build the backend image

docker build -t open-wearables -f backend/Dockerfile .

Create a database (PostgreSQL is the default; see backend/app/config.py for the URL) docker run -d --name pg-db -e POSTGRESUSER=ow -e POSTGRESPASSWORD=owpass -e POSTGRESDB=owdb postgres:15

Run the service

docker run -d -p 8000:8000 \ -e DATABASEURL=postgresql://ow:owpass@host.docker.internal:5432/owdb \ open-wearables

If you prefer a local Python environment, the Makefile defines a make dev target that installs dependencies from requirements.txt (implied by the presence of a backend/.python-version) and starts the server with uvicorn:

make dev # installs deps, runs: uvicorn backend.app.main:app --reload

Configuration – Runtime settings are read from backend/app/config.py. The file expects typical environment variables such as:

DATABASEURL – PostgreSQL connection string. REDISURL – for Celery task broker (defaults to redis://localhost:6379/0). Provider‑specific keys (GARMINCLIENTID, GARMINCLIENTSECRET, APPLETEAMID, …) which are referenced in the OAuth route modules (backend/app/api/routes/v1/oauth.py).

Create a .env file in the repo root and export it before launching, or supply the variables directly to the container (-e flags above).

Running it – The API is served by FastAPI; the entry point is the app object in backend/app/main.py. After the container starts, the OpenAPI docs are available at http://localhost:8000/docs. Authentication is handled via JWTs generated in backend/app/api/routes/v1/auth.py.

Real‑World Use

A fitness‑coaching SaaS can onboard a new user by: Storing the user record via POST /v1/users. Generating a provider‑specific connection link (POST /v1/oauth/link). Receiving a webhook (POST /v1/webhooks) when the user authorises the wearable. Triggering a Celery sync task (backend/app/integrations/celery/tasks/syncvendordatatask.py) that pulls activity, sleep, and heart‑rate data, normalises it through the constants modules, and persists it in PostgreSQL.

The SaaS then queries /v1/timeseries to retrieve a unified time‑series for analytics or AI‑driven recommendations.

The Bottom Line

Open Wearables provides a functional, containerised FastAPI service that abstracts away the complexity of multiple wearable APIs. It is ready for teams that can supply the required provider credentials and are comfortable managing Docker, PostgreSQL, and Redis. The codebase is organized and CI‑enabled, but developers should add clearer environment‑variable documentation and expand test coverage before relying on it for production‑critical health applications.

Pin third-party GitHub Actions to a commit SHAhigh3 occurrences
.github/workflows
dorny/paths-filter@v3, pnpm/action-setup@v4, amannn/action-semantic-pull-request@v5
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Pin the container base image by digestmedium2 occurrences
backend/Dockerfile
python:3.13-slim, python:3.13-slim
An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.
Fix: Use image:tag@sha256:<digest> and enable Dependabot's docker ecosystem.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Set persist-credentials: false on checkoutmedium

checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
