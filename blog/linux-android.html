The Problem

Many Android users want a full Linux desktop or a Home Assistant hub without rooting or a PC. Installing a distribution, configuring X11, and wiring desktop environments is tedious on Termux, leading to broken setups and wasted time.

What This Does

The repo supplies two self‑contained Bash installers:

  • termux-linux-setup.sh – provisions a graphical Linux desktop (XFCE4, LXQt, MATE or KDE) plus optional Wine, then creates helper scripts (start-linux.sh, stop-linux.sh) in the Termux home.
  • setup-homeassistant.sh – installs the Home Assistant Core Python environment and its dependencies, turning the phone into a smart‑home hub.

Both scripts share a ~60‑line block of package‑install and environment‑setup logic (identified as duplicated code). The examples/ folder contains a minimal Python HTTP server (hello_server.py) that demonstrates running a Linux service from Termux.

Documentation lives in README.md (project overview, hardware requirements, step‑by‑step usage) and examples/README.md (how to run the demo server).

How It Is Wired

Entry points – execution begins at either termux-linux-setup.sh or setup-homeassistant.sh, invoked directly from a Termux shell (bash termux-linux-setup.sh). Each script follows the same high‑level flow:

  1. Pre‑flight – checks for Termux‑X11, ensures pkg upgrade has run, and sets a wake lock (termux-wake-lock).
  2. Package install – uses pkg install to pull the required Debian packages (e.g., xfce4, wine, python, homeassistant). This block is duplicated across the two installers.
  3. Filesystem layout – creates $HOME/.local directories, writes wrapper scripts (start-linux.sh, stop-linux.sh) that launch proot-distro with the selected desktop.
  4. Post‑install – writes a log (~/termux-setup.log) and prints next‑step instructions.

No external modules are imported; the repository contains only these shell scripts and one Python example. The Python file (examples/hello_server.py) is a standalone script that starts a http.server inside the Termux environment; it contains a broad except: clause that masks errors.

Effect ownership – all side‑effects (package installs, file writes, wake‑lock) are performed directly in the two installer scripts. No shared library or central function abstracts this work, so any change to the install process must be duplicated in both scripts.

Missing wiring – there is no documented CI pipeline, no test harness, and no higher‑level orchestrator. The repository does not expose a Python module import graph beyond the single example, so the internal call graph is trivial.

How To Use It

# 1. Install Termux (F‑Droid) and Termux‑X11 (GitHub release)
# 2. Open Termux, keep it alive
termux-wake-lock
pkg upgrade -y

# 3. Pull and run the desktop installer
curl -O https://raw.githubusercontent.com/moses-y/linux-android/main/termux-linux-setup.sh
chmod +x termux-linux-setup.sh
bash termux-linux-setup.sh   # choose DE and optional Wine when prompted

# 4. Launch the desktop
bash ~/start-linux.sh
# Open the Termux‑X11 app to view the GUI

For the Home Assistant path, replace step 3 with setup-homeassistant.sh. To test the example server:

cd examples
python3 hello_server.py   # runs on localhost:8000 inside Termux

The repo does not provide a Dockerfile, Makefile, or package manager lockfiles, so no additional build steps are required.

Real‑World Use

A hobbyist can repurpose an old Pixel 4a as a portable development workstation: run termux-linux-setup.sh to get XFCE4, start start-linux.sh, and SSH into the environment from a laptop. The same phone can simultaneously host Home Assistant by also executing setup-homeassistant.sh; both services coexist because they install into separate chroot directories.

Code Health & Issues

  • High – Duplicated code blocks – setup-homeassistant.sh and termux-linux-setup.sh contain 61 identical 6‑line sections. Refactor into a shared helper script to reduce maintenance risk.
  • Medium – Broad exception handling – examples/hello_server.py uses a bare except: that swallows all errors, making debugging difficult. Replace with specific exception types or at least log the traceback.
  • No test suite – repository‑wide untested code paths.
  • No CI/CD – no automated verification of installs.
  • No LICENSE – redistribution rights are unclear.

The Bottom Line

The repo delivers a functional, zero‑root method for turning an Android phone into a Linux desktop or Home Assistant hub, with clear step‑by‑step instructions. However, duplicated install logic, lack of tests/CI, and missing licensing make it a prototype rather than production‑ready code. It is suitable for hobbyists comfortable editing shell scripts, but organizations should refactor the installers and add proper testing before wider adoption.
