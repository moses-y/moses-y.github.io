The Problem

Developers need to coordinate multiple AI‑driven code assistants without manual hand‑off. Existing single‑agent tools cannot parallelize edits, maintain shared state, or enforce consistent rules across a codebase, leading to merge conflicts and lost context.

What This Does

cas implements a factory that runs several Claude Code agents in parallel, each inside an isolated git worktree. A supervisor agent plans work, creates tasks, and merges results, while a shared SQLite‑backed context server (.claude/) stores memories, rules, and skill definitions.

Core components live under cas-cli/: src/cli/mod.rs and related files (cli/factory/.rs) drive the terminal UI and orchestrate workers. src/cloud/syncer/.rs and src/cloud/syncqueue/.rs implement the persistent context service. Built‑in agent definitions are in src/builtins/agents/.md and src/builtins/skills/.md, mirrored in .claude/agents/ and .claude/skills/.

The binary entry point is the Cargo package cas-cli, built from cas-cli/Cargo.toml.

How To Use It

Setup

Clone the repo git clone https://github.com/<owner>/cas.git cd cas

Build the CLI (release for performance)

cargo build --release -p cas-cli Or use the provided Makefile shortcut make -C cas-cli build

The resulting executable is target/release/cas.

Configuration

Persistent context files live in .claude/. .claude/settings.json holds API keys and defaults; edit it before first run. No additional environment variables are required by the code itself, but the Claude API token must be present in settings.json.

Running

Start a factory with the default single worker ./target/release/cas

Start with three parallel workers

./target/release/cas -w 3

The TUI is defined in src/cli/factory/mod.rs and renders via src/cli/tui (implicit). To attach to an existing session: cas attach <session-id> (implemented in src/cli/attach.rs). The context server runs automatically as part of the CLI process; no separate launch command is needed.

Real‑World Use

A team wants to refactor a large codebase. They launch: cas -w 5 --notify

The supervisor splits the refactor into 5 independent tasks, each worker checks out its own worktree, applies changes, and reports back. Upon completion, the supervisor merges all branches, updates the shared context, and the team receives a desktop notification. The entire operation is recorded (--record) for audit.

Code Health & Issues

Low – Missing explicit entry‑point documentation – src/main.rs is not listed; users must infer binary name from Cargo metadata. Medium – Concurrency risk – Worker‑supervisor communication via async channels (src/bridge/server/.rs) lacks visible back‑pressure handling; race conditions could surface under high load. Low – Sparse runtime tests – 13 test files exist, but many core modules (e.g., src/cloud/syncer, src/hybridsearch) have no direct unit tests. Low – Configuration secrets – API keys stored in plain JSON (.claude/settings.json) without encryption guidance. Low – License present – MIT license in LICENSE. Low – CI present – GitHub Actions workflow (.github/workflows/ci.yml) runs cargo test and cargo clippy.

Overall, the repository follows Rust best practices: Cargo.lock is committed, CI runs lint and tests, and the code is modularized with clear separation between CLI, bridge, cloud, and daemon layers.

The Bottom Line

cas delivers a functional multi‑agent coding factory with persistent context, suitable for teams that need parallel AI‑assisted development on sizeable codebases. The implementation is solid and CI‑validated, though production use should review concurrency handling and secure storage of API credentials. Teams comfortable with Rust toolchains will find it ready to adopt; solo developers may see limited benefit from the overhead of worktree orchestration.
