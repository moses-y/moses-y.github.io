open second brain

Local-first 🧠 memory for Hermes Agent that lives in your Obsidian vault and remembers project context. Nightly 😴 dream passes turn repeat corrections into confirmed preferences with measurable confidence. Adapters ship for Claude Code, Codex, and OpenClaw, with an MCP server for anything else.

Forked from itechmeat/open-second-brain

The Problem

AI agents working with Obsidian vaults lack a deterministic memory layer that survives across sessions. Without structured persistence, project context gets lost between interactions, and corrections made during one session vanish in the next. Agents either rely on fragile conversation history or fail to persist structured knowledge that humans can also read and version.

What This Does

Open Second Brain provides a local-first memory layer that stores preferences, signals, and evidence as plain Markdown files within Brain/ directories in your Obsidian vault. The system consists of a Python CLI (cli.py) with adapters for Claude Code, Codex, and OpenClaw, plus an MCP server for extensibility. Configuration lives in brain.yaml at the vault root, which declares write prefixes and authority boundaries. The 1.44.0 release fixed critical bugs including entity extraction failures on non-Latin scripts (Chinese, Thai, Lao) that caused cubic indexing slowdowns, and transient search index failures that silently triggered full rebuilds wiping all embeddings. The project structure shows docs/ contains 179 design and architecture files, while the root contains cli.py, init.py, and plugin configurations including .claude-plugin/plugin.json, .codex-plugin/plugin.json, and .mcp.json.

How To Use It

Setup: Install via the package's Python dependencies. The presence of pyproject.toml and bunfig.toml suggests both Python and Bun/Node tooling are involved, but the primary entry point is cli.py. No explicit install command appears in the excerpt, so verify the package is pip-installable or check for a local development setup.

Configuration: Create brain.yaml at the vault root to declare path prefixes and authority for agent writes. The README notes you can declare which path prefixes a caller-named write may touch, enabling controlled boundary enforcement.

Running it: Invoke the CLI with python cli.py or via the entry point. The system integrates with Hermes Agent and provides MCP server capabilities for tool integration beyond the built-in adapters.

Real-World Use

An AI agent receives a user query about a codebase feature. Instead of losing context after the response, the agent extracts entities from the interaction and writes them to Brain/decision-log.md in the user's Obsidian vault via the brain.yaml-defined prefix. The next day, a different session reads that same .md file to recall the prior decision, searches it with grep, or version-controls the change via git—all without a daemon running or external vector store charged.

Code Health & Issues Bugs / risks: The 1.44.0 CHANGELOG documents two significant bugs: entity extraction backtracking on unbroken letter sequences (affecting CJK text indexing performance), and transient search index failures classified as corruption that trigger silent full rebuilds, potentially losing all embeddings. These are documented in CHANGELOG.md and suggest the indexing pipeline needs stronger error boundaries. SDLC & code violations: Only 1 test file is present despite 200 total files. CI/CD is configured via GitHub Actions (ci.yml, release.yml), but no license file was detected in the file listing. The codebase has extensive documentation (182 doc files in docs/) but the test coverage is minimal. Dependency hygiene appears unremarkable but should be verified against the pyproject.toml and lockfiles. Configuration gaps: The brain.yaml file is referenced but not present in the repo structure—it must be created by users in their own Obsidian vaults, which creates an implicit onboarding step not captured in the codebase itself.

The Bottom Line

This is a functional local-first memory layer for Hermes Agent users who already live in Obsidian and want their AI agent to retain context across sessions. The code is structurally sound with comprehensive design documentation, but low test coverage and the two documented indexing bugs from 1.44.0 warrant caution for production use until those stability issues are resolved. Best suited for individual researchers or small teams comfortable with Obsidian workflows who need persistent agent memory without external dependencies.
