drydock

What's uncommitted, unpushed, and unreleased across every repo you own. A live TUI dashboard for a fleet of git repos.

Forked from yetidevworks/drydock

The Problem Developers with many local clones often lose track of which repositories contain uncommitted edits, unpushed commits, or pending releases. Manually running git status across dozens of directories is time‑consuming and error‑prone, leading to missed changes and delayed releases.

What This Does drydock scans a configurable set of directories (default ~/Projects as defined in crates/drydock/src/config.rs) and presents a live terminal UI that classifies each repo by three independent axes:

Working state – uncommitted, conflicted, or clean (src/fmt.rs, src/git.rs). Push state – commits present on any local branch that haven’t been pushed (src/probe.rs). Release state – unreleased, released, or needs‑release based on tags and CHANGELOG.md (src/report.rs).

The UI lives in crates/drydock/src/tui/ (mod.rs, ui.rs) and is driven from crates/drydock/src/main.rs. The core discovery logic is in src/discover.rs and src/cache.rs, which cache probe results for the fast drydock list --cached command.

How To Use It

Build / install (all three methods are verified in the repo): From source git clone https://github.com/yetidevworks/drydock cd drydock make install # installs to ~/.local/bin

Or via Cargo cargo install drydock

Or Homebrew (pre‑built formula) brew install yetidevworks/drydock/drydock

Configuration – edit ~/.config/drydock/config.toml (the path read by src/config.rs). The file lists root directories to scan; the default contains ~/Projects.

Running – the binary entry point is crates/drydock/src/main.rs. Typical invocations:

Live dashboard (default) drydock

One‑off list filtered to dirty repos in the last day drydock list --dirty --since 1d

JSON output for automation drydock list --unpushed --group acme --json

Show repos that need a release with at least three new commits drydock releasable --min-commits 3

Key bindings and commands are documented in the README and reflected in src/tui/ui.rs.

Real‑World Use A solo engineer maintains 60 micro‑service clones. Adding drydock to their daily terminal startup (drydock runs automatically via a shell alias) lets them instantly spot any service with local changes, pending pushes, or a tag lagging behind code changes. The drydock list --cached command can be scripted to fail a CI gate if any repository reports unpushed commits.

Code Health & Issues Medium – No automated tests – The repository contains no tests/ directory and CI (.github/workflows/ci.yml) only builds the binary; untested logic in src/probe.rs and src/report.rs may hide edge‑case failures. Low – Limited error handling in UI – UI code (src/tui/ui.rs) assumes successful probe data; network or permission errors could cause panics without graceful fallback. Medium – Cache invalidation – src/cache.rs stores probe results but lacks explicit TTL or file‑watch invalidation, risking stale data if repositories change outside drydock’s scan cycle. Low – Configuration defaults hard‑coded – Default scan path is baked into src/config.rs; users must create a config file manually, which could cause confusion on first run. None – License and CI present – LICENSE is included, and GitHub Actions run on push, providing basic CI hygiene.

The Bottom Line drydock delivers a focused, Rust‑native TUI for monitoring the health of many local Git clones, with clear install paths and a well‑structured codebase. The main drawback is the absence of automated tests and limited cache invalidation, which may affect reliability in edge cases. It is a solid fit for individual developers or small teams needing quick visibility into repository state, provided they accept the current testing gap.
