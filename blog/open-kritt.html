open kritt

Open-source, self-hosted AI vulnerability research tool that orchestrates agents to find and validate security issues in code.

Forked from Kritt-ai/open-kritt

The Problem

Security researchers and developers need to find code vulnerabilities at scale, but pointing a single model at an entire repository produces noisy, unverified results. open·kritt addresses this by breaking research into focused, parallelizable tasks, then de-duplicating and ranking findings with configurable validation. It is built for teams that need control over prompts, model providers, and workflow orchestration rather than opaque, black-box scanning.

What This Does

open·kritt is a self-hosted platform comprising a Node.js backend (73 files under backend/) and a React documentation/site frontend (56 files under docs-site/). The backend orchestrates agent workflows, manages scan state, and handles findings serialization. Core infrastructure includes Prisma ORM with 38 database migration files under database/init/, Docker Compose for local development (docker-compose.yml, docker-compose.dev.yml), and npm-managed dependencies (backend/package.json). Scans analyze remote or local repositories using model providers including Codex, Claude Code, OpenAI, Anthropic, and OpenRouter. Findings are enriched via post-scripts, ranked by custom severity rankers, and exported as ZIP archives with manifests through backend/src/lib/serialize.js. The workflow builder and step configuration live in backend/src/lib/defaultWorkflows.js and backend/src/lib/defaultSeverityRankers.js.

How To Use It

Setup: Clone the repository and run ./kritt setup to configure model access (Codex login or OpenAI/Anthropic/OpenRouter API keys). The .env.example at the root and backend/.env.example provide template configuration. A GITHUBTOKEN is optional for private repos.

Configuration: Required environment variables and API keys are defined in .env.example and backend/.env.example. The Prisma schema is at backend/prisma/schema.prisma with migrations in backend/prisma/migrate.js.

Running it: Start the full stack with ./kritt start (Docker Compose) or use the headless CLI with ./kritt-headless for server-only operation. The web UI runs at http://localhost:5173. Scans are created via the backend routes under backend/src/routes/ (scans, generations, vulnerabilities, workflows).

Real-World Use

A security team can define a workflow in JSON under backend/src/lib/defaultWorkflows.json, pointing at a private codebase via GITHUBTOKEN, and trigger a scan that parallelizes focused prompts across multiple agents. Post-scripts in backend/src/lib/defaultPostScripts.js validate findings, generate proofs-of-concept, and enrich the schema before export. Results including de-duplicated findings, severity rankings, and PoC source are packaged in a ZIP with a share-safe manifest—completed scans produce full exports, failed or stopped scans produce partial exports with clear markings.

Code Health & Issues Tests: 23 test files exist under backend/test/ covering accounts, model providers, environment files, and scan pagination—CI is configured via .github/workflows/ci.yml and .github/workflows/release.yml. License: AGPL-3.0 is present in LICENSE; the repo includes CODEOFCONDUCT.md, CONTRIBUTING.md, and SECURITY.md. Dependency hygiene: backend/package-lock.json is committed, and Dependabot is configured via .github/dependabot.yml. Structural concerns: The separation between backend services, database migrations, and the docs-site is clear. No obvious unsafe patterns are visible in the file listing, but the AGPL-3.0 license requires derivative works to remain open source, which is a consideration for commercial adoption. Missing evidence: No runtime security scanning or secrets-detection configuration is apparent beyond the .env.example templates.

The Bottom Line

open·kritt is a well-structured, self-hosted vulnerability research platform that trades ease-of-use for control—researchers define workflows, choose models, and retain full ownership of findings and reports. The AGPL license, Docker-based deployment, and robust test/CI suite make it suitable for teams that can self-host and need custom prompt orchestration. It is less appropriate for users seeking a hosted, turnkey solution or those restricted by AGPL compliance requirements.
