Shuffle

Abstract

Shuffle: A general purpose security automation platform. Our focus is on collaboration and resource sharing.

Forked from Shuffle/Shuffle

The Problem Security‑orchestration teams need a shared, extensible automation console that can be self‑hosted without re‑inventing the underlying workflow engine. Existing SOAR tools are often closed, hard to extend, or require heavyweight infrastructure.

What This Does Shuffle provides a web UI (React) and a Go‑based backend that together expose a workflow editor, app marketplace, and API gateway. The UI lives under frontend/ (entry point frontend/src/index.js → frontend/src/App.jsx). The server starts from backend/go-app/main.go, reads configuration from .env, and talks to an OpenSearch instance defined in backend/database/opensearch/docker-compose.yml. Dockerfiles (backend/Dockerfile, frontend/Dockerfile) and a top‑level docker‑compose.yml orchestrate the whole stack.

How To Use It

# Clone the repo
git clone https://github.com/moses-y/Shuffle
cd Shuffle

# Install UI deps
cd frontend && npm ci && cd ..

# Build Go backend
cd backend/go-app && go build -o shuffle && cd ..

# Bring up the stack (OpenSearch + UI + API)
docker compose up -d

Configuration – copy .env.example (not present, create one) and set at minimum:

SHUFFLE_DOWNLOAD_WORKFLOW_PASSWORD=…
SHUFFLE_OPENSEARCH_PASSWORD=…
OPENSEARCH_INITIAL_ADMIN_PASSWORD=…

Run – the API is reachable at http://localhost:8080, UI at http://localhost:3000. For development, start the UI with npm start inside frontend/ and the backend with go run ./backend/go-app/main.go.

Real‑World Use A SOC can deploy Shuffle on‑premises, register its existing Splunk and TheHive instances as “apps” via the OpenAPI app generator, then author a workflow that triggers a phishing‑email enrichment pipeline: the UI creates the workflow, the backend spins a Docker container for the enrichment app, stores results in OpenSearch, and posts a Slack notification—all within a single end‑to‑end run.

Code Health & Issues

Measured static findings

  • High – Hub module: frontend/src/theme.jsx (111 dependents). Keep it tiny.
  • High – Deep nesting: frontend/src/views/Workflows2.jsx (max depth 22). Refactor to early returns.
  • High – Oversized file: frontend/src/views/Workflows2.jsx (5 449 lines). Split by responsibility.
  • Medium – Empty catch: frontend/src/views/Workflows2.jsx & frontend/src/components/ShuffleCodeEditor1.jsx. Add logging or rethrow.
  • High – Import cycle: frontend/src/views/Workflows2.jsx ↔ WorkflowTemplatePopup.jsx ↔ WorkflowValidationTimeline.jsx. Break the cycle.

Code‑health audit

  • Critical – Vulnerable Go deps (golang.org/x/crypto@0.45.0, google.golang.org/grpc@1.72.2). Upgrade.
  • Critical – Committed credentials in .env. Rotate and remove from repo.
  • Critical – Secrets in .github/workflows/quick-testing.yml. Move to workflow_run or gated environment.
  • High – Unpinned GitHub Actions (docker/setup-buildx-action@v3). Pin to SHA.
  • High – Additional vulnerable Go packages (e.g., github.com/go-jose/go-jose/v4@4.1.3). Upgrade.
  • High – Docker Compose uses privileged mode and host networking. Limit capabilities and publish ports explicitly.
  • High – .env tracked in Git. Remove, add to .gitignore, provide example file.
  • High – CI never runs tests. Add a test step to existing workflows.
  • Medium – GITHUB_TOKEN permissions not scoped. Declare least‑privilege (contents: read).
  • Medium – Base images in backend/Dockerfile use mutable tags (golang:1.24, alpine:latest). Pin by digest.

The Bottom Line Shuffle is a functional, container‑ready SOAR platform with a clear UI/backend split, but the codebase suffers from large, tightly coupled UI modules, several import cycles, and serious secret‑management lapses. It is suitable for teams comfortable tightening the CI pipeline, rotating credentials, and refactoring the workflow editor before extending it in production.

golang.org/x/crypto@0.45.0 CVE-2026-42508 (critical) +26 more; google.golang.org/grpc@1.72.2 CVE-2026-33186 (critical) +3 more
The manifest pins the exact version the advisory covers, so this is not a warning about drift: the vulnerable code is what installs, and a critical rating means it is reachable over the network without credentials or user interaction.
Fix: Upgrade to the fixed version named in the advisory, then commit the lockfile.
Rotate the credentials in the committed environment filecritical3 occurrences
.env
SHUFFLE_DOWNLOAD_WORKFLOW_PASSWORD, SHUFFLE_OPENSEARCH_PASSWORD, OPENSEARCH_INITIAL_ADMIN_PASSWORD hold generated values
These values are loaded by the application at boot, so a generated value here is a working credential for something that runs.
Fix: Rotate each named credential, remove the file from the index, and replace it with a keys-only example.
Keep secrets out of workflows a fork can triggercritical4 occurrences
.github/workflows/quick-testing.yml
TWILIO_ACCOUNT_SID, TWILIO_TO_NUMBER, TWILIO_FROM_NUMBER, TWILIO_AUTH_TOKEN (publish or cloud scope)
Contributor-controlled input reaches a job holding a publish token or cloud credential, so a pull request becomes credential exfiltration.
Fix: Move secret-using steps into a workflow_run job that never checks out pull request code, or gate on an environment with required reviewers.
Pin third-party GitHub Actions to a commit SHAhigh6 occurrences
.github/workflows
docker/setup-buildx-action@v3, docker/setup-qemu-action@v3, docker/login-action@v3, docker/build-push-action@v4
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
