The Problem

Developers need an automated way to understand, navigate, and repair large, heterogeneous codebases. Manual inspection is slow and error‑prone, especially when the code spans many languages and integrates external services (GitHub, Neo4j, LLM APIs).

What This Does

Prometheus builds a knowledge graph of a repository’s files, AST nodes, and textual artefacts, then runs reasoning agents (LLM‑driven sub‑graphs) to answer or fix GitHub issues.

  • Core graph logic lives in prometheus/graph/knowledge_graph.py and the supporting types in prometheus/graph/graph_types.py.
  • Docker orchestration (Dockerfile, docker-compose.yml) provides a Neo4j instance and a Python service container.
  • The FastAPI API (prometheus/app/api/main.py, routers under prometheus/app/api/routes/) exposes endpoints for repository cloning, issue retrieval, and LLM‑based patch generation.

How It Is Wired

Startup – Execution begins in prometheus/app/main.py (lifespan function). It creates a FastAPI app, registers the JWT middleware (prometheus/app/middlewares/jwt_middleware.py), and includes all route modules (/auth, /github, /issue, /repository, /user).

Request flow (example: POST /issue/solve)

  1. JWT middleware validates the bearer token (decode_token → jwt.decode).
  2. The route handler in prometheus/app/api/routes/issue.py calls IssueService (prometheus/app/services/issue_service.py).
  3. IssueService invokes KnowledgeGraphService (prometheus/app/services/knowledge_graph_service.py), which in turn calls KnowledgeGraphHandler (prometheus/neo4j/knowledge_graph_handler.py) to read/write Neo4j nodes.
  4. For a new GitHub issue, IssueService uses GitRepository (prometheus/git/git_repository.py) to clone the repo, then FileGraphBuilder (prometheus/graph/file_graph_builder.py) to populate the graph.
  5. LLM interaction is performed by LLMService (prometheus/app/services/llm_service.py), which constructs a FakeListChatWithToolsModel (used in tests) and invokes the tool‑enabled chain (__call__ -> invoke).

External touch points –

  • Network: GitRepository → client.get (GitHub API) and LLMService → external LLM endpoints.
  • Database: KnowledgeGraphHandler writes nodes/edges to Neo4j (≈20 functions).
  • Filesystem: FileGraphBuilder, GitRepository, and various file_operation helpers read/write source files (≈26 functions).

Blast‑radius hubs – knowledge_graph.py is imported by 54 modules, docker/base_container.py by 47, and git/git_repository.py by 42. Changes in these files propagate widely, so they should remain stable and well‑tested.

How To Use It

# 1. Clone the repo
git clone https://github.com/moses-y/Prometheus
cd Prometheus

# 2. Build and start containers
docker compose up --build -d   # uses Dockerfile and docker-compose.yml

# 3. Provide runtime config (copy the example)
cp example.env .env           # edit .env to add GITHUB_TOKEN, NE04J credentials, LLM keys

# 4. Run the API (inside the container or locally)
uvicorn prometheus.app.main:app --host 0.0.0.0 --port 8000

For ad‑hoc debugging of a single issue, the script prometheus/script/github_issue_debug.py can be executed directly:

python -m prometheus.script.github_issue_debug <issue_number>

The script follows the path main → process_issue → get_github_issue (network call) → graph construction → LLM reasoning.

Real‑World Use

A CI system detects a new GitHub issue, posts its ID to /issue/solve. The service clones the repo, builds a knowledge graph, runs the “bug‑fix verification” sub‑graph, and returns a suggested patch. The patch can be auto‑applied via the /repository/create_branch_and_push endpoint, closing the loop without human intervention.

The Bottom Line

Prometheus delivers a full pipeline—from repo ingestion to LLM‑driven issue resolution—wrapped in a Docker‑composeable FastAPI service. The architecture is clear but hinges on several high‑centrality modules that need careful stewardship. Security hardening (action pinning, lockfile, container privileges) is required before production use. Suitable for teams ready to integrate automated code‑graph reasoning into their DevOps flow.

Pin third-party GitHub Actions to a commit SHAhigh2 occurrences
.github/workflows
tj-actions/coverage-badge-py@v1.8, JamesIves/github-pages-deploy-action@v4
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Commit a lockfile beside the manifesthigh
pyproject.toml
manifest with no lockfile in scope
An unlocked range means the artifact you tested and the artifact you ship can contain different transitive code, so a malicious patch release reaches production with no diff.
Fix: Run the package manager once and commit the generated lockfile.
Drop privileged mode and host networkinghigh
docker-compose.yml
the docker socket mounted
privileged hands the container every capability including direct device access, which makes escaping to the host a documented one-liner, and host networking removes the network boundary so every port the container opens is open on the host.
Fix: Grant the specific capability the workload needs with cap_add, and publish ports explicitly.
Declare least-privilege permissions for GITHUB_TOKENmedium
.github/workflows/ruff_check.yml
1 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Enable Dependabot or Renovatemedium
1 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
Fix: Commit .github/dependabot.yml covering the repo ecosystems plus github-actions.
Pin the container base image by digestmedium
Dockerfile
python:3.11-slim
An untagged or mutable base means today's build and last month's contain different libc and a different CVE set, with no record of which shipped.
Fix: Use image:tag@sha256:<digest> and enable Dependabot's docker ecosystem.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Set persist-credentials: false on checkoutmedium
.github/workflows/pytest_and_coverage.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Add a non-root USER to the imagemedium
Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.

.github/workflows/pytest_and_coverage.yml
2 workflow(s) declare no job timeout
A wedged step runs to the six-hour platform default, which on a two-hourly schedule means three runs overlap behind it.
