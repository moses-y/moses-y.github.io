The Problem

Hosting providers and SaaS operators need a low‑cost way to generate invoices, collect payments, and keep client data organized. Existing commercial platforms are expensive, lock‑in customers, and often hide the underlying logic, making custom billing rules hard to implement.

What This Does

FOSSBilling is a PHP‑based billing suite that runs on a standard LAMP/LEMP stack. The core lives under src/, with most business logic in src/library/FOSSBilling/ (e.g., Module.php, UpdatePatcher.php, Payment/Adapter/Stripe.php). UI assets for the admin theme are in src/themes/admin_default/. The package manager files (composer.json, package.json) pull in Laravel‑style helpers, React for the front‑end, and Docker for reproducible builds.

Key files:

  • src/index.php – HTTP entry point, boots the DI container (src/di.php) and dispatches to Box\AppAdmin or Box\AppClient.
  • src/console.php – CLI bootstrap used by src/cron.php and developer tools.
  • src/library/FOSSBilling/ExtensionManager.php – loads extensions from src/extensions/ (not listed but part of the architecture).

How It Is Wired

Execution starts in src/index.php. It:

  1. Loads Composer autoloader.
  2. Includes src/di.php, which creates a service container (Box\App) wiring database (Box\Database), Twig (Box\TwigLoader), and logger (Box\Log).
  3. Calls Box\App::run(). The run method resolves the request URI, selects the appropriate controller from src/library/Box/, and renders a Twig template (e.g., src/install/assets/install.html.twig for the installer).

For background jobs, src/cron.php boots the same container and invokes scheduled services defined in src/library/Box/.

Payment processing follows a thin adapter pattern: a request hits src/library/Payment/Adapter/Stripe.php (one of the high‑cognitive‑load files) which calls Stripe’s SDK and returns a result to the calling service in src/modules/Invoice/Service.php.

The internal import graph shows 21 modules with 8 import edges and no cycles. The most connected assets are the admin theme JS bundles (src/themes/admin_default/assets/js/*), each imported by a single parent and importing few helpers, giving them low instability.

The widest blast‑radius modules are src/library/FOSSBilling/Module.php and src/library/FOSSBilling/UpdatePatcher.php; both are deep‑nested (max indentation 8) and referenced by many services, so changes there ripple widely.

How To Use It

# Clone the repo
git clone https://github.com/moses-y/FOSSBilling.git
cd FOSSBilling

# Build the Docker dev environment (uses .ddev)
docker compose -f .ddev/docker-compose.phpmyadmin.yaml up -d

# Install PHP dependencies
composer install

# Install front‑end tooling
npm ci   # reads package-lock.json

# Create a database and copy sample config
cp src/config-sample.php src/config.php
# Edit src/config.php with your DB credentials

# Run the installer via web server (http://localhost)
# or via CLI for a quick test
php src/install.php

The web server entry point is src/index.php; the CLI entry point is src/console.php. Environment variables are not required beyond the DB credentials in src/config.php. Extensions are dropped into src/extensions/ and auto‑loaded by ExtensionManager.php.

Real‑World Use

A hosting reseller can point their Nginx virtual host at src/index.php, configure the MySQL DB, and enable the Stripe gateway. When a client signs up, the request flows through Box\AppClient, creates a Client model (src/library/Model/Client.php), generates an Invoice (src/library/Model/Invoice.php), and finally calls Payment/Adapter/Stripe.php to capture payment. All actions are logged via Box\Log.

The repo includes a full test suite (tests/, tests-legacy/), CI via GitHub Actions, a Dockerfile, and an Apache‑compatible license (Apache 2.0). No secrets were found in history.

The Bottom Line

FOSSBilling provides a functional, extensible billing engine with a clear PHP entry point and Docker‑ready dev setup. Code quality suffers from deep nesting, duplicated snippets, and oversized modules, which raise maintenance risk. It is suitable for teams comfortable with PHP/Laravel‑style codebases that can allocate effort to refactor the high‑complexity areas.

Pin third-party GitHub Actions to a commit SHAhigh2 occurrences
.github/workflows
jakejarvis/s3-sync-action@master, pozetroninc/github-action-get-latest-release@master
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Declare least-privilege permissions for GITHUB_TOKENmedium
.github/workflows/live-tests.yml
1 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Gate pull requests on a dependency vulnerability scanmedium
.github/workflows
no dependency scan in CI
This is the one gate that would catch a known-vulnerable package before it reaches a build, and no repository in the sample had it.
Fix: Add dependency-review-action on pull_request, or osv-scanner on push and a schedule.
Move large binaries to Git LFS or out of the repositorymedium2 occurrences
src/library/FOSSBilling/GeoIP/Databases/PDDL-ASN.mmdb
2 blobs over 5MB: PDDL-ASN.mmdb 8.4MB, CC0-Country.mmdb 6.2MB
One repository here carries twenty blobs over 5MB including a 10.9MB spreadsheet, so every clone and every CI checkout pays for data nobody diffs.
Fix: Track those extensions with LFS, or move datasets to object storage and fetch them in a setup step.
Set persist-credentials: false on checkoutmedium
.github/workflows/live-tests.yml
checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Add a non-root USER to the imagemedium
Dockerfile
CMD or ENTRYPOINT with no USER directive
A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
Set timeout-minutes on the workflow jobslow4 occurrences
.github/workflows/ci.yml
4 workflow(s) declare no job timeout
A wedged step runs to the six-hour platform default, which on a two-hourly schedule means three runs overlap behind it.
Fix: Add timeout-minutes with a realistic bound to each job.
