The Problem

Personal knowledge management tools typically require manual effort to organize, cross-link, and maintain notes. Users accumulate bookmarks, PDFs, and highlights but rarely revisit them. The knowledge degrades because no system autonomously synthesizes raw material into a durable, searchable structure over time.

What This Does

LLM Wiki implements Karpathy's concept of an AI-maintained personal wiki. The system ingests documents (PDFs, Word, PowerPoint, Markdown) via upload or a Chrome extension (extension/src/entrypoints/content/), processes them through a Python API (api/services/chunker.py, api/services/ocr.py), and stores them in either local SQLite or Supabase. The MCP server (mcp/localserver.py) exposes read, write, search, and delete tools that Claude can use directly. A scheduled Claude Routine can run nightly to synthesize new sources into the wiki autonomously.

The architecture separates concerns cleanly: an API layer for document processing (api/), a converter for file format extraction (converter/main.py), an MCP server for AI agent access (mcp/), a browser extension for capture, and a Next.js web app (web/) for browsing. The shared/sqliteschema.sql and supabase/migrations/ define the persistence layer, supporting both local and hosted deployments.

Real-World Use

A researcher clips a PDF and a blog post via the Chrome extension, adding highlights and margin notes. That night, a Claude Routine runs: it reads the new sources via MCP, extracts key concepts, writes a new wiki page, and cross-links it to existing pages. The researcher wakes up to a wiki entry with citations, a graph view of related entities, and Mermaid diagrams generated from the synthesized content.

Code Health & Issues

The codebase shows deliberate engineering: 53 test files across unit and integration tests, CI via GitHub Actions (test.yml, security.yml), Docker support for all services, and a license file. However, several issues are visible: Med - api/domain/localprocessor.py and api/services/ocr.py depend on LibreOffice and Mistral API respectively, but error handling for missing external dependencies is unclear from the structure. Users without these tools may get opaque failures. Low - The api/requirements.lock and mcp/requirements.lock files exist alongside requirements.txt, but the build process for pinning dependencies is not documented. This could lead to drift between locked and declared versions. Med - The tests/helpers/schema.sql file duplicates schema definitions found in shared/sqliteschema.sql and supabase/migrations/. Schema drift between test and production environments is a realistic risk. Low - The api/routes/ directory contains 12 route files, but no centralized error handling middleware is visible. Each route likely duplicates error handling logic.

The Bottom Line

LLM Wiki is a well-structured, test-backed implementation of a genuinely useful concept. It's best suited for individuals or teams who already use Claude and want an autonomous knowledge base without manual upkeep. The local-first design and Docker support make self-hosting practical, though the dependency on external services (Claude, optional Mistral) means it's not fully self-contained.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
google/osv-scanner-action/osv-scanner-action@v2.0.2
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Declare least-privilege permissions for GITHUB_TOKENmedium
.github/workflows/test.yml
1 workflow(s) declare no permissions
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.

5 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.

checkout keeps the token, then dependencies are installed
The token stays in .git/config for every later step, so a malicious postinstall script reads a pushable credential without one ever being passed to it.
Fix: Add with: persist-credentials: false, and pass an explicit token only to the step that pushes.
Add a non-root USER to the imagemedium

A process running as root in the container is root against every mounted volume, and it turns any container escape or writable-mount mistake from a contained problem into a host one.
Fix: Create an unprivileged user, chown what it needs, and end the Dockerfile with USER.
