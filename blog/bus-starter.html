bus starter

A starter project for @node-ts/bus for building distributed message based systems with node

Forked from node-ts/bus-starter

The Problem

Building reliable distributed systems in Node.js is hard. Message-based architectures require careful handling of routing, retries, persistence, and fault tolerance—concerns that typically end up scattered through application code. Teams often end up building ad-hoc messaging infrastructure that fails under load or loses data during restarts. This starter project addresses that by providing a working baseline for @node-ts/bus, a service bus framework that encapsulates messaging complexity.

What This Does

bus-starter is a reference implementation of a distributed message-based application. It demonstrates a complete workflow: a siren test is started, events are published on success or failure, and a failed test triggers a workflow that emails the maintenance team. The code is organized into clear layers under src/: messages/ defines the message contracts, handlers/ contains the message processors, workflows/ orchestrates multi-step processes, and services/ provides infrastructure like email-service.ts.

The core wiring lives in src/bus.ts, which configures the service bus instance. The example workflow in src/workflows/siren-test-workflow.ts shows how to coordinate a sequence of steps with compensation logic. Nine test files, including src/workflows/siren-test-workflow.integration.ts, cover the message flow with Jest.

How To Use It

Setup: Clone the repo, install dependencies with npm, and start a local RabbitMQ container. The README documents these exact steps:

git clone https://github.com/node-ts/bus-starter my-bus-app cd my-bus-app npm i docker run -d -p 8080:15672 -p 5672:5672 rabbitmq:3-management npm run dev

Configuration: There are no environment variables to set for local development. The README notes two production requirements: configure a different transport and install durable persistence. Both are documented in the @node-ts/bus documentation, not in this repo.

Running it: npm run dev transpiles and runs the application with watch mode. The entry point is src/index.ts, which initializes the bus and starts message processing.

Real-World Use

This fits where you need reliable, decoupled message processing: order processing, event-driven integrations, or background job orchestration. The siren example generalizes to any "detect failure, notify humans, track resolution" workflow. The pattern of publishing domain events and letting workflows orchestrate side effects keeps services decoupled—a maintenance team email handler doesn't need to know why a siren failed, only that it did.

The Bottom Line

This is a solid, well-organized starter for teams adopting @node-ts/bus. The structure is clean, tests exist, and the documentation is honest about what's included and what needs replacing for production. It's best used as a scaffold—clone it, study the patterns, then strip out the example and build your own messages and workflows. Teams new to message-based architectures will find it a useful reference; experienced teams might prefer to start from the framework documentation directly.
