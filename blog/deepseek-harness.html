DeepSeek Harness: Everything is a Plugin.

Forked from deepseek-ai/deepseek-harness

The Problem

Agent harnesses typically force monolithic architectures where every component is tightly coupled, making extension brittle and deployment context-specific. Teams building AI agent workflows need a framework where components can be composed dynamically without rewriting core logic or enduring breaking changes with each iteration.

What This Does

DeepSeek Harness (dsh) implements a plugin-first architecture where every element—tools, agents, UI modules—is registered as a plugin via Cordis [^1]. The .agents/notes/ directory contains 200 archived architecture decision records documenting the evolution of plugin schemas, from the custom DSL introduced in 2026-06-11-custom-schema-dsl.md to tool-schema assembly patterns documented in 2026-06-11-tool-schemas-in-prompt-assembly.md. The framework is powered by Cordis, whose spatiotemporal composability paradigm is described in the associated paper, enabling plugins to be composed across space and time rather than hard-coded into a binary.

The repository structure reflects an active development history: archived features under .agents/notes/feature/ and bug fixes under .agents/notes/bug-fix/ span from June through August 2026, covering TUI adaptations, session management, and window-specific concerns like 2026-07-05-windows-fs-permissions.md. Kubernetes is detected as the deployed framework, suggesting this is intended for containerized agent execution.

How To Use It

Setup: Clone the repository and install dependencies:

git clone https://github.com/deepseek-ai/deepseek-harness.git cd deepseek-harness pnpm install pnpm run build

The README confirms pnpm as the package manager. No root-level package.json or pnpm-lock.yaml was visible in the file listing, but the build and run commands are documented.

Configuration: The MIT license [^2] and THIRDPARTYNOTICES.md disclose dependency licenses. No environment variable or secrets configuration is documented in the excerpt; the dsh-plugin GitHub topic suggests plugin discovery is via repository metadata rather than key-based auth.

Running it: Start the Web UI with:

This serves the interface at http://127.0.0.1:3080 by default. The Web UI guide is at docs/user/guide/index.md.

Real-World Use

A development team building a code-review agent can compose plugins for file retrieval, diff generation, and LLM calls without modifying the core harness. For example, a dsh-plugin repository exposing a review-tool can be registered via the plugin protocol, and the harness will compose it into the prompt assembly pipeline described in the archived architecture notes. The plugin model means new capabilities are added by dropping a new package into the plugin path rather than forking the main binary.

The Bottom Line

DeepSeek Harness offers a genuine plugin-first model for agent composition, backed by the Cordis spatiotemporal paradigm and a documented architecture history. It is best suited for teams comfortable with rapid, breaking-interface changes and who need to compose diverse tooling across a Kubernetes deployment. For organizations requiring stability, the absence of CI, tests, and a confirmed license file are significant hurdles.
