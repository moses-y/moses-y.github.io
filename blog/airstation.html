airstation

🎵 Your own online radio station

Forked from cheatsnake/airstation

The Problem Self‑hosting a streaming radio service usually requires stitching together a media server, a database, and a custom UI. Existing solutions are either heavyweight (Icecast, Shoutcast) or require deep DevOps knowledge, making it hard for small teams or hobbyists to launch a branded station quickly.

What This Does airstation delivers a complete, container‑ready radio stack. The Go backend (cmd/main.go, internal/http/server.go) handles HLS segment generation via FFmpeg (internal/pkg/ffmpeg/ffmpeg.go) and persists station data in SQLite (internal/storage/sqlite). The public listener UI lives in web/player (entry point web/player/src/App.tsx) while the admin console resides in web/studio (entry point web/studio/src/App.tsx).

Key files illustrate the architecture:

internal/playback/service.go – orchestrates track queue, state transitions, and SSE events (internal/pkg/sse). internal/playlist/service.go and internal/queue/service.go – domain logic for playlists and the live queue. web/player/src/api/index.ts – thin wrapper around the backend HTTP API, used by both player and studio.

All components are wired together by the Docker multi‑arch build (Dockerfile, Dockerfile.multiarch) and a docker‑compose.yml that spins up the Go server and a reverse proxy (if present).

How To Use It Build the Docker image (Dockerfile builds the Go binary and the React assets) docker build -t airstation:latest . Start the stack – the compose file defines the Go service and mounts static assets docker-compose up -d (Optional) Run the front‑ends locally for development Player UI cd web/player && npm ci && npm run dev # uses vite config in vite.config.ts Studio UI cd web/studio && npm ci && npm run dev # also Vite‑based

Configuration is read from environment variables parsed in internal/config/config.go. The repo does not ship a sample .env, but the code expects at least:

PORT – HTTP port for the Go server (default 8080). DBPATH – path to the SQLite file (defaults to ./data/airstation.db).

Running docker-compose up supplies these via the environment: section of the service definition (if the compose file includes them). The Go binary is started by cmd/main.go, which creates the HTTP server defined in internal/http/server.go.

Real‑World Use A small community radio could deploy the stack on a cheap VPS:

docker-compose.override.yml (example) services: airstation: image: airstation:latest ports: "80:8080" volumes: ./data:/app/data environment: PORT=8080 DBPATH=/app/data/airstation.db

Upload tracks via the Studio UI (/studio), arrange the queue, and embed the Player URL (/player) on the organization’s website. The HLS stream (/hls/{track}.m3u8) can be consumed by any standard media player.

Code Health & Issues

Low – Missing env‑sample – No .env.example or documentation of required vars; internal/config/config.go shows defaults but a starter file would aid onboarding. Medium – Limited test coverage – Only internal/pkg/hls has unit tests (playlisttest.go, segmenttest.go). Core services (playback, playlist, queue) lack automated tests. Low – Potential race condition – internal/playback/service.go updates shared state without explicit mutexes; concurrency safety depends on Go’s channel usage, which is not verified by tests. Low – No secret scanning – No obvious secrets committed, but the repo lacks a .gitignore entry for possible credential files (e.g., .env). Low – License present – LICENSE file included, satisfying legal requirements. Low – CI present – GitHub Actions workflow (.github/workflows/docker-image.yml) builds and pushes the Docker image, confirming basic CI.

Overall the project follows a clean separation: Go backend, React front‑ends, Docker orchestration. Dependency files (go.mod, package-lock.json) are locked, and the Makefile provides standard build shortcuts (e.g., make build, make test – inferred from typical patterns).

The Bottom Line airstation offers a ready‑to‑run, Docker‑packaged radio platform with a functional UI and HLS streaming, suitable for small teams or hobbyists. It is stable enough for production but would benefit from broader test coverage and clearer environment‑variable documentation before scaling to larger deployments.
