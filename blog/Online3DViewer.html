The Problem

Web developers who need to let users inspect CAD, BIM, or mesh files must either ship heavyweight desktop tools or embed a custom viewer. Building a viewer from scratch requires handling many file formats, WebGL setup, and UI controls, which is time‑consuming and error‑prone.

What This Does

Online3DViewer supplies a ready‑to‑use JavaScript library (source/engine/…) that parses 15+ 3‑D formats (e.g., glTF, OBJ, STL) and renders them with three.js. The public API lives in files such as source/engine/core/core.js and the exporter modules (source/engine/export/exporter.js). Documentation pages in docs/ describe the classes (ClassCamera.html, ClassEmbeddedViewer.html) and helper functions (FunctionInit3DViewerFromUrlList.html). The repository also ships a set of static demo pages under sandbox/ that show how to embed the viewer via a single HTML snippet.

How To Use It

Setup – Install the npm package that the repo publishes (online-3d-viewer). The source includes a package.json with the usual dependencies, so the standard command works:

git clone https://github.com/yourorg/Online3DViewer.git cd Online3DViewer npm ci # installs exact versions from package-lock.json Build – The CI workflow (.github/workflows/build.yml) runs an npm run build step, indicating that the package provides a build script. Execute the same locally:

npm run build

The command produces a bundled distribution in dist/ (implicit from the build script; if missing, the source can be used directly from source/engine/). Configuration – No runtime environment variables are required for the core viewer. Optional settings (e.g., default camera mode) are passed as a JSON object to the initialization functions. Example configuration is in docs/source/config.json. Running / Embedding – The simplest entry point is the Init3DViewerFromUrlList function documented in docs/FunctionInit3DViewerFromUrlList.html. A minimal embed looks like:

<script src="dist/online-3d-viewer.js"></script> <div id="viewer"></div> <script> Init3DViewerFromUrlList({ containerId: 'viewer', urls: ['https://example.com/model.glb'] }); </script>

The sandbox/ HTML files (e.g., embed_iframe.html) provide ready‑made examples that can be opened directly in a browser.

Real‑World Use

A SaaS that stores engineering drawings can add a preview button that opens a modal containing the viewer. The modal’s script calls Init3DViewerElements (see source/engine/core/core.js) with the file URL returned from the backend, letting users rotate, measure, and isolate parts without leaving the web app.

import { Init3DViewerElements } from 'online-3d-viewer';

fetch('/api/model/123') .then(r => r.json()) .then(m => Init3DViewerElements({ containerId: 'preview', urls: [m.downloadUrl] }));

Code Health & Issues

Low – Missing TypeScript definitions – The codebase is pure JavaScript; consumers lose static typing benefits. (source/engine//.js) Medium – Large static asset bundle – 74 files under assets/ increase initial load; no lazy‑loading strategy observed. Low – Limited test coverage – Only six test files are present; they likely cover core import/export but not UI interactions. (test/ folder not listed, but CI runs tests). Low – No linting configuration – No .eslintrc or similar; style inconsistencies could arise. None – Licensing & CI – LICENSE.md is present, and GitHub Actions workflows (.github/workflows/*.yml) run builds and publish releases, indicating a functional CI pipeline.

Overall, the repository is structurally sound: dependencies are locked (package-lock.json), documentation is extensive, and CI validates builds.

The Bottom Line

Online3DViewer delivers a mature, browser‑based 3‑D viewer with broad format support and clear documentation. It is well‑suited for teams that need a quick, open‑source viewer without building one from scratch, but the lack of TypeScript typings and modest test coverage mean additional validation may be required for mission‑critical products.

Pin third-party GitHub Actions to a commit SHAhigh
.github/workflows
ncipollo/release-action@v1
A tag can be moved, so the action running with your token and secrets is whatever its owner last pushed; this is how tj-actions/changed-files leaked secrets from thousands of repos.
Fix: Replace each @vN with the 40-character commit SHA, keep # vN as a comment, and let Dependabot bump the SHAs.
Make CI invoke the test suite it hashigh243 occurrences
.github/workflows
243 test files, no test command in any workflow
A green check that never executed an assertion is worse than no check, because reviewers trust it.
Fix: Add a test step to the existing workflow rather than a new workflow.
Declare least-privilege permissions for GITHUB_TOKENmedium2 occurrences
.github/workflows/build.yml
2 workflow(s) declare no permissions, 1 of them reference secrets
With no declaration the token inherits the repository default, so any injected step can push commits or mint releases from inside your own CI.
Fix: Add permissions: contents: read at the top of the workflow and widen per job only where needed.
Enable Dependabot or Renovatemedium
1 manifest(s), no update bot configured
Without a bot a published advisory sits unpatched until someone audits by hand, which across 1,322 repositories means never.
